* The one idea the implementation must not lose

`@score` adds NO runtime concept. Every driver already `%yield`s exactly one
0..1 progress signal (`stdlib/primitives/animation/drivers.st`), and a score
is a pure derivation over that signal:

: &lower-third at 2s for 3s          // inside @score &.time(60s)
: $lower_third_progress <- clamp01(($film_progress * 60000 - 2000) / 3000)

If an implementation step starts introducing a scheduler object, a clip list
walked by a tick loop, or a second progress pipeline — stop. That is the
design being lost, and it is how live and rendered films diverge (001b §8.6).

** t3b — `score_rest`: `gap(...)` and `hold(until:)` (DEFERRED, not forgotten)

SIP-001 §Proposal/4 sketches `score_rest` as part of the score body:

: %capture_type score_rest { ( "gap(" $d:measure ")" ) | ( "hold(until:" $cond:expr ")" ) }

t2 implemented `score_line` and `score_mark` but NOT `score_rest` — caught by
the t2 review swarm. Deliberately deferred rather than dropped, because the two
halves have different weights:

- `gap(2s)` is sugar. A gap is an absence, and an absence is already
  expressible by where the next clip starts (`at`). It earns its place only if
  a relative-sequence score (one with no absolute `at` anywhere) is common
  enough that computing the offsets by hand is the pain. Decide with a worked
  example, not in the abstract.
- `hold(until: $cond)` is NOT sugar and must not be conflated with `rate: 0`.
  `rate: 0` freezes ONE CLIP while the timeline runs; `hold` stops the
  PLAYHEAD. The spec calls conflating them the likely bug, and W4.4's gate
  already demands the distinction be asserted. `hold` is also the interactive
  gate that makes a slide deck or a scrollytelling checkpoint work, so it is
  load-bearing for the `.steps` pole.

RESOLVED 2026-08-02. `gap` LANDED; `hold(until:)` is deliberately NOT in W4,
and the reason is a design finding rather than a scheduling choice.

`hold` does not belong to the window map at all. R3's IR maps a parent's
progress to a child's — it answers "given the playhead is HERE, where is this
clip?". `hold` changes where the playhead GOES, which is a property of the
TRANSPORT, i.e. of the driver. The spec already says exactly this (§5: "freeze
= one clip stops while the timeline runs; hold = the playhead stops"), and the
distinction survives contact with the implementation: `rate 0` is a window map
whose integral is flat, while `hold` is a driver that stops advancing.

So implementing `hold` as score-body vocabulary would have been the wrong
shape — it would have put a transport concern in the arrangement layer, and
that IS the pressure I flagged. The right home is a driver-level concern
(`&.time(interrupt: hold)` already has the vocabulary from B8, and `.steps`
needs the same mechanism to wait for an advance signal). It lands with the
`.steps` driver, where there is a real consumer to design against — one worked
example beats a speculative surface.

R3 is UNPRESSURED by this: the window map stays a pure function of its input,
and a held playhead simply stops producing new inputs. Nothing about the
purity claim bends.

** t4 — lowering: the window map (R3)

A score line lowers to a derived signal per clip. `during A to B` resolves
windows from named spans; `mark &name` is a named point other placements
reference. Nested scores compose because a window map of a window map is a
window map.

** t5 — promote the clip driver

`&.clip` is `primitive: planned:clip-driver` ⇒ E0948 today. The thesis test
cannot run without it. `domain: inherited` — the clip reads the window its
parent assigned, which is exactly the R3 IR seen from the inside. NB this is
the honest-dead pattern working as intended: the word was reserved and loud,
never silently wrong.

** t6 — `rate:` as the map's derivative (P13, W4.4)

`rate: 1 -> 2` ramp · `rate: 0` freeze · `rate: -1` reverse. Gate: `rate: 0`
(one clip holds, timeline runs) vs `hold(until:)` (playhead stops) asserted as
DIFFERENT — conflating them is the likely bug.

** The lesson worth carrying to W5

Every defect this wave was a SILENT ACCEPTANCE, and the gates that caught them
were the ones asserting a NEGATIVE or evaluating a VALUE. The gates that missed
them all asserted that something was produced. `rate 2` behaving identically to
`rate 1` was invisible to a test comparing compiled output and obvious the
moment the map was evaluated over sample points. A wave whose deliverable is
behavior needs at least one gate that observes behavior — this one shipped
without it, and BUG-258 is the bill.
