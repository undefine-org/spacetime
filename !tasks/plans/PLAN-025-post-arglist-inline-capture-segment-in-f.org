* Goal
Make `%form` patterns able to capture inline elements BETWEEN the parenthesized arg-list `)`
and the body `{` — the `: $returnType:typeref` run in `@fn`/`@compute`. Fixes BUG-045
(returnType silently dropped; @compute E0804; projects/jallete never compiled). General fix,
not a special-case.

* Non-goals
- NOT touching the operator algebra (`:` stays "type/static annotation").
- NOT re-introducing deleted legacy data macros.
- NOT changing how pre-arglist inline / params / body_params are matched.

* Root cause (verified)
FormClause (src/parser/meta_ast.rs:286) has 3 ordered segments only: inline_elements
(before `(`), params (inside `()`), body_params/body_capture (inside `{}`). The run between
`)` and `{` has no home. parse_form_pattern (src/parser/mod.rs:3476) grabs body via
`after_params.find('{')` and discards the `)`..`{` text. The events directive grammar ALREADY
captures those tokens (second `inline_args(p)` call at directives.rs ~40, "Consume trailing
tokens between ')' and '{'"), flattening them into ctx.inline_tokens — so the matcher's main
cursor reaches them after step 2; only the FormClause model + form-pattern parser + a matcher
step are missing.

* Design — Execution Manifest

** PA-001 Model: FormClause.post_arg_inline
Add `pub post_arg_inline: Vec<FormInlineElement>` (with `#[serde(default)]`) to FormClause
(meta_ast.rs:286). Derive `Default` on FormClause so the ~37 struct-literal sites can append
`..Default::default()` instead of every site spelling the new field. Field holds the inline
elements parsed from the `)`..`{` run, same element vocabulary as inline_elements.

** PA-002 Parser: parse the )..{ run
In parse_form_pattern (mod.rs:3476), in the `Some(paren_start)` branch after computing
`after_params` and locating `brace_start`: parse `after_params[..brace_start]` (the run before
the body, after `)`) via the existing parse_form_inline_elements into post_arg_inline. When
there is no body (`{` absent), parse all of after_params. Set the new field on the FormClause
built at mod.rs:3594. Guard: a leading `:` in that run is a literal element (already handled by
parse_form_inline_elements which emits Literal(":")), and the typeref capture follows.

** PA-003 Matcher: step 3.5 (match post_arg_inline)
In form_compiler.rs::try_match, AFTER step 3 (ARG_LIST params) and BEFORE step 4 (BODY):
iterate self.form.post_arg_inline matching each element against the MAIN `cursor` (which, post
step-2 + flattened trailing ARG tokens, is positioned at the `)`..`{` tokens) using the same
match_inline_element path. Must run on BOTH the has-ARG_LIST and no-ARG_LIST branches (a form
can have post-arg inline whether or not params matched). Apply optional/default semantics
identically to inline_elements.

** PA-004 Scoring + construction-site cutover
Update form_scoring.rs if it counts inline elements for specificity (post_arg_inline literals
like `:` should contribute like inline literals so `@fn(...)‌: T {…}` out-scores a barer form).
Append `..Default::default()` (or the explicit field) to all FormClause struct literals
(~37 sites, mostly tests) so the crate compiles.
