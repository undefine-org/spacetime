* Context

Scroll-driven animations on ora-ventures.com (/en/) show final states immediately instead of animating. Two root causes:

** Primary regression: scope default change
Commit =ac5bb3e8= (March 8) changed the =@scroll= macro's default =scope= from =cover= to =entry= in =stdlib/macros/timeline.st=. For the 300vh scroll-locked sections, this compressed the animation range from ~3072px to ~768px, causing all sequential panel animations to fire in under one viewport height. All 34 =@scroll= blocks in =ora-ventures.com/index.st= rely on the default. Sites that need =entry= already specify it explicitly.

** Latent composition bug
When two =@scroll= animations target the same CSS property on the same element (the in/out pattern: =work-panel-1-in= and =work-panel-1-out= both setting =opacity= on =[data-panel="crystal"]=), the =apply-animations= primitive unconditionally writes to =el.style[property]=. At init, the out-animation's start state (=opacity: 1=) overwrites the in-animation's start state (=opacity: 0=). During scroll, microtask ordering causes the first-registered animation to always write last, preventing later animations from controlling the property. Masked by overlay positioning but architecturally incorrect.

** Approach
1. Revert the scope default to =cover= (one-line stdlib fix, zero website changes)
2. Add per-element, per-property ownership tracking in =apply-animations.st= (prevents the composition clobber)

** Key decisions
- No website code changes required
- =cover= is the safer default — works for both reveals and scroll-scrubbed sequences
- Ownership model: active animations (=0 < progress < 1=) always claim; boundary animations (=progress=0= or =1=) only write if already owner or uncontested
- Transform sub-properties tracked individually (=translateY=, =scale=), not composite
