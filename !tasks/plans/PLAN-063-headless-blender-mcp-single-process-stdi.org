* Why NOT the community ahujasid/blender-mcp shape

Traced its wire protocol: Blender addon opens a TCP socket (port 9876) inside a
LIVE GUI Blender session, requiring a human to manually click "Connect to MCP".
A separate stdio MCP process bridges an MCP client to that socket. This is built
for interactive chat-driven modeling with a human present — not for an agent
generating assets headlessly in a repo pipeline. Wrong shape for our use case.

* What was actually verified this session (2026-07-04)

1. System Blender (5.1.2, Arch pkg) uses the SYSTEM Python 3.14 as its
   interpreter (`sys.executable` = /usr/bin/python3.14) — NOT a vendored/frozen
   interpreter. `pip install --break-system-packages mcp` installs directly
   against it. This is what makes a single-process design possible at all.
2. `asyncio` + stdio pipes work fine inside `blender --background --python
   script.py` — no competing GUI event loop blocks it. Verified with a minimal
   stdin-readline loop.
3. `bpy`/`bmesh` can construct real procedural geometry headless (hexagonal
   prism via bm.faces.new + extrude_face_region + bevel), assign a
   Principled-BSDF PBR material (maps 1:1 onto three.js MeshStandardMaterial:
   baseColorFactor/metallicFactor/roughnessFactor), and export valid glTF 2.0
   via `bpy.ops.export_scene.gltf` — confirmed by inspecting the binary glTF
   JSON chunk directly (magic, version, meshes, materials, accessors all
   correct).
4. CRITICAL BLOCKER FOUND + FIXED: Blender writes its startup banner + "Blender
   quit" directly to the process's stdout (fd 1), which corrupts a naive stdio
   JSON-RPC channel — `ModuleNotFoundError`-free MCP client got
   `mcp.shared.exceptions.McpError: Connection closed` until this was fixed.
   FIX: dup the real stdout fd BEFORE bpy has a chance to write to it, rebind
   fd 1 -> /dev/null for the rest of the process, and hand MCP's
   `stdio_server()` the protected fd re-wrapped as a text-mode `anyio` async
   file (`anyio.wrap_file(os.fdopen(dup_fd, "w", encoding="utf-8"))`). This is
   presumably WHY the community project routes around stdio with a TCP socket
   instead — a stdio-native fix was found here.
5. Blender's isolated Python startup IGNORES `PYTHONPATH` env var entirely
   (verified: sys.path has no trace of it even when exported). Deps must be
   `sys.path.insert(0, "...")`'d INSIDE the bootstrap script itself, before
   `import mcp`.
6. Draco compression IS available in Blender's gltf exporter by default and
   MUST be explicitly disabled (`export_draco_mesh_compression_enable=False`)
   to satisfy the existing `stdlib/3d` constraint (`three-entry.ts` excludes
   DRACOLoader — see stdlib/3d/primitives/three-gltf.st NOTE).

* Proposed design: single-process headless MCP server (not a TCP bridge)

Register directly in spell.kdl exactly like Spacetime's own MCP server:

```kdl
mcp {
    server "blender" type=stdio timeout=120000 {
        command "blender"
        args "--background" "--python" "tools/blender-mcp/bootstrap.py"
    }
}
```

One process. No GUI. No socket. `tools/blender-mcp/bootstrap.py` IS the MCP
server — runs inside Blender's interpreter with direct bpy/bmesh access, tools
return `.glb` paths droppable straight into `projects/<name>/models/`.

Advantages over the community shape:
- Same operational pattern as the existing `spacetime` MCP server in this repo
  (stdio, one binary, cwd-scoped) — consistent mental model.
- Zero manual GUI step, fully agent/CI-drivable.
- No TCP port to manage or collide with anything else on the box.
- Deterministic: each call can spin a fresh `--background` process (safer,
  no state leakage across calls) — or we keep one warm process if latency
  matters; this is a real design knob to decide, not yet chosen.

*** NEW bug found + fixed during Wave 1 (not in the original PoC)
=assign_material= silently dropped the material on ANY object that had
already been through a =boolean_op= \u2014 a boolean-modifier apply leaves a
stray EMPTY (=None=) material slot on the target mesh (Blender pads a slot
for the tool object even when it had none), and if every face still pointed
at that empty slot, the freshly-appended real material had zero faces using
it \u2014 glTF export silently drops UNUSED materials with no diagnostic. Root-
caused by isolating a minimal box-minus-sphere repro (material survived
there) vs. the full medallion script (material vanished) and diffing the
two. Fix: after appending a new material, re-target any face still pointing
at an empty slot to it, so a plain \"assign one material to this object\" call
always actually paints the whole thing (verified: exported glb now lists
the material; before the fix, =MATERIALS: []=).

Manual MCP stdio CLIENT (list/call/script subcommands) \u2014 lets an agent (or

* Wave 2 SHIPPED — hardening verification (2026-07-04, same session)

** Concurrency: VERIFIED SAFE, no code change needed

Stress-tested via 3 independent scripts (since deleted from /tmp after use,
reproducible from the descriptions below):

1. =asyncio.gather()= of 5 concurrent =create_primitive= calls against one
   live server \u2014 all 5 succeeded with correct, non-corrupted vertex counts
   (8 each), no interleaving artifacts.
2. Riskier case: =asyncio.gather()= of 6 concurrent =(clear_scene \u2192
   create_primitive)= pairs \u2014 the exact shape that WOULD race if
   =bpy.context.active_object= got clobbered mid-sequence by another
   task. All 6 completed correctly with distinct object names/sizes,
   zero cross-contamination.

Root cause of why this is safe (not luck): =_dispatch()= in bootstrap.py is
FULLY SYNCHRONOUS \u2014 it contains no =await= internally. Python's asyncio
scheduler can only switch tasks at an =await= point, so even with N
concurrent MCP tool-call requests queued via =tg.start_soon()= in the mcp
SDK's =Server.run()=, only ONE =_dispatch()= body can be mid-execution at
any instant \u2014 the rest are serialized by construction, not by an explicit
lock. This is a real, load-bearing property of the current design: DO NOT
introduce an =await= inside =_dispatch()= (e.g. for a future async bpy
operation) without adding an explicit =asyncio.Lock()= around scene
mutations, or this safety guarantee silently breaks.

** Error surface: VERIFIED CLEAN, no code change needed

Tested two failure shapes against a live server:
1. A logical error we raise ourselves (=boolean_op= referencing a
   nonexistent object name) \u2014 surfaces as a structured
   =`{"error": ..., "trace": ...}`= via the normal MCP content channel (the
   existing =try/except Exception= in =call_tool= already handles this).
   Scene state after the error: fully intact, subsequent calls
   (=assign_material=, =export_glb=) on the surviving object succeeded.
2. Reusing an object already CONSUMED by a prior =boolean_op= (Blender
   deletes the =tool= object as part of the op) \u2014 same clean error, same
   scene-state integrity confirmed by a follow-up =assign_material= +
   =export_glb= both succeeding on the surviving object afterward.

Also re-confirmed the Wave-1 empty-material-slot fix holds under this exact
boolean-then-assign sequence: exported glb had =materials: ["Mat"]= with
the primitive's =material= index correctly remapped (dispatch printed
=slot: 1= internally i.e. the material landed in Blender's 2nd slot after
boolean padded an empty 1st slot, but glTF export correctly compacts unused
slots away \u2014 verified via direct glTF JSON-chunk parsing, not assumed).

** Decision: cold-per-script-invocation (no change from current drive.py
   design), warm-within-a-script

=drive.py='s =script= subcommand already gives the right granularity: ONE
Blender process/scene per multi-step build (the common real workload \u2014
"model this asset end to end"), fresh process per INVOCATION of =drive.py=
itself. This is the right default because:
- Asset generation is not a high-frequency/low-latency workload \u2014 Blender's
  ~1-2s startup cost per invocation is immaterial against the seconds a
  multi-step geometry build already takes.
- Cold-per-invocation means zero state leakage risk between UNRELATED build
  sessions (no need to trust every future tool author to remember to call
  =clear_scene= first) \u2014 the safest default, and =clear_scene= remains
  available for intentional same-session resets mid-script (as the
  medallion build script itself demonstrates: it doesn't need it since
  each script invocation starts fresh, but a LONGER script wanting to
  build multiple unrelated assets from one warm process could call it
  between them).
- No warm-process pooling/reuse infrastructure needed \u2014 avoids an entire
  class of "which warm process is this call talking to" bugs for zero
  proven benefit at current usage scale.

If a future workload needs many small, latency-sensitive calls (e.g. a
live-preview loop), THAT would be the trigger to revisit \u2014 not built
speculatively here.
