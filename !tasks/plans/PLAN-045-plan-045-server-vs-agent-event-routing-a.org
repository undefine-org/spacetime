* Initial Message
User, driving the live MCP workbench: "i also would like to lessen the need for
the agent to do stuff. this is super roundabout; there's a whole category of
requests that can be fulfilled directly by the server without passing through the
agent. the agent should only receive messages it was specifically meant to
receive (generally speaking by having sent those to the agent, or if the .st file
represents an agent-control interface kind of thing)."

* Goal
Make the live MCP environment SELF-DRIVING for the class of requests the server can
resolve on its own (navigation, inspection, toggles), and wake the agent ONLY for
events that are agent-addressed. Today every browser click lands in one undifferentiated
event queue and `st_await` drains all of it — so server-handled nav clicks sit in the
agent's await stream, cost a turn, and can even satisfy an UNRELATED armed await.

Target: a browser click routes by a declared AUDIENCE. Server-audience actions
(st_env_open / st_tab_open / mcp_refresh) run synchronously at the signal sink, update
input.json, repaint — agent never involved. Agent-audience actions (kit-choice /
kit-confirm / kit-submit, and any action a page declares agent-control) are the ONLY
events `st_await` ever returns.

* Design — registry-as-data + audience (passes the elegance bar)
Per AGENTS.md: variants must be DATA (registry entries), not a Rust match-arm per case;
the change must DELETE a special-case; testable by the SAME machinery it generalizes.

** The action registry (single source of truth)
Replace BOTH match blocks (live.rs:739 + tools.rs:532) with one registry:

  enum Audience { Server, Agent }

  struct ActionSpec {
      action: &'static str,
      audience: Audience,
      // Server specs carry a resolver fn(workbench/state, payload) -> Result<(summary, data)>.
      // Agent specs carry none — the event is delivered to the agent verbatim.
  }

  fn action_registry() -> &'static [ActionSpec] { ... }   // the ONLY place actions are enumerated

  Built-in specs:
    st_env_open       -> Server (resolver: open_environment_action)
    st_tab_open       -> Server (resolver: open_tab_action)
    mcp_refresh       -> Server (resolver: refresh snapshot)
    st_workbench_refresh -> Server (alias)
    kit-choice        -> Agent
    kit-confirm       -> Agent
    kit-cancel        -> Agent
    kit-submit        -> Agent

  Lookup(action) -> Option<&ActionSpec>. The two former dispatchers become ONE function
  that takes a spec: Server -> run resolver synchronously at the sink; Agent -> mark the
  event agent-audience and DO NOT resolve (the agent reads it via st_await).

** Audience on the event (the await filter)
- Add `audience: Audience` to `LiveEvent`, set at `record_event` time by registry lookup
  (default for an unregistered action: see "page-declared" below).
- `await_event` filters: only `Audience::Agent` events advance/satisfy `await_cursor`.
  Server events are recorded in `instance.events` (so the comms drawer still shows the
  full history) but are INVISIBLE to st_await. This kills the wrong-consumer bug AND the
  turn-cost: nav never wakes the agent.
- Non-`mcp-action` events (raw `message`/`clicked` envelopes): default Agent (a bare
  signal a page sends is, by definition, something it wants the host/agent to see),
  UNLESS a future page opts out. Keep v1 conservative: only `mcp-action` is registry-routed;
  everything else stays Agent-audience (status quo for those paths).

** Page-declared agent-control (the extensibility hook)
The user's second route to the agent: "if the .st file represents an agent-control
interface". For an action NOT in the built-in registry:
  - default audience = Server-REJECT (return ok:false "unknown action"), so an
    unrecognized click never silently wakes the agent. This is the safe default and
    matches "agent only gets what's meant for it".
  - a mounted instance MAY declare itself agent-control (carries an `agent_control: true`
    or an `agent_actions: [..]` allowlist, sourced from the mount). For such an instance,
    unregistered actions route to the AGENT instead of rejecting. This is how a bespoke
    agent-control surface (not a kit) gets its custom events through without a Rust change.
  SCOPE NOTE: if this needs a new st_mount param + state plumbing beyond a small field,
  it is W3/S0 — the built-in registry already covers EVERYTHING that exists today (kits +
  workbench), so v1 is correct and complete without it. Decide during W3 by inspection;
  do not speculatively add a mount param.
