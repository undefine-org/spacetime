* Key decisions made this session

1. Naming collision resolved: existing =@host= macro (transport binding
   http/ws/live) is unrelated — new macro is =@deploy=, not =@host=.
2. CLI architecture: `spacetime host` in the OSS `verse` binary is a THIN
   PATH-shim to a standalone `spacetime-host` binary living in
   `commercial/host/`, not a subcommand implemented in the OSS crate itself
   — keeps commercial code out of the OSS binary entirely.
3. Reuse verdict: fork+leanify `~/code/ora/push-website`'s `push-online*`
   crates (server/core/dom) as the v1 backend — production-proven today,
   ~80% of v1 backend design is already solved there.
4. v3 preservation directive: do NOT delete push-online's analytics/
   injection/tracker code during the v1 leanify pass — move it into a
   dormant module so v3 (macro-driven analytics/A-B) forks it instead of
   rewriting from scratch.
5. Stack: v1 AND v2 stay pure Rust/Axum. Elixir+Phoenix+NIFs only enters if
   a specific v3 feature (live collaborative multi-editor) demands it —
   `elixir/spacetime_lv` bridge already exists in-repo and would be reused,
   not reinvented, if/when that's prioritized.
6. Status-widget persistence reuses EditAst verbatim (existing protocol,
   `docs/CONTENT_EDITING.md` §8 PLAN-034 singleton-editing pattern) — no new
   persistence mechanism invented.

  work than adopting OTP's primitives for this specific feature.

RESULT: reversed the prior "v2 stays Rust-only" recommendation. v2 now
introduces a real Elixir/Ash service, extending the ALREADY-EXISTING
elixir/spacetime_lv (verified via mix.exs: bare Phoenix 1.8 + LiveView

features, not a blanket language preference.

api_tokens bearer token instead of calling WorkOS directly.
