**Fixed — closing. This was the root of the LSP cluster.**

The static `include_str!` registry is **deleted**. The language server now serves the compiler's live registry, project overlay included.

**Your measurement was the whole issue in one number** — 97 leading form tokens in the compiler versus what the editor advertised.

**The mental model.** The compiler builds its registry by *loading* stdlib and the project overlay, so it always knows exactly what macros exist — including ones your own project defines. The LSP maintained a hand-written list of files, embedded at compile time, and skipped any that failed to parse. Two sources of truth for the same fact.

**Two sources of truth don't drift if someone maintains them.** The real problem is that **nothing failed when they diverged**, so the drift was invisible until a user hit it. That's the actual defect — not the staleness, but the absence of any force keeping them aligned.

So the fix wasn't better syncing. It was **deletion**: one registry, two front-ends.

**A concrete win you can check:** macros defined in your project's `_prelude.st` now get completion, hover and go-to-definition. The embedded copy could never see them at all, because they aren't in stdlib.

**And a real defect the work uncovered:** `@data inline $items` was recording the name *with* the `$` sigil, so definitions never linked to `@each` usages of it. That's fixed too — it's the kind of thing that only surfaces once you're serving real data instead of a snapshot.
