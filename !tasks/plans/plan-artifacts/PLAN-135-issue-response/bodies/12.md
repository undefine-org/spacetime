**Fixed — closing.**

`@stage` on a non-canvas element is now a compile error:

```
error[E0963]: @stage requires a <canvas> element
```

`canvas.hero { @stage { … } }` compiles and emits as before. A selector with no tag at all (`.hero`) can't be checked statically, so it warns (`W0963`) rather than guessing — never silent, never a false error.

**The mental model, and it's a core one.** In Spacetime, macros declare *where they may be used* as **data**, not as code. A macro already says things like:

```spacetime
%macro stage {
  %scope selector      // "attach me to a selector scope"
  …
}
```

`%scope` already understood `file`, `selector`, `property-value` and `within(<construct>)`. This adds one more kind — `%scope element(canvas)` — so the requirement "this needs a `<canvas>`" is stated **once**, in the macro, and the compiler enforces it at bind time.

Two things follow, and they're the reason this took a wave rather than a patch:

1. **A compile-time-knowable constraint belongs in the declaration, not a runtime guard.** Before this, three.js's try/catch plus a sibling `console.warn` were the only things between you and a blank page. Now the error arrives before you ever open a browser.

2. **New constraint kinds must be new data, not new Rust branches.** The variants live in the registry. Adding "must be a `<video>`" tomorrow is a registry entry, not a compiler change. A closed set of cases in the compiler that the runtime doesn't fully enforce is exactly how the two drift apart.

Related note: `@object` and `@light` deliberately did **not** get this constraint. They are scene *children* — they compose against the stage's handle rather than a DOM element, and legitimately live inside a `@stage` body. Requiring a canvas selector on them would be redundant and wrong. The stage alone owns the canvas requirement.
