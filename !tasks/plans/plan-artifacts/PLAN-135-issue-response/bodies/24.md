`splitText` now reads from an immutable snapshot of the author's original content, so calling it repeatedly is stable. Verified: 2 passed.

**The lesson here is one of the most transferable in front-end work.** A DOM transform must be **idempotent**, or it must read from a snapshot it owns. The moment a transform's input is its own past output, calling it twice is a *different program* than calling it once.

Your specific case: `splitText` re-snapshotted `Array.from(el.childNodes)` on every call, so the second call saw the spans the first call had created, and split those.

Adding observers turns "twice" from a hypothetical into a guarantee — and your note about `ResizeObserver` firing before `IntersectionObserver` is exactly right. Observers fire in an order you do not control, so any transform reachable from one must be safe to run at any time, in any order, any number of times.

**An honest limitation.** There is no `ResizeObserver` at the logic rung, so the resize-triggered re-split path is **not exercisable** in the headless test at all.
