* Problem

Spacetime evolves its authoring surface aggressively (pre-release, hard
cutovers: FEAT-072 killed @bind/@show/@input; PLAN-023 W5 killed the
paren-forms of @data/@each/@computed). Today each retirement costs:

1. A hand-written tombstone `%form` in stdlib (keeps the directive
   RECOGNIZED so it fails loud, not silently dropped) — e.g.
   stdlib/macros/data.st `%macro bind/show/input-bind`.
2. A hardcoded Rust checker per retirement —
   `check_bind_deprecation()` + `bind_migration_hint()` in
   src/pipeline/mod.rs:1363-…, emitting E0910 with hand-written,
   per-parameter hint strings.
3. A prose migration doc (docs/MIGRATION.md) the user must apply by
   hand, file by file.

This is exactly the rot the AGENTS elegance bar names: syntax
retirements are DATA, but each one currently costs a Rust match-arm.
And the developer experience is "error wall": old sites break the
moment the toolchain updates, with no mechanical path forward.

* Design — %migration: syntax rewrites as stdlib data

** Elegance-bar check (all four hold)

1. Small extension of EXISTING grammar/registry: one new meta-def kind
   (`%migration`), whose match half IS the existing `%form` grammar and
   whose storage IS the existing MetaRegistry + stdlib loader.
2. Variants are DATA: each retired syntax = one `.st` entry under
   `stdlib/migrations/`. Zero Rust per migration.
3. DELETES existing special-cases: `check_bind_deprecation()` +
   `bind_migration_hint()` (≈100 lines of Rust) and the three tombstone
   `%macro`s in stdlib/macros/data.st are all replaced by data entries.
4. Testable by the SAME machinery: `%match` is parsed by the same
   `%form` PEG (CapturePatternParser), matched by the same form-matcher
   that produces FormMatch — a migration test is an ordinary
   compile-input → diagnostics/output test, plus headless .st tests for
   the widget.

** Grammar (author surface, stdlib-only `%` domain)

#+begin_src spacetime
/// stdlib/migrations/2026-06-09-bind-text.st
%migration bind-text-to-arrow {
  %date 2026-06-09
  %docs "FEAT-072: @bind(text:) became the `text <- $expr` arrow binding."

  %match {
    @bind(text: $x:expr)
  }

  %rewrite {
    text <- `$x`;
  }
}
#+end_src

- `%migration <ident>` — unique id (validated at load; duplicate id =
  stdlib load error).
- `%date YYYY-MM-DD` — REQUIRED. ISO-8601 date literal; lexicographic
  order == chronological order. THE wave key: a wave is the set of all
  migrations sharing one date. Waves apply oldest-first.
- `%docs "…"` — one-line human description; surfaces in the pill panel,
  `check` output, and the W-diagnostic.
- `%match { … }` — EXACTLY the `%form` body grammar (same parser path,
  same capture types, same `$name:type` captures). Registers in the
  form-directive index like a macro form so old syntax still parses
  into a FormMatch instead of being dropped as an unmatched child.
- `%rewrite { … }` — a source-text template. Holes are backtick-quoted
  captures: `` `$x` `` (harmony rule: backtick is THE hole form
  everywhere; bare `$x` in the template is literal output text, which
  rewrites need — e.g. rewriting TO a `$signal <- v` surface). Splice
  value = the RAW SOURCE SLICE of the capture (via
  FormMatch.capture_spans, which already exists), never a typed
  re-serialization — formatting/expressions survive verbatim.
- `%hint "…"` — ALTERNATIVE to `%rewrite` for retirements that are not
  mechanically rewritable (need auxiliary rules or human judgment).
  Exactly one of `%rewrite` | `%hint` must be present (load-time
  validation).

Two migration kinds, one grammar:
- rewrite-kind → compat shim (compiles) + auto-apply (pill/CLI).
- hint-kind → hard error E0910 (as today), but message/hint now come
  from the registry entry, not Rust; pill lists it under "manual".

** `@version` — the project's syntax-version fact (user revision)

User surface (`@`, not `%` — it lives in USER source):

#+begin_example
@version 2026-06-09;
#+end_example

- Location: the project's ROOT entry file (index.st — the file the
  server/CLI compiles as the entry; same place @deploy{} lives as a
  compile-time fact). One per project; duplicate or non-root
  declarations = compile error.
- Backed by an ordinary stdlib %macro (`%form { @version $d:date ; }`)
  — no Rust parser special-case; the compiler reads it as a fact the
  same way read_deploy_project_id reads @deploy{}.
- MEANING: "this project's source is written against the syntax as of
  this wave date." It is the disambiguation key that FIXES the shadow
  guard (see Risks):
  - migrations with %date ≤ @version are INERT for this project —
    they neither match, shim, nor count as pending. The project has
    already crossed that wave; its source means the NEW thing.
  - migrations with %date > @version participate normally (shim +
    pending).
  - ABSENT @version = date-zero: every wave participates (the
    bootstrap case — pre-existing projects).
- WRITE-BACK: the FIRST persisted apply (pill POST or `spacetime
  migrate`) INSERTS `@version <applied-wave-date>;` at the top of the
  root entry file (after any leading doc comments); every subsequent
  apply UPDATES the date in place to the newest applied wave. The
  in-memory shim NEVER writes it — only persistence does (shim is
  read-only by definition).
- Consequence for syntax REUSE: once a wave retires a form and a
  project's @version passes it, the same directive name/shape can
  later be legitimately re-introduced as a live macro — version-
  scoped matching resolves what the global shadow guard alone could
  not (old projects still get the migration; new projects get the
  live macro).

** Mechanics — in-memory shim (one implementation, two consumers)

The shim and the on-disk apply are the SAME function over (source,
matches, registry) → rewritten source. No parallel implementations.

Compile-time pass (in `compile_pipeline`, after parse, before Resolve):

0. Read the project's `@version` fact from the root entry; drop every
   migration wave with %date ≤ @version from consideration (inert).
1. Scan `ast.matches` for FormMatches whose directive resolves to a
   migration `%match` (registry lookup by form-directive, marker flag).
2. If any rewrite-kind matched: compute replacement text per match by
   instantiating `%rewrite` with raw capture slices; splice into the
   SOURCE string at FormMatch.span, applied in reverse span order
   (established pattern: edit_collector / apply_text_patch both do
   reverse-order splicing).
3. Re-parse the rewritten source; loop. Waves apply in date order;
   fuel = (number of distinct dates + 1) iterations, so chained
   rewrites (wave 1: A→B, wave 2: B→C) terminate and a cycle is a
   load-time validation error, not a hang.
4. Emit ONE W-diagnostic per applied match (new code, next free W07xx
   — "old syntax auto-migrated in memory; persist via the migrations
   pill or `spacetime migrate`") carrying migration id + %docs line.
5. Hint-kind matches short-circuit to E0910, message built from the
   registry entry (id + %docs + %hint). E0910 semantics unchanged;
   its message source moves from Rust strings to data.
6. Record pending entries `{migration_id, date, file, span, old_text,
   new_text|hint}` on the compile output — the single source the
   status route, `check`, and CLI all read. No second scanner.

Constraint (observed): the shim needs SOURCE TEXT. `Compiler::from_file`
has it; a bare `Compiler::from_ast` (no source) cannot splice — there,
rewrite-kind matches degrade to the E0910 error path with a
"recompile from source to auto-migrate" hint. All server/CLI paths use
from_file, so in practice the shim always runs.

Trade-off accepted: comments INSIDE a matched span are consumed by the
rewrite (span-replacement). Surrounding trivia is untouched (splice is
span-exact on the original source). Documented in the language doc.

** Persistence — pill, CLI, check (three consumers, one rail)

- `POST /__spacetime/migrations/apply {date}` (dev server, dev-mode
  only like host/push): runs the SAME rewrite fn over each project .st
  file, writes results to disk atomically (write-temp-rename), then
  writes/updates the `@version` fact in the root entry (insert on
  first apply, update in place after), returns
  `{files_changed, per_file_counts, version}`. The existing file
  watcher then triggers live-reload naturally — no bespoke reload
  path.
- `GET /__spacetime/migrations/status.json`: compiles project entries
  (through the existing compile cache), aggregates pending entries →
  `{waves: [{date, migrations: [{id, docs, kind, count}], total}]}`.
- CLI `spacetime migrate <path> [--wave YYYY-MM-DD] [--dry-run]`:
  headless/CI form of the same apply; dry-run prints a unified diff.
- `spacetime check` gains a summary line when pending > 0 (reads the
  same pending entries; no new scan).

Safety: apply only ever touches files under the project dir (never
stdlib/, never vendored paths), refuses when the file changed on disk
since the scan (mtime check), and is idempotent — after a successful
apply, a rescan MUST report 0 for that wave (this is an
integration-test acceptance, not an aspiration).

* Risks
- Host-pill positioning refactor (W4) is the only change touching an
  existing user-visible surface — mitigated by explicit live-browser
  acceptance and by keeping the panel's own anchoring untouched.
- Shadowing a LIVE macro: RESOLVED by `@version` (user revision this
  session). Matching is version-scoped — a migration only ever
  matches in a project whose @version predates its wave, so a
  directive retired in wave N can be re-introduced as a live macro
  for projects at @version ≥ N with zero ambiguity. Residual
  load-time check kept: a %match colliding with a live %macro form

  re-parse step (loop step 3) → surfaced as a stdlib-entry error with
  the migration id, never a silent bad splice.
