** W1 DESIGN RESOLVED (2026-06-19) — construct choice per project

*** Construct survey (all four evaluated against real lowering + the projects' actual structure)
- `.cls: $bool` / `.cls: $expr` (reactive class) — element stays, class flips; CSS owns visibility. Cheapest. W0 made it provable + total.
- `@state(when: $x is Variant)` — attr `data-st-<sig>-type` + CSS; mutually-exclusive by construction, payload-carrying. BUT fed only by @socket today (watchTypedUnion needs a {type} union object); no author-facing local enum-signal rail. PRESERVED by W4, not used for migration.
- `@match $x { "v" => &tpl() }` — RENDER-ONCE (match-render primitive, mount-time dispatch, NO signal subscription). Cannot react to a click that advances state. Wrong tool for any of these migrations. (Confirmed from stdlib/primitives/match-render.st doc + emit: no local:updated listener.)
- `@view $x { "v" => &tpl() }` — the REACTIVE sibling of @match (view-mount subscribes + re-mounts on change). Verified working with a plain `$tab string` local signal (no @socket). BUT it mounts TEMPLATES into a host → using it requires extracting static HTML into `@template`s.

*** Decisive fact: ALL THREE projects are static-HTML hybrids
jallete/index.html, jeton/index.html, playground/index.html are static markup; the .st file styles + drives behavior. The walkthrough/tab/drawer DOM ALREADY EXISTS in HTML. Therefore:
- @view would force extracting that static markup into @template definitions (heavy; jeton has TWO parallel columns .wf-N + .ws-N keyed on one step → two @view hosts + 10 templates). Not warranted.
- The lightest CORRECT migration that preserves the static markup is: a $-signal + reactive class/attr on the element + CSS fan-out. The element stays put; the signal flips; CSS shows/hides. This is the canonical idiom W0 fixed and proved.

*** Per-project final shapes
**jallete** (drawer toggles, genuine 2-state):
  $cartOpen bool: false;  $cfgOpen bool: false;
  .jal-cart { .is-open: $cartOpen; }   .jal-configurator { .is-open: $cfgOpen; }
  triggers (already @on click): replace `@emit open_configurator` → `$cfgOpen <- true;`,
  close handlers → `$cfgOpen <- false;`; cart `@emit add_to_cart` → also `$cfgOpen <- false; $cartOpen <- true;`.
  CSS: `.jal-cart.is-open { /* visible state, lifted from the old @state(when:"open") block */ }`.
  Removes the FEATURE_PARITY.md "cart drawer opening handled by JS controller" gap.

**jeton** (5-step wizard, n-state, two parallel columns, NO stateful inputs in steps — verified):
  $step number: 1;
  Replace the @state_machine block with reactive class on the walkthrough container:
    .walkthrough { .at-1: $step == 1; .at-2: $step == 2; .at-3: $step == 3; .at-4: $step == 4; .at-5: $step == 5; }
  and CSS fan-out (lifted from the old per-step blocks):
    .walkthrough.at-1 .wf-1, .walkthrough.at-1 .ws-1 { display: block; }  (etc; default .wf-*/.ws-* display:none)
  Step buttons (already @on click stepN-click animations): add `$step <- N;` (1..5).
  Restart control: `$step <- 1;`.
  NB chose container-class + CSS fan-out over 10 per-element bindings: ONE signal, ONE reactive
  binding site, exclusivity via the single `.at-N` class; CSS already expresses the 10-element
  show/hide. (@view rejected: would require 10 @templates + 2 hosts for static markup that already exists.)
  walkthrough.test.st: rewrite to drive `[data-step-btn=N]` clicks → assert `.walkthrough` has `.at-N` and
  the right `.wf-N`/`.ws-N` is visible (computed display is a CDP concern; assert the class on --headless,

**playground** (tabs, n-state + a SEPARATE css @transition to preserve):
  $activeTab string: <first-tab-id>;   (ids from the existing .tab markup / data attr)
  .tab { .is-active: $activeTab == <thisId>; }  — but tabs are multiple elements; use a data attr the
  markup already carries: `.tab { .is-active: $activeTab == &.dataset.tab; }` is NOT expressible (reactive
  binding compares to a signal, not per-element attr). RESOLUTION: emit one binding per tab id keyed on the
  tab's own selector, OR (cleaner) drive a container attr `[data-active-tab]` + CSS
  `[data-active-tab="code"] .tab[data-tab="code"] { active styles }`. Decide at W2 start by reading the exact
  .tab markup in index.html; prefer the container-attr form (one signal, CSS fan-out, mirrors jeton).
  Triggers: `.tab { @on click { $activeTab <- &.dataset.tab; } }` (or per-tab literal).
  PRESERVE the css-property `@transition { background 200ms; border-color 200ms }` — it is NOT the state
  machine; it is a CSS transition and must remain untouched. Also retire the `@state active/inactive` CSS
  blocks into plain `.tab.is-active { ... }` / `.tab { ... }`.

*** Probe pattern (W0-proven, file-scope authoring matches production)
File-scope `.sel { @on click { $sig <- v; } }` triggers + file-scope `.sel { .cls: $sig; }` bindings, then
`@when .trigger click` → `@then .target should have_class "..."`. Verified green end-to-end in W0.

*** Why NOT @match (answering the design question directly)
@match is render-once by primitive design (its own doc: "@match dispatches a single time when the host
mounts"; @view "keeps the host in sync ... for the page's lifetime"). A wizard/tab advance is a live signal
change, so @match cannot express it. @view could, but forces static-HTML→@template extraction not justified
here. The reactive-class+CSS path is the harmonious choice for static-HTML pages and is what W0 hardened.
