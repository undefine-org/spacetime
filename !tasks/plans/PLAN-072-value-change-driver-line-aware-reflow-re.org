* Origin

User request (verbatim, after 3 rounds of box-hack patches this session —
BUG-172, BUG-175, BUG-176 — each fixing a symptom of the same missing
foundation): "please look at the text module in the stdlib and please think
about what the value-change syntax tried to achieve... now that you have
access to the full strength of the vendored pretext module, how would you
re-implement this to work properly? For example, text that ends up changing
from one line to two should know that it's going to be two lines and
smoothly reorganise the text around it in a lean way. Same thing for the
vice-versa."

* Diagnosis

`value-change-driver` (`stdlib/primitives/animation/drivers.st`, 55+ commits
of history, oldest predates `pretext` entirely) animates text CONTENT
changes character-by-character (split-flap style), but had ZERO concept of
LINE layout — it always called pretext's line-breaker at `containerWidth =
Infinity` (forcing single-line), and reshaped its box reactively via
box-level WAAPI height/width tricks whenever content happened to wrap. Every
bug fixed earlier this session (BUG-172 false-wrap + width-snap, BUG-175
baseline-toggle height-shift, BUG-176 letter-spacing-blind measurement) was
a symptom of this SAME missing foundation: the driver never asked "how many
lines will this text take against the real container width," so it could
never distinguish "a persisting word relocated to a new line" (should
GLIDE) from "a word's characters actually changed" (should split-flap).

Additionally traced: the driver embedded its OWN private, frozen copy of
pretext (~700 lines of minified JS inlined via `%emit prelude-js`), while
`stdlib/text` already vendors the SAME engine's CURRENT build — with native
`letterSpacing` support the driver's stale copy lacked entirely. Two pretext
copies drifting independently is exactly the "no parallel implementations"
antipattern AGENTS.md's elegance bar exists to prevent.

* Design: line-aware FLIP reflow

Two DISTINCT, purpose-matched transitions, chosen automatically per change:

1. **REFLOW** (a persisting word's LINE POSITION changed, e.g. 1→2 lines): the
   word GLIDES via a real 2D WAAPI `transform: translate` from its old
   (line, x, y) to its new (line, x, y) — lean, bounded duration, NOT
   staggered per-character (a relocating word is a single visual unit
   moving, not new content appearing).
2. **CONTENT CHANGE** (a word's TEXT itself changed): the proven
   per-character split-flap — old graphemes exit, new graphemes enter,
   staggered — unchanged from the original, validated architecture.

Both driven by REAL line layout computed BEFORE any DOM mutation, via the
SHARED `stdlib/text` vendored `pretext` engine (`pretext.layoutWithLines`,
`pretext.prepareWithSegments` with native `{ letterSpacing }` option) — the
"will this wrap to two lines" question is ANSWERED via `oldLayout`/
`newLayout` computed from the actual `oldText`/`newText` strings against the
real `clientWidth`, not inferred after the fact from box-level side effects.

* What was deleted (net complexity reduction)

- ~700 lines of stale, private, inlined pretext bundle (`__Pretext = (() =>
  {...})()`) — replaced by referencing the shared `pretext` global.
- The `ST.text` measurement-wrapper namespace (`measureWord`,
  `measureNaturalWidth`, the `letterSpacingCorrection` arithmetic hack from
  BUG-176) — replaced by direct `pretext.prepareWithSegments(text, font, {
  letterSpacing })` calls using pretext's OWN native letter-spacing support.
- `containerWidth = elIsBlockLevel ? offsetWidth : Infinity` (BUG-172's
  fix) → still present in SHAPE (block-level classification retained) but
  now feeds a REAL line-layout question (`layoutLines`) instead of a
  single Infinity-width call — `clientWidth` used instead of `offsetWidth`
  for accuracy (see bugs found below).

* What was added

- `layoutLines(text, font, maxWidth, lineHeight, letterSpacingPx)` — real
  per-line `{text, width}` breakdown via `pretext.layoutWithLines`.
- `measureNatural(text, font, letterSpacingPx)` — natural width via
  `pretext.prepareWithSegments` + `pretext.measureNaturalWidth`, letter-
  spacing-correct natively.
- `positionWords(lines, font, lineHeight, letterSpacingPx)` — per-word
  (line, x, y) coordinates within a laid-out multi-line block, via prefix-
  width re-measurement against the SAME pretext pipeline the line layout
  used (pixel-exact match).
- `diffWordSequence(oldWords, newWords)` — classic O(n·m) LCS word-sequence
  diff, tagging each word `keep` (persists, may have relocated), `remove`
  (split-flap exit), or `add` (split-flap enter).
- A branch in `animateChange`: `if (oldLayout.lineCount <= 1 &&
  newLayout.lineCount <= 1)` → proven single-line fast path (unchanged
  logic); else → new multi-line reflow path.
- Lead/trail trimming of maximal UNMOVED-`keep` runs to plain text nodes
  (mirrors the single-line path's prefix/suffix optimization) — a paragraph
  whose first two lines never change pays zero span/animation cost for them.

* stdlib/macros/timeline.st wiring

`@value-change`'s macro definition now `@import "stdlib/text"` (previously
ONLY reachable via the always-loaded base `stdlib` dirs, never pulling in
the opt-in `stdlib/text` module) — so any site using `@value-change`
transitively gets the shared `pretext` global registered, with ZERO action
needed from site authors, while the demand-emit rail still gates actual
bytes shipped (a page never using `@value-change`/`@measure`/`@balance`/
`@fit` still ships zero pretext bytes).

* Bugs discovered and fixed during implementation (all verified live)

** Import resolver: bare "stdlib" import had no cwd fallback

`src/lsp/workspace/import_resolver.rs`'s bare `"stdlib"` aggregate-import
branch only checked the configured `stdlib_path` (workspace-root derived);
on failure it dropped to the embedded-stdlib dead end
(`ResolvedImport::Stdlib`, which `resolve_imports` NEVER recurses into —
`Stdlib { .. } => continue`). `resolve_stdlib` (the `stdlib/X` module-path
branch) already had a `<cwd>/stdlib` fallback for exactly this reason
(`workspace_root` is frequently a SITE directory, e.g. `spacetime serve
projects/<name>/`), but the bare-aggregate branch didn't mirror it. Result:
`stdlib/macros/timeline.st`'s own `@import "stdlib/text"` line silently
never got followed when `stdlib` was reached via bare `@import "stdlib"`
under `spacetime serve <site-dir>` — even though the EXACT SAME import
string resolved fine from a file that imported `stdlib/text` directly (as
ora-ventures.com always did, masking the gap all session). Fixed:
mirrored `resolve_stdlib`'s cwd-fallback into the bare-`"stdlib"` branch.
Regression test: `test_bare_stdlib_import_falls_back_to_cwd`
(`src/lsp/workspace/import_resolver.rs`).

** %emit js braceless-if statement-boundary mangling (BUG-177, filed separately, NOT fixed this session)

The lightweight (non-full-AST) JS statement parser in `src/emit/js_parser.rs`
silently produced INVALID JS (zero compiler diagnostics) when a braceless
`if (cond) stmt;` appeared inside a sufficiently complex surrounding scope
(a `for` loop with nested object-literal `.push({...})` calls). Root cause
not fully isolated (deprioritized to ship the rewrite); worked around by
bracing every `if` statement in the new driver code (`if (cond) { stmt; }`)
— semantically identical, zero cost, always safe. Filed as BUG-177 for a
dedicated debugging session — this is a genuine compiler robustness gap
with broad blast radius (any stdlib primitive's `%emit js` body could hit
the same shape).

** MutationObserver read-after-mutation timing (new architecture's own bug, not pre-existing)

`animateChange` runs FROM a `MutationObserver` callback, which by
definition only fires AFTER the DOM mutation (textContent -> newText) has
ALREADY happened. The rewrite's initial version read `currentHeight =
%&el.offsetHeight` / `currentWidth = %&el.offsetWidth` live at that point —
silently measuring the NEW text's box while the code intended to read the
OLD (pre-change) box. Reproduced live: a 2-line→1-line transition SNAPPED
instantly to the 1-line height instead of easing down from the 2-line
height. The ORIGINAL (pre-rewrite) driver had this exact same
read-after-mutation pattern but never surfaced it — its flap was ALWAYS
single-line, and a single line's height never changes with CONTENT (only
line COUNT changes height), so reading "too late" never returned a
different value; this rewrite's reflow path is the first code path to
genuinely need accurate PRE-mutation box geometry. Fixed: derive
`currentHeight`/`currentWidth` from `oldLayout`/`measureNatural(oldText,
...)` (pure functions of the `oldText` STRING, immune to DOM timing),
falling back to a live DOM read only for degenerate (0-height) layouts.
Regression test:
`test_value_change_driver_measures_old_geometry_from_computed_layout_not_live_dom`.

** Reflow-path stagger scaled with character count, not word count

Initial reflow-path implementation reused the single-line path's flat
per-character stagger array across ALL changed words combined — for a large
content change (many words differing at once), `totalAnimDur` scaled with
total changed CHARACTERS (a 66-character, 15-word sentence rewrite took
2.5+ seconds to settle) instead of the intended "lean, bounded duration."
Fixed: stagger each changed word's own characters relative to a per-WORD
delay offset (`changedWordIndex * stagger`, incremented once per add/remove
op, NOT per character) — total duration now scales with WORD count, a much
smaller and more meaningful bound. Regression test:
`test_value_change_driver_bounds_reflow_stagger_by_word_count_not_character_count`.

** Reflow-path add/remove words missing layer-level opacity fade

Initial implementation gave reflow-path added/removed words the
per-character CSS `@keyframes` transform animation but NO layer-level WAAPI
opacity fade (the single-line path always paired both — `kfToCss` only ever
emits `transform` to CSS keyframes; opacity is ALWAYS a separate WAAPI
layer animation per that function's own comment). Fixed: added matching
`enterLayer.animate([opacity...])` / `exitLayer.animate([opacity...])`
calls to the reflow path's add/remove branches, using the author's
`enterKf`/`exitKf` opacity values exactly as the single-line path does.
