* Context

User-visible symptom (verbatim from dev server log):

#+begin_example
[sync] Received EditAst for _work.st
[sync] EditAst for _work.st: rejected — File not found: _work.st
#+end_example

The user's hypothesis is correct: =EditAst= breaks for =.st= files in subfolders. The =_work.st= source actually lives at =projects/<name>/modules/_work.st=, but the dev panel sends just the basename because that's what the compiler stamped into the =data-st-origin= attribute.

** Root cause (single line)

=src/syntax/form_match.rs::inject_provenance_into_matches:1401= calls =extract_filename(source_file_raw)=, which discards the directory component. The dev panel forwards that flattened value as =EditAst.file=, and =src/sync/handlers.rs::validate_file_path:124= cannot resolve a basename when the file is in a subdirectory.

** Why this is a one-line semantic change with three-line surface area

The compiler already has =workspace_root: &Path= available at the call site (=src/compiler.rs::Compiler::from_file:270=). The pipeline just doesn't thread it through =inject_provenance_into_matches=. The HTML provenance pass (=inject_content_provenance=) already takes a relative path from its callers (=src/server.rs:607,712,844,1071,1187=) and works correctly for subfolder HTML files. We are bringing the =.st= flow in line.

** Why not "fix on the server"

- Searching =site_dir= for any file matching =_work.st= is ambiguous (two repos already have =projects/unkn/modules/_work.st= AND =projects/undefine.org/modules/_work.st=).
- The dev-panel JS in =stdlib/__dev__= cannot reconstruct a relative path either; it only sees =data-st-origin=.
- Compile-time emission is the single source of truth.

Only one flow needs to change.
