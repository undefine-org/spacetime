** The acceptance contract

The deliverable of this plan is NOT "the SIPs are implemented". It is:

#+begin_quote
=docs/specs/SIP-001-LAUNCH-ARTICLE.st.md= compiles, serves, animates, and every
factual claim in its prose is true — verified by a test that fails if the claim
stops being true.
#+end_quote

The article is the spec's acceptance test. It is a *literate* document, so its
fences ARE a program: if the syntax in the article does not compile, the article
does not build. That is deliberate — it makes the promise unfakeable.

Two consequences that govern every wave below:

1. *No wave is done because code exists.* A wave is done when the article
   section it serves compiles and its claim-test passes.
2. *Prose claims are gated too.* "Nine directives became one", "existing
   projects keep compiling", "no silent difference between preview and ship" are
   testable statements, and each has a gate below. A prose claim with no gate is
   a lie waiting to happen.

*** W1.3 =DASHED_IDENT= token kind
    Labelling change, not a lexing change — the =RawToken::Minus= ladder already
    merges =--x= into one IDENT. This stops the parser re-deriving it with
    =text.starts_with("--")=, which =src/syntax/ARCHITECTURE.md= forbids.
    *Gate*: =-42=, =-45deg=, =-webkit-box=, =--custom-prop=, =-- foo= all keep
    their current token shapes (regression test on the ladder).

*** W1.4 Retire =~= (PRESET_REF) — prefix path ONLY

** Recommended next step

Rule on **BUG-245** before any further implementation. It is not a bug in the
ordinary sense — it is the discovery that =@form='s defining mechanism ("kind
inferred from body, no kind keyword") has no implementation on the current
matcher. Every later wave splices forms, so building W3/W4 on an unresolved
kind-selection rule means building on sand.

The two fixes differ in kind, which is why this is the user's call and not mine:
- **Tighten the capture types** so =properties= and =keyframes= genuinely reject
  each other's input. Preserves the design exactly. Cost: both types are used by
  existing constructs, so the blast radius must be measured first.
- **Add an explicit kind marker.** Cheap and unambiguous, but SIP-001c
  specifically claims no kind keyword is needed — so adopting it amends the
  design rather than implementing it.

BUG-241 (one parser dispatch arm) can proceed in parallel either way; it is
independent of how kind selection is resolved.
