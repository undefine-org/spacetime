* ───────────────────────── VEIN 3 — id(T) relations ─────────────────────────
(Presented first; the id(T) decision ripples through Veins 2 and all of Stage 3.)
Decision: a relation is a REFERENCE typed =id(Agent)= (single) / =id(WorkCard)[]=
(multi), stored as a bare id string / array of id strings (matches unkn's id/slug
convention). A bare =Agent= would NEST a full object (denormalized); =id(Agent)= keeps
Agent a first-class collection and the field a pointer.
Type-system work (full detail in FUP-028):
- new TypeExpr::Apply{ctor,args} (general primitive) parsing id(Agent), id(WorkCard)[].
- JSON-schema: id(Agent) → {"type":"string","x-st-ref":"Agent"} — the signal the admin
  reads to render a relation PICKER.
- warn-level referential validation (dangling ref warns, not errors).
Admin surface (mockup stage2-relations-graph.png): single → chip+picker; multi →
multi-chip; a List|Graph toggle; the GRAPH VIEW falls out for free (nodes=entries,
edges=id(T) fields). HIDDEN OPPORTUNITY: =@computed { where: … }= already exists →
surface it as structured SAVED VIEWS ("Talents in Fashion") with no GROQ.
Challenges: referential integrity on delete (warn-on-delete); rename cascade (FUP-033);
backlinks (DERIVE, don't store).
FUP: FUP-028 (id(T) relations), FUP-033 (id rename cascade).

* ──────────── VEIN 2 — rich text = constrained Spacetime AST (REFRAMED) ────────────
THE REFRAME (user, 2026-06-03): rich text is NOT a bespoke html5ever document with
invented "traits" + a new wire schema + a new sanitizer. It IS a Spacetime AST subtree
constrained by an allowlist/denylist of node kinds. Proof: Spacetime already parses HTML
into HtmlExpr (src/html/treesink.rs:1, src/ir/code.rs:299); the "traits" (a @scroll on a
quote, a $binding on an img) ARE just AST nodes; EditAst already round-trips the AST (3C).
∴ ONE allow/denylist replaces THREE would-be subsystems (document schema, sanitizer,
object-union types). This is simpler AND more Spacetime-native (AGENTS.md: don't write a
Rust HTML parser/fallback; the metasystem is self-describing; the list IS the policy).
The policy (full detail in FUP-029):
  ALLOW structure: h1/h2/h3, p, ul/ol/li, blockquote, img, a, figure/figcaption
  ALLOW inline:    strong, em, code, br  (the hard 20% — native AST, free)
  ALLOW Spacetime: AttrPart::Hole ($.field); curated motion on blocks (@scroll/@reveal)
  DENY:            %primitive, %emit js, %macro, <script>/<style>/<iframe>, on* attrs,
                   javascript: URLs, form controls
Enforcement: editor OFFERS allowlisted kinds; SERVER VALIDATES incoming EditAst body
(security-bearing); TreeSink already rejects %-directives. A field typed =richtext=
drives the admin to render the block editor (mockup stage2-richtext-blocks.jpg).
Dividends preserved: native inline marks; ANIMATABLE PROSE (a Quote can @reveal — no CMS
has animated structured content); $data bindings in prose; provenance addresses every
node; the block-type menu IS the allowlist (extensible by declaring a type/template, not
by editing the editor).
Open: inline vs sidecar storage; distinct =richtext= TypeExpr vs Reference.
FUP: FUP-029 (supersedes the earlier richtext-schema + sanitizer ideas).

* ──────────── VEIN 1 — page-builder-as-typed-composition (Framer core) ────────────
THE UNLOCK: a Spacetime page is ALREADY an ordered list of template invocations (unkn's
index.st composes the homepage as =.site-header { &unkn-nav() } …=), and the template
registry ALREADY stores each template's typed interface (params: param_list). ∴ the
compiler already knows, for every section, what DATA it consumes (binding params) and
what SLOTS it offers (element params). The builder VISUALIZES the component model that
already exists — it does not invent one.
TYPED COMPOSITION = structurally-valid pages BY CONSTRUCTION: a section is placeable iff
its bindings are satisfiable; a slot accepts a child iff the child is valid. Framer has
no type system under the canvas; this is a category it cannot reach.
The palette WRITES ITSELF: it is registry.templates() rendered with signatures. Add a
@template → it appears in the palette (mockup stage3-page-builder.png left rail).
"Whole Spacetime surface" (3A) mapping (every action emits/edits via EditAst, 3C):
  add/reorder section → insert/reorder &template() in page .st
  bind to data        → set @each(source) or a $binding
  fill a slot         → drop child into &slot
  edit text in section→ in-context content edit (dev-editable + EditAst)
  edit motion         → tune @scroll/@reveal params (slider) — UNIQUE; motion is a
                        DECLARATION the tool reads & writes (the single most
                        differentiated feature; Framer's motion is opaque runtime config)
  restyle via tokens  → pick a @theme token (FUP-031)
  new component       → "extract component": promote a selection to a @template (FUP-032)
World-class UX principles: direct manipulation on the REAL rendered page (requires
compile-time hydration, FUP-030); selection reveals the TYPED inspector
(DATA/PARAMS/SLOTS/MOTION/STYLE); guided insertion (drop-zones only where valid);
two-way with code (a "View .st" toggle — designer & developer see ONE artifact; output
is hand-quality, git-diffable .st, never Framer's opaque React).
Brand/theme (3B): a first-class =@theme= typed-token construct, "as nice as @type",
editable as just another generated form; brand integrity is STRUCTURAL (you edit tokens,
can't smear rust where scarlet belongs — unkn AGENTS.md). FUP-031.
Challenges: extract-component is generalization (anti-unification), hard + high-leverage
(FUP-032); static-vs-dynamic section (bind-to-data step); canvas fidelity NEEDS
compile-time hydration (FUP-030).
FUP: FUP-030 (hydration), FUP-031 (@theme), FUP-032 (extract-component).
