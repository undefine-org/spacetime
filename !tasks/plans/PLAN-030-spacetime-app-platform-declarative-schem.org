* Root cause (single keystone)
=parse_component_body()= (=src/syntax/events/form_compiler.rs:1701=) segments template
bodies with LINE-ORIENTED first-token heuristics instead of the brace/tag-aware
tokenizer used elsewhere. Once a state decl is seen, subsequent HTML is mis-segmented
and lost; multiline desyncs =html_tag_depth=; unrecognized constructs fall through into
the HTML string. This one parser is why the component model "exists" on paper but
collapses on any real component — and thus why the admin is still hand-written JS.
Tracked as [[id:BUG-059-parse-component-body-drops-html-after-st]].

* =========================================================================
* EXECUTION MODEL — main-thread orchestration + swarm review between waves
* =========================================================================
The architectural/keystone work is done ON THE MAIN THREAD (this orchestrator), because
it is deep, cross-cutting, and not safely parallelizable. Implementation waves alternate
with REVIEW waves. Unlimited time budget — correctness and taste over speed.

** Roles
- *Main thread (orchestrator)*: owns the keystone (BUG-059) and every architectural
  decision; writes the load-bearing parser/codegen changes; runs the global gates;
  drives the cutover. Does NOT hand the architecture to subagents.
- *Reviewer swarm*: between each implementation wave (I-wave) and before the next, a set
  of PARALLEL reviewer subagents (agent type =reviewer=) audit the wave's diff.

** The alternating cadence (MANDATORY between every pair of I-waves)
For each wave N:
1. *I-wave N*: main thread implements wave N's FEAT/BUG to its acceptance criteria,
   asserting EMITTED JS (never check-only). Commit.
2. *R-wave N* (swarm): dispatch parallel reviewer subagents over the wave-N diff. Each
   reviewer has a distinct lens (below). Reviewers may FILE new BUG/FEAT items
   (bugs/, features/) AND propose fixes. Unlimited budget — review until the diff is
   clean, not until a timer.
3. *Triage + mid-flight fix*: main thread reads all reviewer findings, files/links any
   new BUG/FEAT under PLAN-030, and FIXES them mid-flight (inline if small; as a linked
   BUG resolved before the next wave if larger). No wave N+1 starts until R-wave N's
   findings are resolved or explicitly deferred with a linked item.
4. Re-run global gates. Commit. Proceed to I-wave N+1.

** Reviewer lenses (dispatch in parallel each R-wave; scope each to ≤3-5 files of the diff)
- *codegen-truth*: does the EMITTED JS actually implement the construct? Re-build the
  wave's fixtures, read dist/spacetime.js, reject any swallowed-into-html no-ops.
- *parser-edge*: feed adversarial bodies (R1-R3 + the BUG-059 edge-case list) and confirm
  segmentation holds; hunt new desync/swallow regressions.
- *test-rigor*: are tests asserting emitted JS + DOM behavior, or just check/compile?
  Flag every check-only green. Confirm negative gates (deliberately-false test FAILS).
- *DRY/architecture*: duplication, leaky abstractions, parallel implementations; does the
  change reduce cognitive load and compose with existing constructs (AGENTS.md).
- *cutover-completeness*: for deletion waves (e.g. @bind kill), confirm ZERO residue via
  repo grep invariants; no dead macros, no stragglers.
- *regression*: full insta/snapshot audit — every diff is intended reactive-arc/emit,
  no stale or accidental snapshot churn.

** Reviewer output contract
Each reviewer returns findings as {file, line, severity, what, why, fix, effort}. Main
thread converts each actionable finding into a bugs/BUG-NNN or features/FEAT-NNN linked
to PLAN-030 and to the originating wave, then resolves it before advancing.
