* Goal
Build V1 of the Spacetime CMS: a LOCAL, ZERO-CONFIG content admin that AUTO-DERIVES its
entire UI from the project's =@type=/=@data= definitions, served on a SEPARATE
full-window route =/__spacetime/admin/=, distinct from the =__dev__= debug overlay,
sharing the existing WebSocket edit protocol. First real target: managing the =unkn=
talent-agency JSONs (Talents, Services, Work, Reasons, Stats, Strip Rows).

THE THESIS (why this beats any general CMS): no CMS config, no schema registration.
Adding a field to a =@type= IS adding it to the admin. The admin is itself a Spacetime
site (primitives + metasystem, NO custom JS). It caters to exactly ONE system —
Spacetime — which is its entire advantage. A general headless CMS must keep its content
layer and presentation layer as different substances that drift; in Spacetime, =@type=
(schema) + =@template=/=@each= (presentation) + =@on=/=@scroll= (behavior) are ONE source
span, so the admin's schema cannot drift from the site.

* The polarities this CMS manages (refresher — why admin/user decoupling matters)
Content splits into two correlated columns, two products over one substrate:
- STATIC / DESIGNER / IN-FILE / PAGE  ← "design surface" (the user-front = the website)
- DYNAMIC / WRITER / JSON / ENTRY     ← "content surface" (the admin-front = V1)
V1 builds the content-surface column. Admin-front (compile-time-only, itself a Spacetime
site, schema→forms, writes data/*.json) is decoupled from user-front (the site). One
substrate (compiler + .st + data/), two emitters. This is NOT "headless" (API-out); it
is COUPLED in-context editing, which is Storyblok/Tina/Framer's strongest feature and
the thing Spacetime is uniquely built for.

* Auto-derivation rules (the heart of V1)
Collections:
  @data X: T[]  → a collection "X", count = json.length (the left-rail nav item)
  @data Y: T    → a "single" (one entry, e.g. site settings)
Field → form widget:
  string                  → text input
  string (desc/body/bio)  → textarea            (heuristic on field name)
  number                  → number input
  boolean                 → toggle
  "A"|"B"|"C" union       → select
  url + image-ish name    → media field          (reuse dev-media-picker + /upload)
  string[]                → repeatable chip/tag editor
  T (nested object)       → nested fieldset
  T[] (nested array)      → nested repeatable list (RECURSE)
  field named slug        → read-only, derived from the title field
Display inference — CONVENTION, override with =@cms= INSIDE the @type body:
  fallback: title=name|title|label ; subtitle=headline|subtitle|description ;
            thumbnail=image|photo|avatar (url) ; chips=categories|tags
  override:
    @type Talent { @cms { title: name; subtitle: headline; thumbnail: image;
                          chips: categories } id:string; slug:string; … }
unkn (6 types in projects/unkn/index.st:35-85) gets a FULL admin with ZERO .st edits.

CRITICAL: =@cms= MUST be scoped to the @type body; used elsewhere → rich error
(FUP-026). The nesting symbol for @cms is a research question (FUP-027). DO NOT hardcode
a Rust parser for @cms placement (AGENTS.md: the metasystem is self-describing).
