** Latest MCP spec facts relevant to this plan

Latest stable spec at time of planning: =2025-11-25=.

Relevant stable surfaces:
- Server resources: =resources/list=, =resources/read=, =resources/templates/list=, optional =resources/subscribe=, =notifications/resources/updated=.

* Core diagnosis

Current Verse design is pull-only at the MCP protocol layer:

#+begin_example
LiveStore queues events ✓
st_await consumes queued events ✓
MCP resource representing event stream ✗
MCP resource subscription ✗
server notification when new event arrives ✗
Spell auto-read / event-specific injection ✗
#+end_example

Spell already has enough generic MCP resource notification plumbing to make a minimal version work, but Verse does not speak that resource/subscription surface yet, and Spell's current follow-up is generic, not event-aware.

* Architecture decision

Use MCP resources + resource subscriptions as the first-class bridge, not a bespoke Spell-only background =st_await= loop.

Rationale:

1. MCP-native: follows existing =resources/subscribe= + =notifications/resources/updated= semantics.
2. Reuses Spell MCP manager and =mcp://= resolver.
3. Keeps =st_await= as manual/blocking compatibility path.
4. Avoids a second parallel transport for the same events.
5. Future-proofs other Spacetime live surfaces: any live instance can expose history as a resource.

Non-goal for first implementation:
- Do not build a CDP/browser event panel first.
- Do not add a custom Spell polling loop as the primary path.
- Do not change Spacetime website code to custom JS; event emitters remain Spacetime/live-surface mechanisms.

*** Important stdio design issue

Current =signal_sink= runs on the live HTTP server thread, while MCP stdout writer lives in =protocol::serve= main stdio loop.

Do NOT write to stdout from the HTTP thread directly without a single writer discipline.

Need one of these designs:

**** Preferred: notification queue drained by MCP loop

- Add shared notification queue/channel to =McpState= / =LiveServer= bridge.
- =signal_sink= enqueues =ResourceUpdated(uri)= after appending event.
- MCP stdio loop drains queued notifications between incoming requests, writing JSON-RPC notifications to stdout.

Problem: stdio loop blocks on =stdin.lock().lines().next()=, so it will not drain while no new client request arrives.

This is not enough for automatic push.

**** Better W1 design: make protocol loop concurrent with channel select

Refactor =protocol::serve= from blocking =std::io::BufRead= loop to a small two-thread or async-ish structure:

- reader thread reads stdin lines and sends parsed =Value= into =incoming_rx=.
- live server sends outbound notifications into =outbound_rx=.
- main protocol loop owns stdout lock and =recv= selects between:
  - incoming JSON-RPC messages → dispatch response
  - outbound notifications → write notification

Rust std option:

#+begin_src rust
std::sync::mpsc::channel::<Inbound>()
std::sync::mpsc::channel::<Outbound>()
recv_timeout(Duration::from_millis(50))
try_recv outbound in a loop
#+end_src

Invariant:
- stdout single-owner: main protocol loop only.
- stderr remains diagnostics only.
- server-initiated elicitation must continue to work; if =elicit_roundtrip= currently pulls =lines= directly, refactor it to send a server request via stdout owner and await matching inbound response through the same dispatcher. If too large, keep W1 resource notifications isolated and schedule elicitation dispatcher cleanup in W1.5.

Risk:
- Existing =st_elicit= currently depends on direct line pulling inside =protocol.rs=. A full concurrent dispatcher touches this. Plan tests must cover =st_elicit= regression.

**** Acceptable temporary design if avoiding dispatcher refactor

Implement =resources/list/read/subscribe= + =st_events= first, but no actual async notifications. This improves manual/cursor polling but does NOT satisfy automatic surfacing. Mark as W0 only, not done.

*** Behavior

When Spell receives:

#+begin_src json
{
  "method": "notifications/resources/updated",
  "params": { "uri": "spacetime://instances/inst-1/events" }
}
#+end_src

and =mcp.notifications=true=:

1. Debounce per =(serverName, uri)= as today.
2. Detect Spacetime events URI:

   #+begin_src text
   /^spacetime:\/\/instances\/([^/]+)\/events$/
   #+end_src

3. Read resource via =mcpManager.readServerResource(serverName, uri)=.
4. Parse JSON text.
5. Inject only new events since last injected seq for that URI.
6. Store last injected seq in session-local map, not persistent global settings.
7. Follow-up text should be concise and actionable:

   #+begin_example
   [Spacetime event] inst-1 emitted click#7
   payload: {"id":"save"}
   source: mcp://spacetime://instances/inst-1/events
   #+end_example

8. If parse/read fails, fall back to current generic follow-up.

*** State

Add in =sdk.ts= near =notificationDebounceTimers=:

#+end_src

Key:

#+begin_src ts

Cursor semantics:

- Use max seq successfully injected.
- If resource read returns full history, filter =event.seq > lastSeq=.
- If no =seq= fields, fall back to generic notification.
- If many events arrive, cap injected events per follow-up (e.g. 5) and summarize rest.

* Failure modes + mitigations

** Notification emitted before Spell subscribes

Mitigation:
- Resource read returns full history; Spell cursor catches up on next notification/read.
- =st_mount= tells agent resource URI immediately.

** Spell misses notification due process restart

Mitigation:
- MCP state is in-memory today; restart loses events. Accept for live-session W1.
- Future: durable event log if needed.

** High-frequency UI events flood chat

Mitigation:
- W2 cap events per follow-up.
- W4 event inbox/digest.
- Encourage semantic host-directed events, not raw mousemove.

** stdout corruption

Mitigation:
- Single stdout owner in protocol loop.
- All diagnostics remain =eprintln!=.
- Add protocol tests that parse every stdout line as JSON-RPC.

** st_elicit regression during protocol-loop refactor

Mitigation:
- Keep explicit regression test.
- Prefer dispatcher abstraction that supports both server notifications and server requests.

** Generic MCP resource content as prompt injection

Mitigation:
- Spell follow-up labels content as event payload, not instruction.
- No automatic tool execution from payload.

* Open questions

1. Should event history resource return full history forever or bounded latest N?
   - Recommendation: W1 full history; W3 add =after_seq/limit= via =st_events= and/or template URI.

2. Should Spell auto-subscribe to all resources or only Spacetime event resources?
   - Current Spell subscribes to all listed resources when notifications enabled.
   - Recommendation: keep global behavior but auto-read only recognized/low-risk resources.

3. Should =st_await= and Spell auto-read share a cursor?
   - Recommendation: no. =await_cursor= remains tool-specific; Spell has its own injection cursor. Shared cursor would cause one consumer to starve the other.

4. Should this use latest MCP 2025-11-25 tasks?
   - Recommendation: no for event surfacing. Tasks are for durable request execution, not live UI event streams. Resource notifications fit better.
