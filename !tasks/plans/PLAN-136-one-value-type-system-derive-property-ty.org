* The finding that reframes the work

FUP-181 asked: can property->type be derived from the `%scalar_type` table
instead of hand-written? Investigation says yes, the types ARE already declared
(`easing: $easing:easing`) — but deriving them surfaces something larger.

Measured with `capture_type_accepts` (src/syntax/events/mod.rs:123):

  | capture type | 60 | 60ms | #e8eef7 | abc | verdict          |
  |--------------+----+------+---------+-----+------------------|
  | number       | Y  | Y    | Y       | Y   | accepts anything |
  | bool         | Y  | Y    | Y       | Y   | accepts anything |
  | string       | Y  | Y    | Y       | Y   | accepts anything |
  | ident        | Y  | Y    | Y       | Y   | accepts anything |
  | color        | n  | n    | Y       | n   | DISCRIMINATES    |
  | time         | n  | Y    | n       | n   | DISCRIMINATES    |

Every capture type backed by a RUST ENUM ARM accepts everything. Only the ones
backed by a STDLIB GRAMMAR check anything. And:

  344 of 409 typed form params (84%) use a Rust enum arm.

So the type annotations across the stdlib are 84% decoration. `bool` accepting
`abc` is not a CSS-coverage gap — it is the type system not being connected.

* The second finding: the conflicts are not conflicts

16 properties are declared with different types in different forms. Scoped to
the form that owns them:

  same-DIRECTIVE conflicts: 3   (down from 16 global)

And all 3 are deliberate: `@data refresh` is `duration?` in the productive form
and `expr` in a SIBLING form whose only job is to error on the invalid spelling
(comment at stdlib/macros/data-kind.st:352 says so). Same for `@cycle field`
and `@on-mutation target`.

The other 13 are DIFFERENT PROPERTIES SHARING A NAME:
  - `size: $size:number = 1` in @object is scene units (3D)
  - `size: $size:string = "24px"` in @cursor is a CSS length
  - `color: $color:color` in @light is a THREE.js colour; `:string` in @cursor is CSS

∴ the map key is (directive, property), NOT property. A global property->type map
would have forced 13 false reconciliations and broken the 3D macros. This is why
the derivation is the right shape and the hand-written table was not: the table
had no place to put the scope.

* Design

** D1. Key by (directive, property) — derive, never write

`SyntaxRegistry::all_forms()` (src/syntax/registry.rs:247-290) already enumerates
every registered form. `FormParam.name` retains the property label and
`FormCapture.capture_type` its type (src/parser/meta_ast.rs:419-464). The map is
a fold over data that is already in memory. No new file, no new table, no new
`%directive`.

Conflict policy: a same-(directive, property) disagreement is a DIAGNOSTIC, not a
silent winner. It would fire 3 times today; each of the 3 is a legitimate
sibling-form pair, so the check must be scoped to one form clause, not to the
directive's whole form set. Gate must be seen to fail.

** D2. `CaptureType` enum arms are the rot — route the value-ish ones to stdlib

AGENTS: "a closed Rust enum whose arms the runtime doesn't all enforce is rot —
prefer a registry-keyed reference (kinds-as-data)."

`number`, `bool` and `ident` are exactly that. The precedent is already set and
proven: `color`/`length`/`time`/`duration`/`easing` were DELETED from
`parse_capture_type` in PLAN-122 W1.2 and now resolve through `Custom(String)`
against stdlib grammars. The same route, for the same reason.

  W1: add `%capture_type number`, `bool`, `ident` to stdlib/capture-types/,
      delete their arms from parse_capture_type (src/parser/mod.rs:7666-7671).

`string` and `expr` stay Rust: a string is a lexer token, and `expr` is
deliberately permissive (it means "hand this to JS").

** D3. Token references, admitted ONCE, not per-scalar

Blocker: the scalar grammars refuse `--ease-out-expo` and `var(--ink)`, and
`easing: --ease-out-expo` is authored code TODAY (demos/spacetime-docs/index.st:148).
Tighten before admitting and a correct fix produces a red build.

The explore agent recommended one shared `%capture_type token_ref` plus an arm
in each of six leaf scalars, and flagged its own defect: a future scalar does
NOT inherit the arm. That is the drift class this arc exists to delete — the
same shape as the seven hand-synced scalar lists already removed.

Instead: `capture_type_accepts` (and the extractor path) admits a token
reference for any capture type that is a REGISTERED SCALAR, read from
`SyntaxRegistry::scalar_captures()` — the set FEAT-168 already maintains. One
place. A new `%scalar_type` row inherits it for free, which is the same negative
acceptance test FEAT-168 shipped: adding a scalar needs zero Rust edits.

`var()` and `--token` are values of the type whose resolution is deferred, which
is precisely the argument that already makes `var()` a deferral rather than an
error in the declaration validator (src/validation/css.rs). One rule, two places
it was needed.

** D4. Enforce the derived map, and close the two coverage holes

  - FUP-179: `@style`/`@media`/`@supports`/`@keyframes` bodies are `RawCssBlock`
    raw text (src/parser/ast.rs:215), never lowered to `CssDeclaration`, so
    `.a { color: #e8ee1 }` is refused at file scope and SILENT inside a block.
    535 decls / 111 files. Parse the block's source, run the SAME validator,
    offset spans by the block's start.
  - FUP-180: 735 design tokens exempt; 80% probe as a scalar we have a grammar
    for. Needs a declared type (`@tokens Brand { --ink color; }`) — DEFERRED to
    its own wave; it is a new author-facing surface and this plan is already
    large. Filed, not folded in (elegance bar: it fails "no new subsystem").
