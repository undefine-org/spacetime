* Motivation — two anti-patterns the FEAT-092 admin shipped

The CMS admin works, but it leaks two anti-patterns that betray the
"Spacetime expresses everything" mandate:

** AP1 — JS-in-derive (opaque logic escaping the language)
@data derive $assets : ($d.images || []).filter(a => a.path.toLowerCase()...).map(...)
ST.adThemeRows($d) · ST.adGraphLayout($e,$t) · ST.adFormFields(...)
The "shaping seam" is a euphemism: arbitrary JS arrow-fns + ST.* helpers do
the real work. The derive grammar can't express filter/map/group, so we wrote
JS. Every shaping helper is logic the language can't see, optimize, or verify.

** AP2 — name-coupling (the admin hardcodes field names it shouldn't know)
Helpers reach into JSON by literal field names: a.path, t.type, e[titleField],
node.widget, p['x-st-ref']. The descriptors {tpl,name,value,file,token} are a
PARALLEL SHADOW-SCHEMA — a second source of truth the admin invents because
the data arrives as opaque JSON it must reverse-engineer.

Root cause (shared): the admin treats its data as OPAQUE JSON to be reshaped by
JS. It fetches /__spacetime/dev/{site,types,theme,templates,motion}.json — all
SYNTHESIZED FROM the project's .st AST by the server — then throws away the
structure and re-derives it field-by-field in JS.

* The pivot — the data IS the AST; edit it structurally

The dev-ws protocol already has EditAst (src/sync/protocol.rs:48,
src/sync/handlers.rs:437) — patch a .st AST node by `<css-selector> §<directive>`
selector. Today it does text-patch of directive props + __content innerHTML.
EditJson edits JSON data files; EditAst edits the .st SOURCE STRUCTURE.

And the metasystem ALREADY proves "AST-as-native-data": @data registry / @data
dispatch (FEAT-084/089, stdlib/macros/data-kind.st:221-275) expose the
compiler's own registry/AST as a Spacetime data source — the pipeline
(src/compiler.rs::inject_registry_data:791) rewrites the macro to @data inline
with synthesized structured JSON, flowing through the IDENTICAL @each/SSG path.
A %primitive is added → a card appears next build, zero page edits, ZERO JS.

∴ The fix is not "improve the shaping helpers." It is: make the admin's data
SELF-DESCRIBING STRUCTURED SOURCES the way @data registry is, and make EditAst
the structural write path — so filter/group/relabel happen in the DATA SOURCE
definition (compiler-side, typed) and edits mutate AST nodes, not JSON blobs by
string path.

* Vision

** V1 — Structural admin data sources (kills AP2)
New self-describing @data kinds, server-synthesized like @data registry:
  @data schema $types ;            // type schemas as structured rows
  @data collections $cols ;        // the rail's collections, render-ready
  @data tokens $theme ;            // design tokens, ALREADY grouped + typed
  @data components $palette ;      // @template signatures, param-typed
  @data motions $motion ;          // @reveal/@scroll decls, param-typed
Each row arrives PRE-SHAPED with named, typed fields the compiler guarantees —
so @each reads $t.title, $tok.group, $c.params WITHOUT the admin inventing the
shape. The grouping/typing that adThemeRows/adGraphLayout/adFormFields do in JS
moves SERVER-SIDE into the synthesizer (Rust, but DELIVERY not UI — the accepted
boundary, same as build_registry_json). The admin stops knowing field names; it
reads a contract the compiler owns.

** V2 — Structural relations as first-class (kills AP2 for the graph)
@data relations $graph from $activeType ;   // nodes + edges, server-computed
The relation graph's bipartite layout is GEOMETRY (acceptable presentation
glue), but the EDGE DERIVATION (which entry refs which target) is schema
knowledge the server already has (x-st-ref). Expose it as structured rows;
adGraphLayout shrinks to pure x/y math over typed {from,to,label} edges.

** V3 — EditAst for structural content edits (kills AP1 for writes)
Today CRUD = EditJson by string path ("[2].author"). Reframe: an entry edit is
a STRUCTURAL mutation. Extend EditAst (+ a structural ArrayOp twin) so the admin
expresses "set field author of entry 2 to a1" as an AST/node operation the
server validates against the schema — not a blind JSON path write. This also
unlocks editing .st-backed content (not just JSON), and makes the dev-ws ops
symmetric: EditAst for structure, EditJson kept only for raw-value leaves.

** V4 — Derive grammar OR structural sources retire JS-in-derive (kills AP1)
Two complementary routes, pick per case:
  (a) If the data source is structural (V1), the filter/group is ALREADY DONE
      server-side → the derive is a trivial field read, no JS. (Most cases.)
  (b) For genuinely client-side reactive filter (media search box), extend the
      derive grammar to express filter/map declaratively — a @data filtered /
      @each where clause — instead of arrow-fn JS. (Obviates BUG-084 too.)

* What this obviates / connects
- BUG-084 (nested-ternary derive grammar): V4 — structural sources remove the
  ternary; or declarative filter removes the JS.
- BUG-085 (nested @each in template): orthogonal but the typed component rows
  (V1) make the param sub-list a real typed array, easing a proper fix.
- The "shaping seam" disappears as a CATEGORY: adThemeRows/adComponentCards/
  adMotionCards/adGraphLayout/adFormFields all collapse into server synthesizers
  + trivial field-read derives. st.js keeps ONLY: dev-ws transport, optimistic
  revert, control hydration (option lists the DOM can't know) — true glue.

** Q1 addressing — reject (c), take corrected (a). Content stays EditJson.

  content through EditAst. It means: the STRUCTURE the admin reverse-engineers

  server synthesizes (V1); EditAst writes back to those STRUCTURAL .st decls (V3).
  Content VALUES stay EditJson.

** Q2 backing — bulk content STAYS in JSON. .st-content is a category error.
The @data registry precedent works ONLY because the source of truth GENUINELY
IS the compiler's AST/MetaRegistry. Content's source of truth is user data; it
does NOT live in the AST. Putting it in .st INVENTS an AST that doesn't exist —
the same reverse-engineering we're killing. Plus: recompile-per-edit, diff
noise, no pagination, no optimistic CRUD. Structure is .st; content is data;
the admin READS both through one @data interface (V1), WRITES through
domain-appropriate ops.

** Q3 synthesizer boundary — the "different-UI test" (crisp line)
Test each transform: "If I built a COMPLETELY DIFFERENT UI over the same source,
would this transform still be correct and needed?"
  YES → DELIVERY (Rust synthesizer OK — a source-truth projection)
  NO (bakes in THIS UI's template names / ordering / copy) → UI LOGIC (must .st)
Applied:
  - group tokens by type        → DELIVERY (type is intrinsic; like build_registry_json)
  - widget kind from schema      → DELIVERY (already correct: widget_for)
  - flatten nested fields+depth  → DELIVERY (deterministic projection)
  - order color/length/duration  → UI LOGIC → .st (ordering is presentation policy)
  - tpl-name assignment (tpl:'ad-token-color') → UI LOGIC → .st via @match on the
    SEMANTIC kind (drawer.st already proves @match on $f.widget → template)
  - label/copy strings (adToolTitle) → UI LOGIC → .st
RULE: synthesizer emits source-determined SEMANTIC facts (type, widget kind,
group, depth, relation edges); .st owns UI-determined BINDINGS (which template
renders a kind, ordering, copy). Moving the former to Rust kills AP1/AP2; moving
the latter just relocates the opacity. My draft conflated these — FIX.
