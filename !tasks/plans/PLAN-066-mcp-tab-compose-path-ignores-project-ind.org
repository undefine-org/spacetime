## Summary

Opening a project's `.st` entry as an MCP tab (`st_tab_open`) and composing it onto the workbench stage (`mcp_compose` / "Open on stage") silently renders BLANK or near-empty when that entry relies on either:

1. a sibling `index.html` shell that the `.st` file composes INTO via CSS selectors (e.g. `.site-header`, `main`, `footer` defined in `index.html`, populated by `&unkn-nav()` etc targeting those selectors) — the compiled HTML output is then legitimately `0 bytes` because the `.st` file itself declares no root-level markup, all of it lives in `index.html`.
2. `@locale(...)` + build scripts (`projects/*/landing/index.st` pattern) — the real dev server (`server.rs::try_serve_locale`) executes build scripts via a v8 runtime (`build_runtime::execute_build_scripts`) to materialize the locale HTML; the MCP path never does this.

## Root cause

`src/mcp/bundle.rs::compile_function` / `compile_to_bundle` call ONLY `Compiler::from_ast(&ast).compile()` — the raw AST→HTML/CSS/JS compile. They never:
- look for a sibling `index.html` (as `server.rs::try_serve_locale`, `index_handler`, `catch_all_handler` all do via `derive_st_path`/`html_path.exists()` checks and page-shell merge), and
- never execute `@locale` build scripts (`build_runtime::execute_build_scripts`), which the same `server.rs` locale-serve path treats as a first-class case.

This means `src/mcp/live.rs`'s `put_source` / `mount_into_host` / `mount_function` are a SEPARATE, simplified compile pipeline from the real `serve`/`build` pipeline in `server.rs` — they diverge structurally, not just by accident. Confirmed via `st_inspect{fn_id}`: a tab opened from `projects/unkn/index.st` (relies on `index.html` shell) compiles `ok` with `html_len: 0`; composing it onto the workbench stage yields a near-invisible collapsed guest root (`.unkn-stat` template shell leaking through at ~8px height, no header/main/footer). A tab opened from `projects/ora-ventures.com/landing/index.st` (`@locale`) compiles `ok` with `html_len: 0, css_len: 0, js_len: 0` — total blank.

## Fix direction

`compile_function`/`compile_to_bundle` (or a new wrapper used by `put_source`) should, when compiling an ENV-origin (file-backed) entry:
- check for a sibling `index.html` (same `derive_st_path`/existence check `server.rs` uses) and if present, treat the compiled HTML as a fragment to merge into that shell's `body` region (mirroring `render_page_shell` / the existing `index.html` DOM merge in `server.rs`'s handlers), OR at minimum surface this discrepancy to the agent/user via a compile diagnostic ("this entry composes into an index.html shell not present in the MCP compile — result may be incomplete") rather than silently reporting `compile_ok: true, html_len: 0`.
- detect `@locale` in the AST and either execute build scripts (reusing `build_runtime::execute_build_scripts`, same as `server.rs`) or surface a clear diagnostic that MCP compose does not support locale-routed entries yet.

Either way: **`compile_ok: true` + `html_len: 0` for an entry that visibly has a full page of markup on disk is a lie the tool tells the agent** — worth gating explicitly rather than leaving it as a silent footgun.

NOTE [2026-07-06]: ## Additional bug found + fixed during implementation: subdirectory entry import resolution

While live-verifying the MCP-SHELL fix against `projects/ora-ventures.com/landing/index.st` (a subdirectory entry with `@locale` + a relative `@import "../modules/_theme.st"`), discovered `compile_pipeline`'s import resolution ALWAYS used `ws_root.join("<bundle>.st")` as the pseudo main-file path, regardless of the entry's REAL on-disk location. For any subdirectory entry (not at the env root) with a `../`-relative import, this produced a bogus "Import resolution failed" error — reproduced live: `st_tab_open{env:"env-2", entry:"landing/index.st"}` failed to compile entirely (not just the MCP-SHELL/LOCALE warning gap this ticket was originally about).

### Fix
`compile_pipeline` now accepts `entry_path: Option<&Path>` and uses it (when given) as the import-resolution `main_path` instead of the ws_root pseudo-path. `compile_function` (used by `put_source_with_entry`, which `st_tab_open`/`open_tab_action` now call) threads its existing `entry_path` param through. `compile_to_bundle` (used by bundle re-polling / structure introspection, not entry-opening) keeps passing `None` — unchanged behavior there, out of scope for this ticket.
