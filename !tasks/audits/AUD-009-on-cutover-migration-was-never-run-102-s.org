NOTE [2026-08-07]: OPEN QUESTION RESOLVED \u2014 `@on &.loop` IS the correct landing point. No
double-migration risk; the 92-site sweep can proceed on the capsule's own
`%into` target.

`loop` is not a directive being replaced by unrelated surfaces. It is a
registered DRIVER: `%registers driver(loop) { primitive: loop-driver,
value_type: transport, seekable: true, domain: declared, reduced_motion: hold }`
(=stdlib/macros/drivers.st:356=). Two heads consume drivers, and both are
current:

- =@on &.loop(\u2026) { <keyframes> }=  \u2014 one element, one keyframe body. The
  capsule's =%into= target.
- =@score &.loop { <clip entries> }= \u2014 =%form { @score $driver:driver_expr
  $as:score_as_name? { $entries:score_entry+ } }= (=stdlib/macros/score.st:162=).
  An ARRANGEMENT over the same driver: many clips with windows, not one
  keyframe body.

So `@score` did not deprecate `@loop`; the =@on <driver>= cutover did, and
=@score= is the richer head built on the identical driver registry. Migrating
=@loop \u2192 @on &.loop= lands on live vocabulary. A file that wants an arrangement
rather than a single body is then a further, EDITORIAL change (=@on= \u2192 =@score=),
never a mechanical one \u2014 correctly outside a =%rewrite='s remit.

Corroborating evidence that both heads are live and gated in a real browser:
=demos/score-launch/= (=index.st.md=, a literate page) with =--cdp= gates in
=tests/score/{score-launch-film,score-launch,two-pole}.test.st=. Its README
records a bug where "=@score &.loop= inherited =loop-driver='s =pingpong=
default" \u2014 i.e. =@score= reads the same driver defaults the =%rewrite= writes
explicitly (=mode: pingpong=, =phase: 0=), which is exactly why the rewrite
emits them rather than relying on inheritance.

** The mechanism, and why it is NOT "delete the retired macros"

My plan said delete the embedded `%macro` defs. That would have worked and been
worse: the `%rewrite` rules and `%hint` entries live in the same capsules, and
they are what makes `spacetime migrate` able to FIX the code and what makes the
error message teach. Deleting the macros would have turned a good diagnostic
into "unknown directive".

The actual hole was the DEFAULT. An absent `@version` compared as "older than
every wave", so the migration window (W0715) stood open forever for any file
that never declared one — a file written today in syntax retired months ago
compiled silently. A permanent amnesty, not a transition. That is the whole
reason ~100 sites accumulated with nobody noticing.

Inverting the default closes it with everything else intact: capsules keep
their rewrite rules, `migrate` still works, the hint still teaches, and a
project genuinely mid-migration opts INTO the window by declaring the older
`@version` it is migrating FROM — which is exactly what `spacetime migrate`
writes before bumping it forward. The default is derived from the registry
(`newest_migration_wave()`), so a new wave moves it automatically; no date to
keep in sync in Rust.

** Where the policy lives (two attempts)

First attempt defaulted inside `apply_migration_shim_for_wave` and broke all 7
`migrate::tests` — correctly, since they drive SYNTHETIC registries and each
one closed its own window. `None` must keep meaning "no version constraint" for
a caller that means it. So the default is POLICY about real source files and
lives in `migrate::effective_syntax_version`, applied at the two entry points
that compile a real file: `Compiler::from_file` and the `check` command.

That second call site was itself a latent bug: before this, `check`
auto-migrated (W0715) source that `build`/`serve` would refuse. They now agree.
