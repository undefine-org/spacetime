* Symptom
A motion directive whose body nests CHILD SELECTORS:

#+begin_src st
.bd-hero {
    @on visible hero-entrance(900ms, immediate: true) {
        .bd-hero__h1 { opacity: 0 -> 1; translate-y: 44px -> 0; easing: ~bd-smooth; at: 0.1; }
        .bd-hero__sub { opacity: 0 -> 1; ... at: 0.25; }

#+end_src

compiles to an applier IIFE whose animation data is EMPTY: `const anims = [];`. The timeline DRIVER runs (sets the `hero-entrance` progress signal 0→1, reaches 1) but NO applier ever writes styles to the children. Result: children keep CSS defaults (opacity 1, no transform) — animation silently dead. Same for `@scroll NAME(start,end){ .child { ... } }`.

Verified in browser: `[...document.querySelectorAll('[style*=opacity],[style*=transform]')].length === 0` for the backdesk hero; `.bd-hero__h1` has no init flag and no inline style, while `.bd-hero` reports `ST.get(el,'hero-entrance') === 1`.

* Likely root cause (hypothesis)
The codegen for child-nested motion blocks needs to emit a `%scope` (nested-selector scope) so each child selector becomes a populated entry in the applier's `anims.scopes[]` (with `selector` + `properties` + `at`/`stagger`). Currently the nested-child branch produces the applier scaffold (`processScope`, `root.querySelectorAll(selector)`) but `anims` is left `[]`, so `anims.scopes` is undefined and nothing binds. I.e. the parser/lowering recognises the block enough to emit a driver + applier shell, but drops the child property scopes on the floor.

Expected: child-nested `@on visible` / `@scroll` should populate `anims` (root `properties` and/or `scopes[{selector, properties, at, stagger, easing}]`) so the applier's existing `processScope` + `querySelectorAll` path animates the children — with the children inheriting the driver progress signal/var from the scope root.

* ROOT CAUSE (corrected after deeper runtime inspection)
The problem is NOT specific to child-nesting. The animation APPLIER IIFE in the
compiled runtime expects its `anims` to be an OBJECT:
  anims.properties = [{ property, keyframes, easing }, ...]
  anims.scopes     = [{ selector, properties, at, stagger, easing }, ...]
and only then calls `applyInitialState(...)` / `processScope(...)` → `applyStyle()`
→ writes `el.style.opacity` / `el.style.transform`.

But codegen EMITS `anims` as a raw STRING ARRAY:
  const anims = ["opacity: 0 -> 1", "translate-y: 44px -> 0", "easing: ~bd-smooth"];
So `anims.properties` and `anims.scopes` are BOTH `undefined`. The guard
`if (!anims) return;` passes (non-empty array is truthy), every
`if (anims.properties && ...)` / `if (anims.scopes && ...)` is skipped, and
applyStyle is NEVER called. The ONLY thing that runs is the driver-var binding:
  ST.watch(root, "<name>", p => root.style.setProperty('--st-<name>', p));
i.e. the element gets `--st-<name>: <0..1>` published but no real opacity/transform.

Verified identical in unkn (`const anims = ["opacity: 0 -> 1", ...]`) — meaning
unkn's plain `@on visible { opacity: 0->1 }` reveals ALSO don't actually animate;
unkn's visible motion really comes from `@import "stdlib/text"` (.st-reveal-char,
a separate codegen path) and from scrubbed `@scroll` whose `--var` is consumed by
hand-written `calc()` CSS. So the string[]-anims bug is environment-wide, not a
backdesk regression.

** Where to fix
The codegen that builds the applier IIFE (src/emit/* animation lowering): the
parsed keyframe properties must be serialized into the object shape
`{ properties: [...], scopes: [...], staticProperties: [...] }` the runtime
applier already consumes — instead of `JSON`-ing the raw `"prop: a -> b"` strings
into a flat array. The runtime side already has the full machinery
(interpolateKeyframes/applyStyle/processScope); only the emitted `anims` literal
is malformed.

** Reliable workaround (now the project standard)
Treat every `@on visible` / `@scroll` as a PROGRESS-VAR PUBLISHER and consume the
var in CSS:
  .el { @on visible bd-x(700ms, immediate:true) { opacity: 0 -> 1; } }  // publishes --st-bd-x: 0->1
  .el { opacity: var(--st-bd-x, 0); }                                    // CSS consumes it
For scrollytelling:
  .sec { @scroll p(start,end, scrub:true){ --p: 0 -> 1; } }
  .sec .child { opacity: clamp(0, calc((var(--p,0) - 0.2)/0.25), 1); transform: ... }
`@loop` ... `--v: a -> b -> c` + CSS `var(--v)` consumption works the same way.

** Revised acceptance
- Codegen emits `anims` as the object the applier expects; a per-element
  `@on visible { opacity: 0->1; translate-y: 40px->0 }` writes real inline
  opacity/transform (browser shows `[style*=opacity]` count > 0) with NO CSS-var
  consumer needed.
- Child-nested form populates `anims.scopes[]` and animates descendants.
