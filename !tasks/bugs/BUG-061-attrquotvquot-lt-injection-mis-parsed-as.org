* Problem
=parse_injection= (src/syntax/events/form_compiler.rs:2628) classifies an injection TARGET as
Text (`text`), Slot (`[slot="x"]`), else Attr. A general attribute-selector target like
`[class="v"] <- $n` falls into the `else` and becomes
=InjectionTarget::Attr { name: "[class=\"v\"]" }= \u2014 the runtime then does
`element.setAttribute("[class=\"v\"]", value)`, setting a NONSENSE attribute literally named
`[class="v"]` instead of targeting the descendant matching `[class=v]`. Verified: the emitted
payload carries `target: { type: "Attr", name: "[class=\"v\"]" }`.

Root cause: the target grammar conflates "the element's own attribute" (bare ident: `src`,
`href`) with "a descendant matched by an attribute selector" (`[attr="v"]`). Only the
specific `[slot=]` case was special-cased; every other `[...]` selector is garbage.

* Structural fix
Add an `InjectionTarget::Selector { selector }` variant for general `[...]` attribute-selector
targets (the descendant's textContent), parallel to Slot (which is the `[slot=]` ergonomic
special case). Parser: `[...]` containing `slot=` -> Slot; any other `[...]` -> Selector; bare
ident -> Attr. Runtime: Selector -> `element.querySelector(sel).textContent` (reactive via
ST.watch, same as Slot). This is the clean general model; Slot becomes sugar for
`Selector{"[slot=name]"}` semantically but kept for its ergonomic name resolution.

* Acceptance
- [ ] `[class="v"] <- $n` targets the descendant matching `[class=v]`, sets its textContent.
- [ ] no `setAttribute("[...]", ...)` garbage; bare-ident attr injection (`src <- $x`) unchanged.
- [ ] `[slot="x"]` unchanged. Reactive (ST.watch). Unit + V8 tests.
- [ ] NB: Phase B grammar rewrite will express this in the stdlib component-body grammar; this
