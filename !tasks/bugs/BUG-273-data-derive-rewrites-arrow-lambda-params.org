* Symptom
Serving stdlib/comments (the pill) floods the console:

  [derived-signal comOpenCount] SyntaxError: missing ) after formal parameters
  [derived-signal comPruneFiles] SyntaxError: missing ) after formal parameters

Both derives use arrow lambdas with $-prefixed params, e.g. stdlib/comments/__dev__/pill.st:25:

  @data derive $comOpenCount number : $comRecords.filter(($comRecord) => $comRecord.status == "open" || ...).length;

* Root cause
stdlib/primitives/data/derived-signal.st rewrites EVERY $name token in the raw
expr to SpacetimeLocal['name'] for Global-scope evaluation — including the
arrow-lambda's formal parameter. The emitted function becomes:

  SpacetimeLocal['comRecords'].filter((SpacetimeLocal['comRecord']) => ...)

which is an invalid formal-parameter list → SyntaxError at every recompute.
Dep discovery has the same flaw (would watch a nonexistent 'comRecord' signal).

The template never had a lambda-param exemption (present since f46bbb2a); the
pill surface (PLAN-123 W2, Aug 2) is the first derive consumer to use lambdas.

* Fix
In derived-signal.st: pre-scan the expr for arrow params (`($a, $b) =>`,
`$a =>`, `(a) =>`), collect the bound names, and:
  1. skip them in the $sig → SpacetimeLocal[...] rewrite (emit $name verbatim — valid JS identifier)
  2. exclude them from dep discovery (no phantom watcher)

* Verification
V8 behavior test: compile a page with a lambda derive through the real
pipeline, run emitted JS in V8, assert the derived value — not a string gate
(BUG-252 rule: behavior, not source).

Sibling computed-source.st uses the `$.field` row idiom (no $param lambdas) —
not affected.

* Resolution (2026-08-04)
Fixed in stdlib/primitives/data/derived-signal.st: a pre-scan collects
arrow-lambda param names (`($a, $b) =>`, `$a =>`, `(a) =>`) into `lambdaBound`
BEFORE dep discovery; the $sig→SpacetimeLocal rewrite emits bound names
verbatim (`$r` is a valid JS identifier) and dep discovery skips them (no
phantom watcher).
