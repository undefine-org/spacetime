* Verified state (reasoned, not run — needs CDP)
gh-6's `@on &.visible(300ms)` compiles to the `intersection` driver
(stdlib/primitives/intersection.st, registered for driver(visible) in
stdlib/macros/drivers.st) with `once: false` — the emitted JS's observer is
`if (false && entry.isIntersecting) observer.disconnect()`. It publishes
`ST.set(el, "reveal", entry.intersectionRatio)` on EVERY intersection change.

apply-animations' scalar path (emitted from stdlib/primitives/animation/apply-animations.st)
watches that "reveal" driver signal:
```
const owner = el._stAnimOwner[normProp];
const isActive = progress > 0 && progress < 1;
if (owner && owner !== driverSignal && !isActive) return;
if (isActive || !owner) el._stAnimOwner[normProp] = driverSignal;
const value = interpolateKeyframes(prop.keyframes, progress, ...);
applyStyle(el, prop.property, value, driverSignal, scopeId);
```
On first visible (ratio=1, progress=1): owner unset → `!owner` → owner=driverSignal, apply end
value (opacity:1). RETAINED (this is the FIXED gh-6 case).

On LEAVING the viewport (ratio→0, progress=0): isActive=false, owner===driverSignal so the
return guard is false → interpolate at progress=0 → applyStyle START value (opacity:0). The
one-shot reveal REVERTS while off-screen, and re-entering re-reveals (ratio→1 → opacity:1).

∴ Reasoning shows re-entry WOULD revert — a real browser IntersectionObserver firing
ratio=0 on scroll-out drops the end state. This is a re-entry POLICY defect, not fill-mode.

* Fix direction (not implemented)
A one-shot (`@on` keyframe, non-scrub) visible driver should either (a) disconnect after the
first intersecting publish (one-shot semantics — the author asked for a one-time reveal), or
(b) not publish a p=0 that drops a completed animation's owned end state. The intersection
primitive already has `once: bool` support; `&.visible` currently binds once:false. Decide
once-policy per plan; this issue records that re-entry reverts today.

* RESOLVED 2026-08-07 — the premise is DISPROVED

This bug reasoned that a one-shot `@on &.visible` would revert when the element leaves and
re-enters the viewport, because the driver re-fires from p=0. It was filed as reasoning, never
as an observation — the caveat posted on GH-6 said so explicitly ("proving it either way needs a
real browser").

Now proven, in real Chromium:

    /home/user/cdp-target/debug/spacetime test \
      tests/repro/gh-6-hold-end-state/re-entry.cdp.test.st --cdp
    -> 1 passed

The gate scrolls the element fully out of the viewport, back in, and asserts opacity is still 1.
It holds. A one-shot reveal does NOT revert on re-entry.

Why this took two corrections to reach: the gate first appeared to fail, which I attributed to a
fixture-init gap (BUG-325). Both were wrong. The real cause was BUG-328 — every page importing
stdlib emitted a bundle that did not parse, so nothing ran at all. Once that landed, the gate
passed on the first run.

GH-6 can be considered fully closed, including the caveat I attached to it. The reporter was told
to reopen if they saw a curtain flicker on re-scroll; that invitation stands, but the mechanism
described here is not the explanation.
