* The three distinct defects

** 1. `if (area < 0) area = 1 + area` is a REVERSE HACK, not arithmetic

It exists to make `rate -1` produce 1 -> 0. It works only when the total area
is exactly -1. At `rate -2` the area reaches -0.5 at t=.25 (rendered 0.5,
accidentally right) and -1 at t=.5 (rendered 0.0) — the clip plays backwards at
double speed, hits the start halfway through, and sits dead for the rest of its
window with no indication.

The correct formulation: a NEGATIVE rate means the playhead starts at the END
of the clip and walks back. That is `1 + area` applied as an ORIGIN, not as a
correction fired when a value happens to go negative. The origin is a property
of the rate's sign at t=0, decided once, not per-sample.

** 2. A ramp CROSSING ZERO is meaningless under the current form

`rate 1 -> -1` gives 0, .188, .25, .188, 0 — the clip advances to a quarter and
retreats. That may even be desirable (an ease-out-and-return), but nothing says
so and the `1 + area` branch never fires because the integral stays positive.
So a sign-crossing ramp silently means something entirely different from either
endpoint's steady meaning. Either specify it or refuse it.

** 3. Clamping hides a MIS-SPECIFIED score

`rate 10` reaches 1.0 at t=.1 and holds for 90% of its window. `rate 2 -> 0.5`
finishes at t≈.7. Neither is wrong ARITHMETICALLY — a fast clip finishing early
is exactly what `rate 2` means. But there is no way to distinguish "I meant
that" from "I got my numbers wrong", and the clamp makes both look identical
and intentional.

Proposal: rate values are a DOMAIN question like R1's. A rate whose integral
does not reach 1.0 by the window's end (`0.5`) or reaches it before (`10`)
should at minimum be a warning naming the fraction of the window that is dead,
because that is the number the author actually wants to know.

* Why the existing gates pass

`ramp_freeze_and_reverse_are_three_distinct_maps` compares EMITTED CONSTANTS —
`_swRateFrom = -1` differs from `= 2`, so it is green regardless of what the
map computes. `the_rate_map_evaluates_correctly_over_its_window` evaluates the
map but only over the values in the table's top half, which are all correct.

The lesson from W4 repeats exactly: a gate that asserts something was PRODUCED
cannot see wrong arithmetic. Only sampling the map catches it.

* Fix sketch

1. Decide the sign rule: negative rate = reversed origin, decided at t=0.
2. Decide sign-crossing ramps: specify or refuse (refusing is defensible —
   `rate 1 -> -1` has no obvious single meaning).
3. Rebuild the map from that decision rather than patching the branch.
4. Gate by SAMPLING, with the full table above as the fixture, negatives
   included. The drift guard (`the_transcribed_rate_map_matches_the_primitive`)
   already exists and should be extended, not replaced.

* Fixed

Implemented BUG-259 as one window-map rule: a negative initial rate selects
origin 1 once, then the same rate integral runs backward. The old per-sample
`1 + area` correction is gone, so `rate -2` samples as `1, .5, 0, 0, 0`.

`rate 1 -> -1` is now refused as E0954 with a two-clips hint; it cannot emit an
arbitrary map. W0718 warns when a nonzero same-signed integral finishes early
or never reaches the endpoint. The warning reports the unused fraction and an
adjusted `for` duration; `rate 10` in `for 2s` suggests `for 200ms`. `rate 0`
remains an intentional freeze and `rate 1` remains quiet.
