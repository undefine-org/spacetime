* Symptom
`@data signal $cursor(x number, y number) to $board { send emit "cursor" { x: $x, y: $y } … }`
— params spelled BARE (`x number`, not `$x number`) — compiles CLEAN (cargo
check green) but the emitted `callParams` table is `[]`. At runtime the
buildBody template eval (`return ({x: $x, y: $y})`) throws ReferenceError ($x
unbound), the catch silently falls back to RAW ARGS, and the wire receives
`[arg1, arg2]` instead of the declared object — or `{}` when the args are
undefined. move_card/add_card/lock_card on the board only worked BY ACCIDENT:
their call sites pass a single object literal, which the bodyless-passthrough
fallback returns untouched.

The canonical spelling (`$x number`, per AGENTS.md one-sigil harmony: `$price
number`, never `name: type`) compiles a correct table — stdlib/__host__'s
$createProject($name string) is the working reference.

* Expected
Bare-ident params in a signal signature are a COMPILE ERROR (E-diagnostic
naming the param and the `$`-prefixed spelling) — never a silent empty table.
The silent-fallback class is exactly what the repo's diagnostics discipline
forbids.

* Reproduction
1. Declare `@data signal $f(x number) to $h { send emit "e" { x: $x } receive … }`.
2. cargo check → green (wrong). Build → `var callParams = [] || [];` (wrong).
3. Fire → server receives raw args, not {x: …}.

* Workaround (shipped in board.st)
Spell params `$`-prefixed: `$cursor($x number, $y number)`.

* Suspected layer
param_list capture → signal-call %params marshalling: bare-ident entries are
dropped instead of diagnosed.
