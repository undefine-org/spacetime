* Symptom
An `@data inline` (or `@data fold`) whose value is an array of OBJECT LITERALS fails to
parse:
  @data inline $todos : [{"title": "Alpha"}, {"title": "Beta"}];
  -> × expected scope block, directive, or declaration (multiple, at each `{`)

Scalar arrays parse fine: `@data inline $items : ["Alpha", "Beta"];` ✓

* Root cause
The directive grammar (CST parser parse_directive / inline value handling) treats `{` as
the start of a directive BODY block, not as part of an inline expression value. An object
literal `{ "title": ... }` inside the `: value` position is misread as the directive's
body, breaking the parse. Same family as the leading-paren ambiguity hit in W3 fold
(`($src, acc, item)` split into ARG_LIST) and the greedy-value boundary (W3 required `;`).

* Impact
Medium. Realistic @each-over-objects demos (todo lists, product cards) want inline object
arrays. Workarounds today: (a) @data fetch from a JSON file/URL, (b) scalar arrays +
derive, (c) runtime-populated signals. The HTML-bodied @each (W4) renders object fields
correctly via `$.field` once the data arrives through any of those channels — only the
INLINE object-literal authoring path is blocked.

* Fix direction
The inline value after `:` in a value-bearing directive should parse as a full expression
(balanced over `{}`/`[]`/`()` + strings) up to the `;` terminator, NOT stop at the first
`{`. The W3 `balanced(';')` terminal already does depth-aware brace/bracket/paren tracking
via source byte-scan (src/syntax/events/extractors/custom.rs) — the @data value capture
could adopt it (the kind macros currently use `$value:expr`). Care: must not regress the
body-block forms (legacy `@data $n:type { … }`). Likely: only treat `{` as a body when the
value position is NOT already inside a balanced expression.

* Acceptance
- `@data inline $todos : [{"title":"A"},{"title":"B"}];` parses + compiles.
- @each over it renders object fields (`<li>\`$t.title\`</li>`), live-verified.
- Scalar arrays + body-block @data forms unaffected. Full gate green.
