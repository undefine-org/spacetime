* Problem
The admin's rich-text widget does not render an editor. In the entry drawer, the
`&fld-richtext` field shows the LITERAL TEXT:
  @editable(bind: , marks: ["bold","italic","link"], blocks: ["p","h2","blockquote"]);
instead of a mounted block editor. No contenteditable, bind: is EMPTY, no ST.Editable
surface for that field. Every other widget (text, textarea, number, toggle, select, media,
chips, relation, color) renders correctly — only richtext is broken.

* Repro
- projects/cms-testbed/index.st with a `body: richtext` field on @type Post (added this turn).
- cargo run -- serve projects/cms-testbed/ -p 4456 --debug
- /__spacetime/admin/ → posts → open "First Light" → the drawer's `body` field shows the
  raw @editable(...) directive as text.
- Confirmed in the compiled admin runtime: `@editable(bind` appears as a LITERAL STRING (2×),
  not a compiled editable-surface invocation.

* Root cause (located, not yet fixed)
`@editable` is a SELECTOR-SCOPE macro. Inside `@template &fld-richtext($f) { … @editable(bind:
`$f.value`…); }`, the template body's nested directive is NOT expanded by the macro pipeline
— the template captures its body as HTML/text and emits @editable verbatim. So a nested macro
inside a @template body never runs. (drawer.st:36-43; admin runtime shows the literal.)

This is the admin analogue of the on-page richtext we DID get working (W1) — on a normal page
`@richtext`/`@editable` is a top-level selector macro and compiles fine; inside a @template
body it does not. The drawer is the ONLY place richtext is mounted via a template, which is
why it slipped.

* Why it matters
This is THE blocker for "rich text editing in the admin" (the user's explicit ask). The
whole CMS rich-text story (edit a Post.body block document in the admin drawer) is currently
non-functional. P1.

* Fix direction (needs design — parser/pipeline, real blast radius)
@template bodies must EXPAND nested selector-scope macros (at least @editable, ideally any),
binding their hole args (`$f.value`) per-instantiation. Options:
  (a) make the template-body compiler recurse into nested macro invocations (general; the
      right fix, but touches how template bodies are parsed/expanded — pipeline/expand.rs,
      pipeline/mod.rs template-body capture);
  (b) a narrower richtext path: the drawer mounts the editable surface imperatively from JS
      (admin runtime) keyed on [data-widget="richtext"], reading the bound value — bypasses
      the template-nesting gap but adds an admin-specific mount (less harmonious).
Prefer (a) if the blast radius is containable; (b) is the pragmatic unblock.
