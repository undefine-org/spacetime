* Symptom
A `@data derive` value that STARTS with `(` AND has a TRAILING method call —
`@data derive $shown : ($x || []).filter(...).slice(0, 5)` — captured only
`($x || []).filter`, dropping everything from the first trailing call-args
onward. The emitted derived-signal exprText truncated at the method name, so
the derive evaluated wrong / threw at runtime. Surfaced building the FEAT-092
media library's `$assets` derive (the search-filter pipeline).

* Root cause — the OTHER parser
BUG-077 fixed the CST parser (src/syntax/cst/parser.rs `last_was_value_colon`
guard). But the **events grammar** (src/syntax/events/grammar/directives.rs)
is a SEPARATE parser, and it drives the actual FormMatch capture/emission. It
lacked the twin guard: a value-colon followed by `(` opened an ARG_LIST
structural node for the leading `(...)`, then `.slice` parsed as trailing
inline_args, and the final `(0, 5)` was orphaned. The balanced(';') extractor
byte-scans only the directive's flat inline-token slice (ARG_LIST tokens are
structural, excluded), so the scan ended at the last inline token (`.slice`).

The `.length` case BUG-077 originally tested has NO trailing call, so it never
exposed this — the truncation only bites when a method call FOLLOWS the
paren-led head.

* Fix (structural, mirrors the CST guard)
- inline_args() now RETURNS whether the last arg was a standalone
  value-introducing COLON (parsed as its own ARG so a following token resets
  the flag — preserves preset `~x: cubic-bezier(…)` routing).
- directive_with_source(): when value_colon && at `(`, consume the whole
  paren-led value via new inline_value_expr() (balanced run to depth-0
  `;`/`{`/`}`) as ONE value ARG, instead of arg_list().
- The trailing call-args now stay in the directive's inline tokens, so the
  balanced(';') scan captures the WHOLE expression.

* Tests (RED→GREEN)

  asserts the emit contains `.filter(x => x > 0).slice(0, 5)`.
