* Symptom

Importing a stdlib SUBMODULE without also importing `stdlib` fails:

#+begin_src spacetime
@import "stdlib/3d";
body { margin: 0; }
canvas.hero { @stage(camZ: 5) {} }
#+end_src

  error[E0956]: unknown primitive: stage

Adding `@import "stdlib"` first makes it pass. So the submodule does not resolve its own macros
when imported alone — every macro it declares falls through to a primitive lookup by the
directive's own name.

Affects at least three modules, all with the same signature:

| import                              | directive | result |
|-------------------------------------+-----------+--------|
| `@import "stdlib/3d"`               | `@stage`  | E0956 unknown primitive: stage |
| `@import "stdlib/md"`               | `@doc`    | E0956 unknown primitive: doc   |
| `@import "stdlib/scripting/script"` | `@script` | E0956 unknown primitive: script |

* Blast radius

29 `cargo test --lib` failures and 6 integration failures, including:
- all 9 `three_*` snapshot tests (`@stage should demand-inject the vendored three.js engine`)
- `doc_*` and `bug220_literate_export_tests::*` — every literate `.st.md` document
  (previously filed as BUG-338, which is almost certainly THIS bug, not a separate one)
- `bug218_clean_path_export_tests::doc_src_resolves_against_the_site_dir`

The tests are CORRECT and are catching a real regression. They write
`@import "stdlib/3d";` alone, which is the documented spelling — `stdlib/3d/index.st`'s own doc
comment says `@import "stdlib/3d"` brings in the 3D surface.

* Not caused by the PLAN-141 work (checked, not assumed)

- `src/lsp/workspace/import_resolver.rs` (changed in W5) is LSP-ONLY: grepping for its use
  outside `src/lsp` returns nothing, so it cannot affect `check`/`build`.
- `stdlib/3d/index.st` has not been touched in months (last commits 0d29a51e, 6fae395a).
- W2's scoped-unknown-directive check emits W0714 warnings; none of the 29 failures mentions
  W0714.

Most likely a recent change to module/registry loading — the same family as BUG-336 (`@script`)
and BUG-338 (literate `@doc`). All three are "a macro exists, the directive resolves to a
nonexistent primitive of the same name, E0956", which strongly suggests ONE underlying cause:
a submodule's `%macro` definitions are not registered when the module is loaded on its own.

Fixing that one mechanism likely closes BUG-336, BUG-338 and this item together.

* Fix direction

Trace what registers a module's `%macro` set at import time, and why it only happens when
`stdlib/index.st` is the entry. A submodule should be self-sufficient: importing it must register
everything it declares, exactly as its own doc comment promises.

* RESOLVED (verified 2026-08-07, commit 28d7cd3b)

Root cause was ONE mechanism, shared with BUG-336/338/340: `resolve_stdlib` consulted the
EMBEDDED module index BEFORE the filesystem. `build_stdlib_index` indexes every .st under
stdlib/ by bare name, so `stdlib/md/index.st` registered the name "md"; the embedded branch
matched and returned `ResolvedImport::Stdlib`, which `resolve_imports` skips as "handled by
MetaRegistry" — and MetaRegistry only loads STDLIB_DIRS. So an opt-in module's file on disk was
never read and its %macro set never registered. Fix: filesystem first, embedded name as fallback.
No module-name special-casing in Rust.
