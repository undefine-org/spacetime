* Found via
Round-2 pressure test, continuing the BUG-155/160/161 audit into every
stdlib primitive resolving a `$signal.field`-shaped param. `@effect(on:
$wrap.count) { ... }` never fired its mutation body at all.

* Repro (isolated, RED confirmed on pre-fix code)
#+begin_src
@data inline $wrap : { "count": 0 };
@data inline $log : 0;
.host {
  @effect(on: $wrap.count) {
    $log <- $log + 1;
  }
}
#+end_src
Reassigning `$wrap.count` (via a real body-scope write,
`ST.set(document.body, 'wrap', {count:1})`) left `$log` at 0 — the effect
never ran.

* Root cause
`stdlib/primitives/effect.st::effect-runner` keyed BOTH its reactive channels
by the literal `sig` string: `document.addEventListener('local:' + sig +
':updated', ...)` and `ST.watch(host, sig, ...)`. With `sig = "wrap.count"`,
neither channel is ever dispatched (no signal is ever literally named
"wrap.count") — same root cause as BUG-155/160/161.

* Fix
Derive `sigHead = sig.split('.')[0]`; key both the `local:<sig>:updated`
listener and `ST.watch` off `sigHead` instead. Unlike @each/@view/@portal,
`@effect` never needs to RESOLVE a value here at all — the mutation body
re-reads whatever it needs via `ST.runMutations`'s own `$name` substitution,
so watching the head signal (which fires whenever ANY of its fields change,
a superset) is sufficient and correct; no value-walk logic was needed.
