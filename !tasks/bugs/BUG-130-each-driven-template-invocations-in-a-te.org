* Symptom
A `&child($x)` invocation inside an `@each` block within a `@template` body's
MARKUP is not captured in the parent template's `refs`. The MCP builder navigator
(PLAN-051 B2, which walks the template graph via body.refs) therefore omits every
@each-driven child \u2014 a page that renders a list of components shows only the
container in the structure tree, not the repeated child.

* Reproduction (unit test, currently asserting the BUGGY behavior)
src/mcp/live.rs::snapshot_stage_structure_captures_each_driven_children:
  @data inline $items : [{"label":"A"}];
  @template &item($it) { <li>`$it.label`</li> }
  @template &main() { <ul>@each($items as $x) { &item($x); }</ul> }
-> main's bundle body.refs is EMPTY; the structure walk yields only ["main"],
missing "item". (The test currently asserts !has_item so the suite is green;
FLIP to assert!(has_item) when fixed.)

* Root cause (traced 2026-06-20)
Parsing the guest shows `@template:main matches=[] nested=0` \u2014 the
`@each($items){ &item($x); }` inside the `<ul>` markup produces NO scope matches
and NO nested scopes on main's Construct scope. So there is nothing for
scope_refs to harvest. Two layers:
1. scope_refs only read scope.matches (root), missing NESTED-scope invocations.
   FIXED this session (scope_refs now recurses scope.nested_scopes via
   nested_scope_refs) \u2014 covers `.sel{}`/conditional nested invocations.
2. REMAINING: an `@each` block embedded in a TEMPLATE BODY's HTML markup does not
   land as a nested scope (or matches) on the template's Construct scope at all.
   The @each-in-markup-within-a-template-body parse path doesn't surface the
   interior `&item($x)` template-invoke match to the template scope. THIS is the
   open bug. (Contrast: @each in a top-level selector scope \u2014 e.g.
   `[data-col] > .col__cards { @each(...){ &card($c); } }` \u2014 DOES work, as in
   demos/liveview-kanban; the gap is specifically @each INSIDE a @template body's
   markup.)

* Fix direction
Make the @each-in-template-body-markup parse route its interior template-invoke
matches into the template's Construct scope (as matches or a nested scope), so the
already-recursive scope_refs harvests them. Investigate convert_cst_scope /
the template-body span-containment assignment (src/parser/mod.rs ~476) for why an
@each inside template markup yields no scope content, vs an @each in a selector
scope which does. Likely the template-body-as-scope builder doesn't descend
@each blocks the way selector scopes do.

* Root cause CONFIRMED (2026-06-20, parse-layer probe)
Definitive contrast via `inspect --layer parse`:
- @each in a SELECTOR scope:
    .list { @each($items as $x) { &item($x); } }
  -> parse layer shows `@each (item, key, source, invocations)` + `each_blocks: 1`.
  FULLY PARSED; the interior &item invoke is captured.
- @each in a TEMPLATE BODY's markup:
    @template &main() { <ul>@each($items as $x) { &item($x); }</ul> }
  -> parse layer shows ONLY `@template (body, params, name)`. The @each block is
  SWALLOWED into the template's `body` capture as opaque HTML \u2014 NOT parsed into an
  @each FormMatch, so its interior &item invoke never exists as a match.

So the template-body parser treats body content as HTML markup + recognizes only
nested `.sel{}` scopes / injections / directives \u2014 it does NOT descend @each blocks
embedded in markup the way a selector-scope body does. The interior template
invocation is therefore never produced (confirmed: main's Construct scope has
matches=[] nested=0).

* Fix (scoped)
Make the template-body parse path recognize + descend `@each` (and likely `@view`/
conditional) blocks embedded in body MARKUP, parsing their interiors into the
template's scope (as an @each match with invocations, mirroring the selector-scope
path that already yields `each_blocks` + `invocations`). Then the existing
(now-recursive) scope_refs harvests the interior invoke. Candidate site: the
template-body-as-scope construction (src/parser/mod.rs ~575-700) +
reconstruct_template_body_html / the body capture \u2014 the @each interior must not be
absorbed as opaque HTML. Cross-check how selector-scope @each parsing
(`each_blocks`) is produced and bring the template-body path to parity.

* Deep root-cause trace (2026-06-22, PLAN-059 headless review)
Reproduced the COLLECTION-REF form failure precisely and traced it through all layers. The 4 RED pins in tests/unit/templates/collection-ref-each.test.st all stem from ONE gap:

REPRO (minimal):
  @template &cr-dash() {
    <section class="cr-dash"><div class="cr-cards"></div></section>
    &cards[] .cr-cards { @each($crItems as $item) { &cr-card($item); } }
  }
`inspect --layer parse` on this shows cr-dash has ONLY `directives: 1 (@element-ref)` + `element_ref_decls: 1` — NO @each match, NO each_blocks, NO nested scope. The entire `{ @each }` body is dropped.

CONTRAST (works today): the PLAIN selector form `.cr-cards { @each(...) { &cr-card } }` parses to `nested_scopes: 1` and renders correctly headless (proven: a minimal kit-form-style template with ST.setData seeding renders N rows, holes resolved). So plain selector-scope @each in a @template body WORKS; only the `&ref[] .sel { @each }` collection-ref wrapper drops it.

LAYER-BY-LAYER (the real pipeline is rowan CST in src/syntax/cst/, NOT tree-sitter — tree-sitter-spacetime/grammar.js is GENERATED downstream for editors via treesitter_gen, irrelevant to the parse):
1. CST parse: `parse_element_ref_stmt` (src/syntax/cst/parser.rs:1926) DOES parse `&name selector { body }` — it consumes the selector and calls parse_body() on the `{...}`. So the body IS in the CST, under an ELEMENT_REF_STMT node. (NB: parse_element_ref at :1898 does NOT consume the `[]` collection marker — a separate small gap.)
2. Match scan: the directive/FormMatch scanner does NOT descend ELEMENT_REF_STMT bodies — so the interior `@each(...)` never becomes a FormMatch at all (parse layer shows zero @each). This is the PRIMARY drop.
3. Scope harvest: src/parser/mod.rs:592 `for nested in body.nested_scopes()` collects only SCOPE_BLOCK children. ELEMENT_REF_STMT children (body.element_ref_stmts(), ast.rs:246) are NOT harvested as nested scopes — so even if the @each match existed, there'd be no nested scope (selector .cr-cards) to receive it via assign_match_to_nested_scopes.
4. Builder/runtime: never reached — the cr-dash factory emits ONLY `<section><div>` markup (dumped compiled JS: `crItems` appears only in the test's own ST.setData call, never in an emitted @each primitive). No collection-ref state array wiring.

THE FIX (vertical, 4 layers):
(a) Match scanner must descend ELEMENT_REF_STMT bodies so the interior @each/@view/&invoke become FormMatches (mirroring how SCOPE_BLOCK bodies are scanned).
(b) src/parser/mod.rs template harvest must turn an ElementRefStmt-with-body into a NestedScope (selector = its selector_text, e.g. `.cr-cards`) AND record the collection-ref binding (`&cards[]`, is_collection=true) so the @each match assigns into it.
(c) parse_element_ref / element-ref-stmt must consume the `[]` collection marker (currently dropped).
(d) Builder: emit the @each primitive from that nested scope + wire the collection-ref state array (MutationObserver collecting children into `ST.set(host, 'cards', [...])`), which the 4 tests assert.
