* Root cause

CSS2.1 §10.8.1 baseline rule for atomic inline-level boxes (inline-block /
inline-flex / inline-grid / inline-table):

  "If the box has no aforementioned inline-level descendants, the baseline
  is the bottom margin edge... unless it has `overflow` other than
  `visible`, in which case the baseline is the bottom margin edge. When
  overflow computes to `visible`, the baseline is the last line box's
  baseline (or the box's own baseline if it has content lines)."

`.ora-hero__flap` is authored `display: inline-block; overflow: hidden;`
(`projects/ora-ventures.com/modules/_hero.st::.ora-hero__flap`).
`value-change-driver`'s Phase 2 (overflow setup, `stdlib/primitives/animation/drivers.st`
~L868-869) legitimately sets `%&el.style.overflow = 'visible'` during the
transition (needed so the clip-path reveal isn't double-clipped), then
Phase 5 cleanup resets it back to `''` (→ authored `hidden`) once the
transition settles.

Each toggle FLIPS which baseline rule the browser applies to this atomic
inline-level box. Flipping the baseline rule changes how much ascent/descent
the box contributes to the surrounding anonymous line box inside
`.ora-hero__title` — which changes the ENCLOSING line box's computed height,
even though the flap's own rect stayed the same shape.

Direct proof (forced state toggle via puppeteer `evaluate`, same DOM, same
text, only `overflow`/`vertical-align` changed):

```
current (overflow: visible, vertical-align: baseline)        → titleH = 315.25px
force overflow: hidden  (vertical-align: baseline, default)  → titleH = 329.36px
force overflow: visible (vertical-align: baseline, default)  → titleH = 315.25px
force overflow: visible + vertical-align: bottom             → titleH = 315.25px  (stable)
force overflow: hidden  + vertical-align: bottom              → titleH = 315.25px  (stable)
```

Pinning `vertical-align: bottom` makes BOTH overflow states agree on
315.25px — proving the coupling and the fix in one probe.

* Fix

`stdlib/primitives/animation/drivers.st::value-change-driver` — pin an
explicit, FIXED `vertical-align` on the target element ONCE at mount time
(not just during the transition window), so the CSS2.1 baseline-computation
mode never depends on which `overflow` value happens to be set at any given
instant:

```js
var initialCs = getComputedStyle(%&el);
var initialDisplay = initialCs.display;
var isAtomicInlineBox = initialDisplay === 'inline-block' ||
  initialDisplay === 'inline-flex' || initialDisplay === 'inline-grid' ||
  initialDisplay === 'inline-table';
if (isAtomicInlineBox && initialCs.verticalAlign === 'baseline') {
  %&el.style.verticalAlign = 'bottom';
}
```

Placed right before the `MutationObserver` setup (after `currentText` init,
before `observer = new MutationObserver(...)`), so it runs once per driver
instance mount, unconditionally of any subsequent transition cycles.

Design choices:
- Scoped to atomic inline-level `display` values only (`inline-block`,
  `inline-flex`, `inline-grid`, `inline-table`) — block-level elements don't
  participate in inline baseline alignment, so the coupling is a non-issue
  for them; skipping avoids an unnecessary style write.
- Conditioned on the element's CURRENT computed `vertical-align` being the
  default `baseline` — if an author already set an explicit
  `vertical-align` (e.g. `top`, `middle`), that choice is respected instead
  of being silently overridden.
- `bottom` chosen (not `top`/`middle`) because it matches the existing
  per-word container convention already used inside the same driver
  (`wc.style.verticalAlign = 'bottom'`, Phase 3 word-container setup) — one
  consistent alignment mode top-to-bottom through the whole component.
