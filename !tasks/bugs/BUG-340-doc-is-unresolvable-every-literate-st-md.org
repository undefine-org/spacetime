EVERY literate `.st.md` document, since the tangler synthesizes that import for

The `doc` macro binds `render-markdown` (`stdlib/md/macros/doc.st`), so

Each probe carries the explicit `@import "stdlib/<module>"`, so this is not the
literate synthesis path — it is module import resolution generally.

MECHANISM (partly established): `STDLIB_DIRS` (`src/metasystem/registry.rs:147`)
lists only the always-on directories — capture-types, runtime, primitives,
syntax, macros, testing, migrations/entries, comments/entries, scalars, enum.
The opt-in modules are NOT in that list by design; they are meant to load
on demand when a page imports them. That on-demand path is what regressed:
`spacetime inspect --layer registry` on a page that imports `stdlib/md` shows
129 primitives and no `render-markdown`, and no `doc` macro.

Each module's own files parse clean (`check` on `stdlib/md/{index,MODULE,vendor}.st`,
`macros/doc.st`, `primitives/render-markdown.st` — 0 errors each), and the
vendored snarkdown bundle is present and matches its `.commit` pin. So the
files are fine; the loader never registers them.

them spans a large lane merge (~170 files incl. `src/lsp/workspace/import_resolver.rs`,

** NOTE FIXED (commit 1b24e320)
Ordering bug in resolve_stdlib (src/lsp/workspace/import_resolver.rs): the
EMBEDDED module index was checked before the filesystem, and build_stdlib_index
indexes every .st under stdlib/ by BARE NAME — so stdlib/md/index.st registered
the name "md", the embedded branch matched, and the import returned
ResolvedImport::Stdlib. That variant is a dead end for the opt-in modules:
resolve_imports skips it ("handled by MetaRegistry") and MetaRegistry loads only
STDLIB_DIRS, which deliberately excludes them.

Fix: filesystem first, embedded name as the fallback (for an installed binary
with no checkout). The always-on modules resolved either way, which is why this
presented as a @doc bug rather than a resolver bug.

Gates: tests/bug_340_optin_stdlib_modules_test.rs — one page per opt-in module
(md / text / 3d) plus a literate .st.md page built end to end. RED-checked: all
four fail against the old ordering. The literate test is the one that would have
caught this on landing day — it imports nothing by hand, and asserts the prose
segment reaches the document, so a green build emitting no prose still fails.

Recovered: demos/brand-catalog (demo_brand_catalog_test 0/4 -> 4/4),
demos/spacetime-docs, every .st.md page. NB demos/starter-pack still fails on an
unrelated pre-existing issue (retired @on syntax, 2026-07-26 wave).
