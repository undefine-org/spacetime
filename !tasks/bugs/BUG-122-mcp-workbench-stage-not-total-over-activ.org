* Initial Message

Found while test-driving the MCP workbench (2026-06-19). User: "open environment
simply doesn't work" and "why a separate page instead of loading it when I load an
environment — load in the main frame is the primary concern."

* VERIFIED behaviour (live, source-traced)

Clicking "Open environment" DOES work server-side: the `.mcp-open-env` button fires
`st_env_open` (audience: server), the sink resolves it synchronously, and the
snapshot's `environments.open` grows (verified: after clicking, `open:[ikarchitecte,
playground]` in input.json; the nav drawer's "open" section renders the open-env
cards). So the ACTION is wired and the server state is correct.

The DEFECT is on the render side: the dominant surface (the STAGE) is NOT a function
of the active-env state. Opening an env changes server state but the stage shows the
SAME "Begin here" empty-state. From the user's seat that is indistinguishable from
"doesn't work" — the result is buried as one card among 40+ "discovered" cards in a
drawer, with zero feedback on the main surface.

* Root cause: the stage @view is not total over active state

stdlib/__mcp__/env.st, the stage region:

  .mcp-stage[data-st-region="stage"] {
    @mcp-region
    @view $stageTpl {
      _ => &$stageTpl();      // ONLY guest-or-empty. NO arm for an opened env.
    }
  }

The stage switches on `$stageTpl` (a composed guest function) with a single
wildcard arm. There is NO arm for "an environment is open" — so opening one cannot
paint anything on the stage. The state exists; the surface ignores it.

Compounding (the "separate page" complaint): the only env/tab affordance that shows
CONTENT is the instance card's `<a href=... target="_blank">Open preview</a>`
(cards.st). Frame-first loading does not exist for envs/tabs — separate page is the
ONLY door, when it should be the secondary opt-out.

* The invariant being violated: the dominant surface is total over declared state

A state-mutating action with no visible effect on the dominant surface must be
UNREPRESENTABLE. The cure is the pattern env.st ALREADY uses for `$drawer` and
`$selected`: a single-value signal + a TOTAL `@view` switch (every value has an arm).
Once `stage = f(activeView)`, "I opened an env and the stage ignored it" cannot exist
— the author either writes the arm or sees the gap.

* FIX (Spacetime — mirrors the existing $drawer idiom in env.st)

1. Add an active-view signal (mirrors `@data inline $drawer : "none"`):
     @data inline $stageView : "";

2. The open-env button also NAMES the view (pairs with the existing server action):
     .mcp-open-env { @on click { $stageView <- "env"; } }
   (the @mcp-action stays — server opens the env; this makes the stage react.)

3. Make the stage @view TOTAL — an arm per state, including the open-env one:
     .mcp-stage[data-st-region="stage"] {
       @mcp-region
       @view $stageView {
         "env"   => &mcp-env-detail($mcpActiveEnv);   // tabs + files, IN the stage
         "guest" => &$stageTpl();                       // composed function (today's path)
         _       => &mcp-begin();                        // "Begin here" empty-state
       }
     }

4. New `&mcp-env-detail($env)` template (cards.st) renders the open env's tabs/files
   IN the stage, with the separate-page link demoted to an explicit secondary action:
     @template &mcp-env-detail($env) {
       <section class="mcp-env-detail">
         <h2>`$env.title`</h2>
         <div class="mcp-tab-list"></div>            // tabs load HERE, frame-first
         <a class="mcp-popout" href="`$env.url`" target="_blank">Open as separate page ↗</a>
       </section>
     }

5. Data plumbing: the snapshot must publish the ACTIVE env (the most-recently-opened,
   or a selected one) as `$mcpActiveEnv` so the "env" arm has a subject. Check
   workbench_snapshot in src/mcp/live.rs (it already flattens environments.open) +
   data.st (the $mcp* published signals). Likely: publish `active_env` = last opened,
   set $stageView to "env" on open server-side too (so a reload shows it), and bind
   $mcpActiveEnv from it. Confirm the empty-state ("Begin here") becomes the `&mcp-begin`
   template extracted from the current inline stage-empty markup (so the `_` arm has a
   real template to mount).

NB harmony: this adds ONE signal + arms mirroring the proven $drawer/$selected
pattern — no new mechanism, no parallel renderer. The empty-state markup currently
inlined in the stage must move into a `&mcp-begin` template so it's an @view arm
(today it's the region root's initial child + a CSS hide-on-sibling rule; with a
total @view the empty-state becomes the `_` arm — cleaner, and removes the CSS
:has hide hack).

NOTE [2026-06-19]: IMPLEMENTATION DEVIATION from the original fix sketch (source-verified 2026-06-19). The body proposed a second `@data inline $stageView` + a `@view $stageView` switch on the stage region. VERIFIED that collides: the stage region `.mcp-stage[data-st-region="stage"]` already owns ONE `@view $stageTpl` slot, and `$stageTpl` is an ELEMENT-scoped signal written by the bundle-poll's `registerBundle` (guest composition, bundle.st + view.st). A second `@view` on the same root is not supported and would fight the guest-mount path.

HARMONIOUS FIX (respects existing architecture, pure stdlib, zero server change): render the open-env detail FRAME-FIRST inside the stage empty-state (`.mcp-stage-empty`), revealed by the SAME JS-free `:has()` CSS idiom the gallery + comms already use (styles.st:230/300/435). Data is already published — `$mcpOpenEnvironments` + `$mcpTabs` (data.st via mcp-input). When an env is open, the stage shows its env card(s) + tabs and the "Begin here" zero-state recedes; composing a guest function still overlays via the untouched `$stageTpl` path. This converts "open env → nothing visible on the dominant surface" into "open env → env appears in the main frame", which is the user's core complaint, without a second reactive plane.
