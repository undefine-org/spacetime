* Intention & Purpose

Inline content edits originating in =.st= files that live in subdirectories of the site root (e.g. =projects/unkn/modules/_work.st=, =projects/undefine.org/modules/_work.st=) MUST round-trip through the =EditAst= sync protocol and successfully update the on-disk file.

Today they fail at the very first step because the compiler emits =data-st-origin= attributes containing only the *basename* of the source file, so the dev panel sends =EditAst { file: "_work.st", ... }=, and the server's =validate_file_path(site_dir, "_work.st")= cannot find the file (it lives at =modules/_work.st= relative to =site_dir=).

* Context & Narrative

** Sync protocol contract

The server-side handler =sync::handlers::handle_edit_ast= validates =file= via =validate_file_path(site_dir, relative_path)= (=src/sync/handlers.rs= ~124–140~). The function joins =site_dir= with the supplied relative path and canonicalizes; failure ⇒ =Err(format!("File not found: {}", relative_path))=. So the protocol REQUIRES =file= to be a path relative to =site_dir=.

** HTML files (already correct)

For =.html= files, =inject_content_provenance(html, file_path)= is invoked from =src/server.rs= ~607, 712, 844, 1071, 1187~ with a path that is already relative to =site_dir= (e.g. =subdir/page.html=, =index.html=). The dev panel echoes that string back as =EditAst.file=. Server resolves correctly.

** =.st= files (broken)

For =.st= files, the template body HTML is annotated at compile time by =inject_template_provenance= via =inject_provenance_into_matches= (=src/syntax/form_match.rs= ~1394–1418~). The injected attribute format is:

#+begin_example
data-st-origin="{source_file}::{scope_selector} §{macro_name} {tag_name}"
#+end_example

The =source_file= portion is computed as:

#+begin_src rust
let source_file_raw = fm.source_file.as_deref().unwrap_or(default_source_file);
let source_file = extract_filename(source_file_raw);  // ← BUG
#+end_src

=extract_filename= (=src/syntax/form_match.rs= ~1376–1382~) returns *only the basename*. =fm.source_file= contains the absolute path of the originating =.st= file (set by =resolve_imports= at =src/parser/mod.rs:4602= and =merge_ast= at ~4725~). So a file at =/abs/.../projects/unkn/modules/_work.st= becomes =_work.st= in the origin attribute.

** Client → server flow

=stdlib/__dev__/primitives/dev-editable.st= ~64–91~ reads =data-st-origin=, splits on the first =::=, takes the left half as =file=, and the right half as =locator= (= the selector for =.st= files). =stdlib/__dev__/primitives/dev-save.st= ~141, 186~ assigns =filePath = editEvent.file= and ships it as the =EditAst.file= field.

So the client faithfully forwards whatever the compiler put in =data-st-origin=. The server cannot correct this — it has no way to know the basename =_work.st= is supposed to mean =modules/_work.st=. The compiler MUST emit the relative path.

** Why HTML works and =.st= doesn't

=inject_content_provenance= already takes a caller-supplied =file_path: &str= argument that the dev server populates with the URL/relative path. =inject_template_provenance= is called from inside the compile pipeline where only the absolute path is known, and the original implementation chose to flatten it via =extract_filename=. We must instead carry =workspace_root= into the injection pass so it can compute a true relative path.

** Inspect-element flow (already correct, do not touch)

=src/sync/handlers.rs::handle_inspect_element= ~1177–1181~ already emits =rel_path = file_path.strip_prefix(site_dir)= for its =source_files= response and =PropertyNode.source_file= entries, which is what the dev panel's animation-properties macro echoes back as =EditAst.file= (=stdlib/__dev__/primitives/dev-panel.st:564=). That path is correct. This bug only affects the *content edit* flow (=editType === 'content'=) where the file is read from =data-st-origin=.

#+begin_src rust
/// Convert an absolute (or possibly relative) source-file path into a path
/// relative to `workspace_root`, suitable for the `EditAst` sync protocol.
///
/// Falls back to the bare filename when the source file lives outside
/// `workspace_root` (canonical equality cannot be established) — this preserves
/// the historical behavior for stdlib / orphan paths while fixing the common
/// case of project-local subfolders.
fn workspace_relative_path(source_file_raw: &str, workspace_root: &Path) -> String {
    use std::path::Path;
    let p = Path::new(source_file_raw);

    // Prefer canonical comparison when both sides are accessible.
    if let (Ok(canon_file), Ok(canon_root)) = (p.canonicalize(), workspace_root.canonicalize()) {
        if let Ok(rel) = canon_file.strip_prefix(&canon_root) {
            return rel.to_string_lossy().to_string();
        }
    }

    // Fast path: if the raw value is already relative under workspace_root,
    // strip directly without touching the filesystem (covers tests and tmpdirs
    // where canonicalize is fine but we want to avoid double work).
    if let Ok(rel) = p.strip_prefix(workspace_root) {
        return rel.to_string_lossy().to_string();
    }

    // Safety net: bare filename. Prevents emitting an absolute path into
    // data-st-origin (which would still break the protocol downstream).
    extract_filename(source_file_raw).to_string()
}
#+end_src
