NOTE [2026-08-05]: FIXED in cb3b820a, same session it was filed.

The fix is neither of the two options this item recorded as rejected. Both were
tried and backed out for the reasons above; the third seam is the right one:

**Coerce at the primitive-argument boundary**, in `resolved_to_primitive_args`
and its sibling call site (`src/pipeline/expand.rs`). That is the ONE place that
knows both halves — what the value IS (a duration's source text) and what the
receiver DECLARED it should be (`source.st:20`: `refresh: number = 0`). Neither
the extractor (which knows the value but not the receiver) nor codegen (which
knows neither, and would have to sniff the spelling) can answer it.

Found by INSTRUMENTING rather than guessing. Two call sites were patched on the
assumption the value was a `String`, and both still failed; a one-line probe
showed it arrives as `Expr("300ms")`, because a body-param capture
(`{ refresh: 5m }`) is an unparsed expression rather than a typed scalar. The
declared param type is what makes it a number either way — which is also why the
fix generalizes: any duration landing in any `number`-typed primitive param now
converts, not just `refresh`.

Only a value the duration converter RECOGNISES is rewritten. Anything else falls
through unchanged, so a genuinely non-numeric value still reaches codegen as
itself instead of being coerced into a plausible lie.
