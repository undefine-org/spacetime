* Initial Message

* Report

Live user report (2026-07-24): "i can't host backdesk-new :( when I click on
create project in the host pill it does nothing".

* Diagnosis (verified this session, live browser against `serve projects/backdesk-new`)

Two stacked causes:

** 1. Environment: orchestrator unreachable (the actual hosting blocker)

`spacetime.undefine.org` resolves to 178.105.176.219 (direct IP, NOT the
Cloudflare-proxied `undefine.org` = 188.114.96.5/97.5). TCP connect to
:443/:80 times out (~135s), ping 100% loss. General connectivity is fine
(google/undefine.org reachable). The widget's `POST /api/v1/projects` can
therefore never succeed from this machine until that server is back up (or
`SPACETIME_HOST_ENDPOINT` points at a live instance -- src/server.rs::host_api_base).

** 2. Widget bug: network-level failure is INVISIBLE (the "does nothing")

Verified live: the click DOES fire (instrumented `window.fetch` -- the request
to `https://spacetime.undefine.org/api/v1/projects` appears), the fetch
rejects (`TypeError: Failed to fetch`), and then... nothing renders.

Chain:
- stdlib/primitives/signal.st: a network-level rejection never builds a reply
  envelope -- `runWithRetry` catches, sets the internal `error`, and
  `yieldState()` publishes ONLY the `_pending`/`_error` yields (BUG-197 made
  those real). No `signal:<name>:reply` event fires, BY DESIGN.
- stdlib/__host__/index.st `@handle $createProject` has only reply arms
  (Created/Rejected/Failed) => none run => `$createProjectError` stays `""`
  => `.st-host-widget__create-project-error` stays hidden.
- The widget does NOT consume `$createProject_error` -- unlike push-preview,
  which already established the pattern after the SAME bug class
  (line ~943: `$pushPreviewErrorText : ($pushPreviewMessage || $pushPreview_error || "")`).
- Compounding: `$createProject` declares `policy latest` with NO timeout, so
  against a black-holed host the fetch hangs for the browser's full TCP
  timeout (order of minutes) before even the `_error` yield fires.

Same latent gap in the write-back half: `$initDeploy`'s `$writeBackFailed` is
only set by its Failed arm -- a network-level rejection of the LOCAL write-back
call would also be silent.

* Fix (stdlib/__host__/index.st only -- platform rails are already correct)

1. Fold the `_error` yield into the create-project error surface, mirroring
   push-preview verbatim:
   - `@data derive $createProjectErrorText string : ($createProjectError || $createProject_error || "");`
   - `$hasCreateProjectError` now tests `$createProjectErrorText`
   - error <p> renders `$createProjectErrorText`
2. Same for write-back: derive a boolean that also tests `$initDeploy_error`
   gating `.st-host-widget__write-back-error`.
3. `policy latest timeout 15s` on `$createProject` (grammar:
   stdlib/capture-types/signal-receive.st `policy $mode ("timeout" $dur)?`)
   so a dead host surfaces in 15s, not minutes.
