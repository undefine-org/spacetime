* Symptom
`@state_machine(initial:"off") { @transition(from:"off", to:"on", on: click) }`
on a selector (or in `@given` in a test) initializes state + a `setState`
closure but the transition NEVER fires: clicking the element does not change
data-st-state / the state signal. ~37 headless failures (state-machine.test.st
+ much of state.test.st) and broken in PRODUCTION (jallete cart/configurator,
jeton wizard, playground tabs all dead).

* Reproduction
/tmp/sm_site.st:
```
<div class="toggle-click" data-st-state="off">Toggle</div>
.toggle-click {
  @state_machine(initial: "off") {
    @transition(from: "off", to: "on", on: click)
  }
}
```
`cargo run --features headless -- inspect /tmp/sm_site.st --layer emit`:
- EMITS: `const setState = (newState) => {...}`, state bookkeeping
  (__stStateHistory etc.), `ST.set(el,'setState',setState)`.
- DOES NOT EMIT: any `addEventListener`, any `setState(` INVOCATION, any
  `__stSetState(` call. Grep the emit: 0 occurrences. The transition is a
  no-op.

* Root cause (verified)
The primitive IS correct: stdlib/primitives/state.st:123 `%primitive
state-transition(&el, from, to, on, run?)` emits
`%&el.addEventListener(%on, handler)` + a shared document listener, and handler
calls `%&el.__stSetState(%to)`. So the listener exists IN THE PRIMITIVE.

The defect is the macro→primitive expansion. stdlib/macros/state-machine.st:
- `state-machine-block` (%form captures `$transitions:transitions*` inline) has
  a `%binds` with `%for $t in $transitions { ... state-transition(&self, ...) }`
  dispatcher (lines ~74-110) that routes each transition to the right primitive
  by inspecting $t.after / $t.on / $t.debounce.
- That %for loop's `%binds state-transition(&self, ...)` is NOT expanding into
  the output. Tracing `inspect --layer expand` shows NOTHING for the
  transitions; `--layer ir` shows only the Cleanup statements, no transition
  primitive. So the `transitions*` capture is either empty at bind time, or the
  %for-over-captured-registrations does not emit the %binds.

Open question for the fix (if fixing instead of deleting): is the bug in (a)
the `transitions*` capture not populating, (b) %for not iterating a
`%registers`-collected list, or (c) the %binds inside %for not reaching
codegen? Likely related to the `%registers transition { ... }` →
`$transitions` collection wiring. NB the separate-directive form (jallete:
`@state_machine(...); @transition(...);` as sibling selector directives, not
nested) likely fails for a DIFFERENT reason (the @transition is a sibling, not
captured by the block) — confirm both forms.

* Resolution path
Per PLAN-047 (user decision): this construct is being DELETED, not fixed —
replaced by the $-signal idiom. This bug documents WHY (so the deletion is
justified by a real, root-caused defect, not a guess). If a future need for a
declarative state machine arises, this analysis is the starting point: the fix
is in the block dispatcher's transition-collection→%binds expansion, the
primitive itself is sound.
