* Symptom
After FEAT-047 deleted the legacy block-form macros (`@data NAME : T { src/value/cache }`,
`@computed NAME : T { from/where/... }`, paren-forms `@data(...)`, `@each(items:...)`,
`@computed(...)`), an .st file still USING the old syntax does not error — it parses as an
unrecognized directive and SILENTLY NO-OPS (binds nothing). The in-repo corpus is fully
migrated, but EXTERNAL authors of this published stdlib who used the old forms get no
signal that their data binding stopped working.

* Repro
  @data products: Product[] { src: "/api"; }
  .l { text: $products; }
-> compiles ✓, but products is never bound (no data-source emitted). No diagnostic.

* Fix direction
Add a deprecation/error diagnostic (e.g. W07xx) that recognizes the SHAPE of the removed
forms and points at the unified surface:
  - `@data NAME : T { src: ... }`        -> "use @data fetch $NAME T : <url> { refresh: ... }"
  - `@data NAME : T { src: inline; value: V }` -> "use @data inline $NAME T : V ;"
  - `@computed $NAME : T { from: S; ... }` -> "use @data query/fold $NAME from $S ..."
  - `@data(...)`, `@each(items:...)`, `@computed(...)` paren-forms -> unified equivalents
This is a lint over FormMatch/unmatched-directive shape, NOT a re-introduction of the macros.
Could live alongside the existing migration note in stdlib/macros/type-data.st + data.st.

* Acceptance
- An .st using any removed legacy form emits a clear deprecation diagnostic naming the
  unified replacement (not a silent no-op).
- The diagnostic does NOT fire for the unified surface.
- A test enshrining the diagnostic for each removed form.
