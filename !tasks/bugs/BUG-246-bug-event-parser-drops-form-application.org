Reproduced: `@on &.visible(threshold: 0.2) --rise(distance: 8px);` loses the form's call args at MATCH time — the `form` capture becomes `Named{form: --rise}` with NO `args` key, so the expansion silently substitutes the form's DEFAULTS (measured: emitted keyframes carry `24px`, not `8px`). Without driver params (`@on &.visible --rise(distance: 8px);`) the args survive.

Measured facts:
- Extractors work in isolation: driver_expr consumes 9 tokens, form_application consumes 8 WITH args (unit probe in src/syntax/events/extractors/custom.rs::driver_form_probe).
- The bug only appears through the production event-parser path (parse_matches → MatchSink): `parse_matches(".x { @on &.visible(threshold: 0.2) --rise(distance: 8px); }")` returns the args-less capture.
- Body splices are unaffected: `@on &.scroll(start: 0.2) { --rise(distance: 8px); }` emits 8px correctly.
- Present since the driver-params commit (025981d5, W3.2) — the combination driver-params + form-args was never tested together. Found by the W3.5 article gate (tests/sip_001_w3_article_gate_test.rs) when the article's footer fence combined them.

Impact: silent wrong behavior (defaults substituted for explicit args) — the worst class per the project's uninferrable-is-error rule.

Suspected area: the event-parser/MatchSink path for custom-type captures (NOT form_compiler — the isolated extractor path is clean, and the body-splice path works). Next step: trace how MatchSink computes the token slice for the second custom capture and where the `args` key is dropped in capture merging.

Gate: tests/sip_001_w3_article_gate_test.rs::the_splice_call_args_override (currently RED against the article's footer fence).
