* Symptom
A Spacetime test `@eval (() => { ... })` body that contains a JS ARRAY LITERAL holding
an OBJECT LITERAL crashes the test parser with `expected '{' after selector` (multiple,
at offsets into the EXPANDED source ~47K for a tiny file). The `@eval` body extractor /
lexer treats the `[ { ... } ]` sequence as a CSS selector followed by a rule block.

* Minimal repro (no imports)
#+begin_src
@test "arrobj" {
  @mount { <main><div class="x"></div></main> }
  @eval (() => { const o = { c:[ { t:1 } ] }; window.__v = o.c[0].t; })
  @then { @assert (window.__v === 1) "ao"; }
}
#+end_src
→ ParseError "expected '{' after selector".

* What WORKS (narrows the trigger)
- `const o = { a:{ b:1 } };`        ✓ (nested object, no array)
- `const o = { a: { b:1 } };`       ✓
- `JSON.parse('{"a":1}')`           ✓ (colon inside a string is fine)
So the trigger is specifically an OBJECT literal nested INSIDE an ARRAY literal:
`[ { … } ]`. The `[` then `{` makes the embedded-JS scanner think `{ … }` is a
selector's rule block.

* Impact
Blocks writing a Spacetime `.test.st` `@eval` that constructs a structured document
inline (e.g. an editable doc `{ type:'doc', content:[ { type:'p', … } ] }`). Hit while
writing the FUP-045 S3 region surface test \u2014 had to route the live region-edit proof to
the CDP/puppeteer rung instead (real browser JS, not the `.st` @eval lexer). Workaround:
avoid array-of-object literals in `@eval`; build via property assignment or a runtime
helper, OR seed through a bound signal rather than `@eval`.

* Likely fix locus
The embedded-JS body scanner for `@eval` (and probably `@when`/`@drive` payloads) \u2014
wherever the `.st` parser balances `@eval (...)` it must treat `[`/`{` uniformly as JS
bracket nesting, not switch into selector/rule mode on `{` after `[`. Find the @eval
body tokenizer in the test-runner parser.

NOTE [2026-06-12]: FIXED. Root cause: parse_arg_value (the @eval/@drive/@when payload path) had NO arrow-fn handling. An arrow `(params) => { …JS… }` fell through to parse_paren_expr → the body `{}` was parsed as parse_object_or_body (Spacetime selectors/rules), and the body's first inner `}` ended the arg early, spilling the rest of the JS to the top level → "expected '{' after selector".

Fix (src/syntax/cst/parser.rs): a new parse_arrow_fn_balanced() consumes the whole arrow — params paren (matched), `=>` (EQUALS+GT), then the body with FULL bracket-depth tracking (block body by matched braces tracking {}/[]/(); expression body to the depth-0 boundary). Wired via `L_PAREN if self.is_arrow_fn() => parse_arrow_fn_balanced()` in parse_arg_value, reusing the existing is_arrow_fn() lookahead. ~55 lines, purely additive (a non-arrow `(` still routes to parse_paren_expr).

Verified: the exact array-of-object @eval repro now parses + runs; lib 2250, integration 172, import_resolution 22, all green (no regression in the shared directive parser).
