* Summary

A `@on &.scroll(...)` animation does not paint its FIRST keyframe before the
scroll driver has advanced. At rest (progress 0) the element shows a
partially-advanced value instead of the declared start value.

Under `--cdp`, 6 of the 7 failures are the same assertion:

#+begin_example
✗ in/out scroll animations: initial state uses first animation value
    Expected .comp-target to have opacity: 0, got 0.441667
✗ in/out composition with multiple properties preserves initial state
    Expected .multi-target to have opacity: 0, got 0.353333
✗ single scroll animation applies initial state normally
    Expected .single-target to have opacity: 0, got 0.276667
✗ single scroll animation with multiple properties
    Expected .sm-target to have opacity: 0, got 0.265556
✗ multi-keyframe initial state uses first keyframe value for opacity
    Expected .mk-initial to have opacity: 0, got 0.51
✗ two-keyframe initial state uses first keyframe value
    Expected .mk-two-kf to have opacity: 0, got 0.83
#+end_example

The 7th is adjacent but distinct and may have its own cause:

#+begin_example
✗ scroll animation respects start parameter
    Timeline "delayed" not registered
#+end_example

The observed values are non-deterministic across runs (0.44, 0.35, 0.27,
0.51, 0.83) — consistent with the element being sampled while the driver is
mid-advance, i.e. the animation is running on wall-clock/RAF before scroll
progress is bound, rather than being pinned to progress 0.

Visible consequence: any scroll reveal flashes a partially-faded element on
load instead of starting from its declared first keyframe.
