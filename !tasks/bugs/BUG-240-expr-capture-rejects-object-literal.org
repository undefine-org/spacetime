#+TITLE: `expr` capture rejects a `{ ... }` object literal (@output-json)
#+STATE: ITEM
#+CUSTOM_ID: BUG-240-expr-capture-rejects-object-literal

* Symptom

`stdlib/scripting/io.st:105` declares `@output-json $path:string data: $data:expr`,
and its OWN doc comment (line 100) shows an object literal as the argument:

: /// @output-json "./analysis.json" data: { edits: $edits, stats: $stats }

`examples/scripts/analyze-directives.st:30` writes exactly that shape and it does
not match: "`$data` could not be captured as `Expr`: no tokens matched that
grammar". The directive was silently dropped; `check` was green, and the script
produced no output.

* Why this matters

The documented usage of a stdlib macro does not work. The doc comment is the
specification an author reads, so this is a contract break, not a typo.

Also note `{ ... }` after a directive is ambiguous with a BODY block — which is
plausibly why `expr` refuses it. If so, the fix may be a distinct capture type
(`object_literal`) rather than widening `expr`, since widening could make every
directive's body ambiguous.

* Found by

BUG-229's E0946 gate.

* Acceptance

- The documented `@output-json "..." data: { ... }` form works, OR the doc comment
  and the example are corrected to the shape that does.
- `examples/scripts/` compiles clean.
- If a new capture type is introduced, it does not make `$x:expr` swallow bodies.
