* Symptom
On demos/liveview-kanban, the browser threw on every recompute:

#+begin_example
[derived-signal viewedCards] TypeError: can't access property "length", SpacetimeLocal.history is undefined
#+end_example

The =@data derive $viewedCards= reads =$history.length=, but =$history= (declared
=@data inline $history Card[][] : []=) was never seeded into =SpacetimeLocal=, so
the derive's initial recompute crashed. This crash aborted the page's reactive
init, cascading into "Template not found: card N" warnings and the user-reported
"%animates don't work" (enter/exit transitions never ran because init died).

* Root cause
=consume_type_term= in =src/syntax/events/extractors/simple.rs= consumed only ONE
=[]= array suffix. For a 2-D type =Card[][]= it captured =Card[]= and left a
trailing =[]=. The enclosing =@data inline= =%form= pattern
(=$name:binding $type:typeref? : $value:expr ;=) then failed to match the stray
=[]= before =:=, so the WHOLE directive was silently dropped — no =local-state-impl=
emitted, =SpacetimeLocal.history= never created.

Verified: =cargo run -- inspect --layer parse= on three =@data inline= decls showed
=data: 2= (not 3); =Card[][]= alone yielded =data: 0=.

* Fix
Changed the single =if= consuming =[]= to a =while= loop so a type term consumes
every adjacent =[]= pair (=Card[]=, =Card[][]=, ...). One-line structural fix in
=consume_type_term=.

* Tests
- Unit: =typeref_extractor_nested_array= in =src/syntax/events/extractors/simple.rs=

* Update — ws parse-error spam also fixed (was listed out-of-scope)
The =[ws] Failed to parse client message= spam was a SECOND defect, now fixed:

The dev =/ws= is the edit-protocol socket, but a served page aims its OWN runtime
traffic there too (=@host ws("/ws")= signal frames =\{type:"move",\u2026\}=, =@presence=
=\{type:"PresenceJoin",\u2026\}=). The recv loop logged EVERY non-edit frame as a parse
error. Fix (=src/dev_server.rs=): on a parse failure, inspect the frame's =type=
discriminator; only warn when it names a KNOWN edit/control message
(=is_edit_protocol_type=) — a genuinely malformed edit. A page's own runtime
frame (unknown type) is swallowed quietly. New unit test
=edit_protocol_type_recognises_own_frames_only=.

Verified: a freshly-built server logs 0 parse errors for move / PresenceJoin /
PresenceUpdate / Subscribe frames.

GOTCHA: the fix only takes effect on a server STARTED FROM THE NEW BINARY. A
=cargo run -- serve= process launched before the rebuild keeps running the old
code and will keep spamming — restart it.

NB: this only silences the noise. The =$move= optimistic→reply loop and
=@presence= cursors still need a real runtime-signal/presence BACKEND on the dev
=/ws= (and =public/runtime/realtime.js= is not bundled, so =SpacetimeRealtime= is
undefined client-side). That multiplayer backend remains FEAT-136/137 scope.
