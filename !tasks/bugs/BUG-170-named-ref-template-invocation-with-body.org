* Found via
PLAN-071 (ora-ventures.com rewrite) \u2014 the nav template's =&links= slot never
rendered its content when invoked with a named ref
(=#ora-nav-slot { &nav &ora-nav("Ora Ventures") { <a>...</a> } }=).

* Repro (RED, confirmed 2026-07-09 on main, dev server + puppeteer)
#+begin_src spacetime
@template &nav-tpl($brand, &links) {
  <nav>
    <span>`$brand`</span>
    <div class="links">`&links`</div>
  </nav>
}
<main class="page">
  <div id="nav-slot"></div>
</main>
#nav-slot {
  &navinst &nav-tpl("Test") {
    <a href="#a">OnlyOne</a>
  }
}
#+end_src
Rendered DOM: =<div class="links"><!--&links--></div>= \u2014 the =<a>= never
appears. Removing ONLY the =&navinst= named ref (bare form:
=&nav-tpl("Test") { <a>...</a> }=) makes the link render correctly:
=<div class="links"><a href="#a">OnlyOne</a><!--&links--></div>=.

* Secondary finding (both forms): leftover comment marker
Even the WORKING bare-invocation case leaves the =<!--&links-->= HTML
comment marker sitting in the DOM alongside the correctly-inserted content
(=<a>...</a><!--&links-->=, not just =<a>...</a>=). This is a cosmetic/DOM-
cleanliness bug independent of the named-ref issue \u2014 the anchor comment
used for insertion-position tracking should presumably be removed (or kept
invisible/non-conflicting) once its content resolves, not persisted forever
next to the real content.

* Scope note vs BUG-169
This is DIFFERENT from BUG-169 (=@mount= test-harness bare-vs-named-ref
=$param= hole resolution): BUG-169 was about VALUE params (=`$label`=) inside
the =@mount= test harness specifically, and found NAMED-ref FIXES the bug
there. THIS bug is about an ELEMENT param (=&links=) body-SLOT, reproduced
in a REAL served page (dev server, not =@mount=), and found the OPPOSITE
polarity: named-ref BREAKS it, bare WORKS (with the marker leftover). Two
distinct bugs in the same invocation-form space \u2014 do not conflate fixes.

* Impact on PLAN-071
The nav/footer templates in projects/ora-ventures.com/index.st originally
used named-ref invocations (=&nav &ora-nav(...)=, =&footer &ora-footer(...)=)
to give the runtime-rendered element a stable ref handle. Switched to BARE
invocations as a workaround (this bug) \u2014 losing the =&nav=/=&footer= ref
handles, which were unused elsewhere anyway so no functional loss for this
site, but a real API-usability loss in general (named refs are how a page
reaches into a template instance from outside, e.g. for a controlling
script or a sibling selector).
