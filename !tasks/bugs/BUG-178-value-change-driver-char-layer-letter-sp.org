* Summary

Two independent, live-verified defects in the PLAN-072 line-aware rewrite of
value-change-driver (stdlib/primitives/animation/drivers.st), found via
fresh CDP/puppeteer DOM sampling per user report ("still looks weird... text
goes from one line then jumps to two"). Both DONE: root-caused, fixed,
live-verified with before/after numbers, covered by new Rust unit tests.

** Bug A -- buildCharLayer doesn't apply letter-spacing to its char spans

Each grapheme in a word becomes its own display:inline-block span (so it can
animate independently during the split-flap enter/exit). Per-element
inline-block boxes do NOT inherit letter-spacing across their combined width
the way a single text run does -- splitting a word into N separate atomic
inline boxes with letter-spacing set nowhere removes N-1 of the
letter-spacing gaps a real text run would have.

Root cause proof (direct DOM construction test against the live
ora-ventures.com hero, letter-spacing -1.911px, word "stalls"):
- single span text node, letter-spacing applied: 232.19px
- buildCharLayer pre-fix construction (no ls anywhere): 245.20px
- letter-spacing set on the LAYER WRAPPER (the fix): 233.75px

233.75 vs 232.19 is the SAME ~1.5px baseline inline-block overhead present
even at letter-spacing 0 (245.20 vs 243.66 = 1.54px) -- the fix closes the
letter-spacing gap exactly, leaving only pre-existing baseline noise.

This mismatch was between the width buildCharLayer ACTUALLY renders at and
the width ALL of the driver's own layout math (measureNatural, layoutLines,
positionWords) assumes via pretext's native letterSpacing option. The two
numbers only converged the instant cleanup swapped the DOM back to real
textContent -- producing a visible width snap at the end of every
transition, worse with more/longer changed words. Distinct from BUG-176
(BUG-176 fixed pretext's own canvas-measurement blindness to
letter-spacing; this bug is pretext's fix never reaching the rendered
char-layer DOM).

*** Fix

buildCharLayer now takes a third parameter letterSpacingPx and applies
layer.style.letterSpacing on the LAYER WRAPPER (not each character span)
when non-zero. All 4 call sites (single-line path enter/exit words, reflow
path add/remove words) thread the driver's letterSpacingPx local through.

** Bug B -- containerWidth classifies wrap-eligibility by the element's OWN display, missing ancestor-constrained inline elements

The prior containerWidth fix used: containerWidth = elIsBlockLevel ?
clientWidth : Infinity -- reasoning an auto-width inline-level element never
force-wraps ITSELF. True in isolation, but misses that the element can
still SIT inside an ancestor that constrains where its own line runs.
Exactly the ora-ventures.com hero's shape: .ora-hero__flap is inline-block,
but display:block siblings force it onto its own line inside an h1 whose
width IS constrained by .ora-hero__content's max-width (or viewport at
narrow widths). The flap genuinely wraps when narrow enough, but the
driver always computed containerWidth=Infinity for it, always designing a
single-line transition -- the instant cleanup ran, the browser's REAL
(already-wrapped) layout snapped into view.

*** Root cause proof

Live CDP/puppeteer, .ora-hero__content constrained to 340px:
1. Ground truth: forcing display:block; white-space:normal directly on the
   flap -> clientWidth 340, real height 300.9375 (3 wrapped lines).
2. Driver's actual computed containerWidth pre-fix for this element:
   Infinity (inline-block, not in the block-level set).
3. Live rAF sampling across 12 real transition cycles at this width
   (pre-fix): 12 discontinuous height jumps, each exactly +-100.3125px or
   +-200.625px within a single ~17-18ms frame -- an instant snap at
   transition start and the mirror snap at cleanup.

*** Fix

Replaced the display-type heuristic with a direct measurement of the real
constraining ancestor via a display/white-space toggle: force
display:block + white-space:normal on the element alone (at its actual DOM
position), read clientWidth, revert both inline styles immediately. The
ONE legitimate remaining Infinity case is the element's own RESTING
(author-set) white-space:nowrap -- an explicit opt-out of wrapping.
Verified this technique is a safe no-op for the already-correct
block-level case (synthetic 400px padded div: direct clientWidth 360px,
toggle-measured 360px, exact match).

currentWidth/targetWidth for an auto-width element were also updated: now
uses the widest LINE of the real (line-count-aware) layout instead of
measureNatural alone (which assumed exactly one unwrapped line).

*** Post-fix verification

Live CDP/puppeteer, same 340px-constrained container, same rAF sampling,
clean isolated capture across 12+ transitions (strict >8px discontinuity
threshold): 0 jumps (vs 12 pre-fix). All height changes during a
transition are smooth ~3-4px/frame eases. At normal (900px) desktop width
the fix is a correct no-op.

** Why "always split at rest" was rejected

Kerning (glyph-pair shaping between ADJACENT glyphs in one continuous
inline run) is structurally impossible to reproduce once graphemes are
split into separate `inline-block` boxes — confirmed empirically (`(canvas
font-kerning:none)` on both sides collapses the width delta to ~0, proving
the residual after the original BUG-178 fix was kerning loss, not leftover
letter-spacing). "Always split, even at rest" would make the site's actual
resting typography (site-wide, not just during a 400ms transition)
permanently un-kerned — a real, visible degradation on a 95px hero
headline (T/A/V/W/Y-class pairs) — while STILL not fully closing the gap,
since pretext's own layout math (`measureNatural`/`layoutLines`) computes
KERNED widths regardless. Also breaks text selection/copy semantics
(spaces become literal `\u00A0` per-char spans) and would need a shadow
real-text node for accessibility. Rejected; pursued a surgical fix
instead.

** Two additional defects found via the same live-CDP-first methodology

*** Defect 1 — exit layer's explicit `width` pinned it to the WRONG (kerned) value

`buildCharLayer`'s exit-layer (`exit.layer`, the single-line fast path's
absolutely-positioned OLD-word rendering) had `exit.layer.style.width =
measureNatural(oldWord, font, letterSpacingPx) + 'px'` — pinning its box
to pretext's KERNED measurement, while its actual rendered content
(char-split, un-kerned) is WIDER. This clipped the tail of the exit
layer's OWN text against the flap's clip-path for the animation's entire
duration, not just at the boundary — verified live: word pairs like
"AVAV"/"WAWA" lose 8-16px to kerning; a real transition on the hero
showed a fully-opaque "L" character clipped 114px past the flap's
boundary.

Root cause of the pin itself: `exit.layer` is already `display:inline-
block` + `position:absolute`, so it ALREADY shrink-wraps to its own
rendered content width — the explicit `width` was both unnecessary AND
wrong. Fix: removed the explicit width entirely; the layer now correctly
auto-sizes to its real (un-kerned) rendered width.

*** Defect 2 — word-container box ignores its absolutely-positioned exit layer's width entirely

Separate, more severe defect, pre-existing since the PLAN-072 rewrite
(confirmed via an isolated worktree build at commit 5ee30f3b, BEFORE any
of this session's BUG-178 changes — same magnitude of overflow reproduced
there). Each word-container (`wc`) is `display:inline-block`; its own box
width comes ONLY from its in-flow child (the enter layer). The exit layer
is `position:absolute` specifically so enter/exit can cross-fade in place
without pushing layout — but that also means it does NOT contribute to
`wc`'s box width AT ALL. When a word shrinks or a word is removed
outright (e.g. cycling "misses the P&L." [3 words] → "never ships." [2
words]), the enter layer is narrow/empty while the exit layer still
paints the FULL old word — with nothing reserving space for it. Verified
live: the third word-container's exit layer ("P&L") painted 114px past
the flap's clip-path boundary, fully opaque, genuinely clipped (not
animation-in-flight noise — confirmed via `opacity` check ≥0.3 and cross-
checked against a pre-fix isolated worktree build).

Two fix attempts:
1. REJECTED: `minWidth` reservation on each `wc` (set to
   `Math.max(exitLayerWidth, enterLayerWidth)` read via
   `getBoundingClientRect()` right after DOM attach). Live-verified WRONG:
   the outer box (`%&el`) legitimately eases its own width via WAAPI from
   `currentWidth` toward `targetWidth`; forcing the wrapper's rendered
   content to stay at its full original width fights that shrink — the
   visible clipped-overflow gap GREW monotonically as the box narrowed
   (measured 3.6px → 168px within a single transition, worse than before
   the "fix").
2. ADOPTED: widen the clip-path pad to the REAL measured overflow instead
   of reserving space. `position:absolute` elements don't contribute to
   ANY ancestor's `getBoundingClientRect()` (not `wc`'s, not `wrapper`'s),
   so the true painted extent is read from the LEAF (grapheme) spans
   directly — the widest left/right excursion across all of them relative
   to `wrapper`'s own left edge — then used to grow the flap's
   `clipPath` horizontal inset beyond the baseline `overflowPad`, compared
   against the NARROWER of `currentWidth`/`targetWidth` (the WAAPI tween's
   worst-case endpoint). This lets the box keep tweening on its correct
   (kerned) width trajectory while ensuring nothing paintable is ever
   clipped.
