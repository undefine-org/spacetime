* Root cause (traced)
The failure is in the CST parser, BEFORE macro/form matching:

1. The template header's arg list is parsed by
   =src/syntax/cst/parser.rs::Parser.parse_arg_list= → =parse_arg= → =parse_arg_value=.
2. For =&b?=: =parse_arg_value= hits =SyntaxKind::AMPERSAND= → =parse_element_ref=,
   which consumes =&b= and RETURNS — it has NO modifier handling.
3. Control returns to =parse_arg_value='s postfix loop, which sees
   =SyntaxKind::QUESTION= and unconditionally takes the TERNARY branch:
   bump =?= → =parse_arg_value= (matches nothing before =)=) →
   =expect(SyntaxKind::COLON)= → "expected COLON, found R_PAREN".

Why =$a?= works: =parse_arg_value='s DOLLAR branch calls
=src/syntax/cst/parser.rs::Parser.parse_variable_ref=, which ALREADY consumes a
trailing =?=/=*=/=+= modifier itself (the "Handle modifier: $name:type?" block,
~L1861) — so the QUESTION never reaches the ternary branch. The element-ref
path lacks the symmetric handling. Asymmetry between the two param kinds is
the bug; the grammar layer (=stdlib/capture-types/param_list.st::optmark=,
=( $binding:binding | $element:element ) $collection:collmark? $ptype:typeref? $optional:optmark?=)
is already correct and never gets the chance to run.

* Structural fix (chosen)
Mirror the modifier handling into the element-ref path so =$name= and =&name=
params are symmetric at the CST level — one meaning for =?= in param position,
same consumption point for both sigils:

- =src/syntax/cst/parser.rs::Parser.parse_element_ref=: after the name/property-path
  loop, consume an optional =QUESTION= / =STAR= / =PLUS= modifier token exactly like
  =parse_variable_ref= does (same token kinds, same position — before =finish_node=).
  This is the precedent-following fix: =parse_variable_ref= established that the
  modifier belongs to the ref node.
- No reifier change expected: =stdlib/capture-types/param_list.st= already matches
  =optmark?= after an element param; verify the param record reaches
  =stdlib/primitives/template.st='s factory with ={ kind: "element", optional: true }=
  (the runtime already treats a missing optional &param as =null= per the
  documented contract in =stdlib/macros/template.st=).

Risk check (do this, don't skip): =parse_element_ref= is called from expression
positions too (=src/syntax/cst/parser.rs= call sites ~L824, L956, L1263, L1597,
L3284). A genuine ternary with an element-ref condition (=&el ? a : b=) would
change meaning — grep the repo + tests for that shape first; it is not a
documented author surface (conditions on refs are written =@if(&footer)=), and
=parse_variable_ref= already imposes the same greediness on =$x ?=, so symmetry
argues the ternary-on-bare-ref shape was never parseable consistently anyway.
If a test depends on it, scope the modifier consumption to arg-list context via
a parser flag instead (fallback plan, less elegant).
