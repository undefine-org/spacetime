#+TITLE: The function-call validator has never run on a real file
#+STATE: DONE
#+PRIORITY: #B
#+CUSTOM_ID: BUG-367-function-call-validator-never-runs

* Summary

`src/validator/functions.rs::validate_function_calls` walks `ast.presets` and
nothing else. Measured this session: `ast.presets` is EMPTY for every `.st` file
in the corpus, including files that plainly contain `@preset` blocks. So the
arity check, the unknown-function check and the "did you mean?" suggestions have
never fired on any real source.

* Measurement (tests/probe_val.rs, since deleted)

  files containing @preset/@easing/@animation text : 4+ (examples, stdlib)
  of those, parsed ok                              : 4
  TOTAL PresetDef produced                          : 0

Verbatim from the corpus, `examples/data-binding/styles.st:226`:

    @preset quick-reveal {
        opacity: 0 -> 1;
        translate-y: 40px -> 0;
        duration: 600ms;
        easing: --ease-out;
    }

`spacetime::parse` on that whole file yields `presets=0`, `diags=0`.

* Where it breaks

`src/parser/mod.rs:1199` routes `"preset" | "easing" | "scroll" | "animation"`
to `convert_cst_directive_to_preset`, and pushes only when it returns `Some`.
The function returns `None` here \u2014 that is the thing to find. Candidates, in the
order worth checking:

  1. `directive.body()` is `None` for a `@preset` with a `{ ... }` block, so the
     `PresetValue::AnimationBlock` arm at `src/parser/mod.rs:4081` is never
     reached (the CST may hang the body elsewhere for this directive shape).
  2. `name.is_empty()` returns `None` early (`:4061`) because the name is being
     read from a part of the directive that is empty for this spelling.
  3. Presets are consumed by the METASYSTEM instead (`%preset` in the registry,
     `src/metasystem/registry.rs:183` holds a separate `presets` map) and the
     parser-level `PresetDef` is vestigial \u2014 in which case the answer is to
     DELETE `src/validator/functions.rs` rather than fix it.

Determine which before writing any code. If (3), this is not a bug but a
deletion, and the arity/name checks should either move to the live surface or go
away with it.

* Why it matters

Beyond the dead checks: it is the reason FEAT-109 W4 (argument TYPE checking)
cannot land where it was planned. Type-checking arguments inside a validator
that never runs would produce a gate incapable of failing \u2014 exactly the
BUG-252 trap. Type checking must attach to whatever surface actually carries
function calls today.

    let src = std::fs::read_to_string("examples/data-binding/styles.st").unwrap();
    let ast = spacetime::parse(&src).unwrap();
    assert_eq!(ast.presets.len(), 0);   // passes today; should be 2

* 2026-08-11 — RESOLVED. It was candidate (3), and worse.

** Which candidate it was

Candidate (3): the parser-level `PresetDef` is vestigial. `@preset` is RETIRED
(SIP-001c / BUG-263) and the retirement is COMPLETE — measured, every spelling
produces nothing:

    tilde (RETIRED)  @preset easing ~smooth: ...     -> PARSE ERROR (correct)
    amp inline       @preset duration &quick: 200ms; -> presets=0 diags=0
    amp block        @preset animation &fade { ... } -> presets=0 diags=0
    bare block       @preset quick-reveal { ... }    -> presets=0 diags=0
    scroll amp       @preset scroll &through: (...)  -> presets=0 diags=0
    examples/data-binding/styles.st (2 @preset blocks) -> presets=0 diags=0

So the answer was DELETE, exactly as the item predicted. The named work is now
`@form style --name` + `--name;` splices, which DOES validate: an undeclared
splice is E0947, verified live through the CLI.

** The worse finding, which the item did not predict

`src/validator/functions.rs` matched on `Value::FunctionCall(name, args)`.
Measured: **`Value::FunctionCall` is NEVER CONSTRUCTED ANYWHERE in the
codebase** — four mentions total, all of them the enum declaration or a
`match` arm. So the walk was dead TWICE: an always-empty list, iterated for a
variant nothing ever builds. Even had `ast.presets` been populated, not one
check could have fired.

Third layer, and this one was mine: FEAT-109 W4's `check_param_types` in
`src/metasystem/validate.rs` had NO CALLER outside its own unit test — the
exact defect this bug is about, reproduced by the fix for it. A gate that calls
the checker directly cannot tell "checks correctly" from "checks correctly and
never runs".

Fourth: `src/metasystem/validate.rs::validate_scope_form_matches` is also
uncalled (only re-exported). Left in place — out of scope here, noted for
whoever touches that module next.

** And the registry was stale where it overlapped stdlib

Every one of the 5 functions declared in BOTH `src/functions/builtins.rs` and a
stdlib `%primitive` DISAGREED about its own arity:

    noise      RUST 2..2  STDLIB 0..2   parallax  RUST 1..2  STDLIB 0..2
    random     RUST 2..2  STDLIB 0..3   wave      RUST 1..4  STDLIB 0..4

The remaining 6 (`rgb`, `rgba`, `hsl`, `hsla`, `oklch`, `oklcha`, `velocity`)
have no `%primitive` at all — they are CSS colour functions, and the GRAMMAR
already owns them (FEAT-109 W1 taught `color_fn_name` about `color-mix`,
`light-dark`, `device-cmyk` there). A second Rust spelling of a stdlib
declaration is the hand-synced-list defect this arc exists to delete.
