* Symptom (observed, W2.5 of PLAN-037)
`@data fetch $proposal : "data.json";` in stdlib/__mcp__/picker.st compiles fine
under `build` but FAILS under `cargo run -- check`: a relative fetch URL does not
resolve to a static File source, so the dispatch layer errors:

    server.rs:4478  "@data fetch URL must resolve to a File source; got {:?}"

The picker only works today because it is served via `build`, not `check`. Any
.st FUNCTION the MCP loads that fetches a runtime contract (data.json) hits this.

* Root cause (verified)
src/server.rs:4478 — the `@data fetch` validation insists the URL resolve to an
on-disk File at check-time. A RELATIVE URL ("data.json", "/api/x") is a legitimate
RUNTIME endpoint, not a build-time file. check-mode conflates "static asset" with
"runtime data source". `build` skips this resolution, which is why it passes there.

* Expected
A relative/absolute URL string is a valid runtime data source under BOTH `check`
and `build`. check should validate the SHAPE (it is a url-typed value), not require
the endpoint to exist on disk. Only an explicit file: or workspace-relative ASSET
import should require on-disk resolution.

* Fix sketch (confirm before editing)
In the `@data fetch` resolution (server.rs ~4478 + dispatch in main.rs:96 region):
distinguish "asset reference" (must resolve to File) from "runtime endpoint"
(url string → pass shape-check, no disk hit). A leading scheme/`/`/`./` + .json|
api-ish path → runtime endpoint. Mirror how `build` already tolerates it.

* Verification

- After fix: same page passes `check`; `build` unchanged; picker.st passes both.
- Regression: a genuine bad asset import (`@data fetch $x : "./missing.st"`) still
  errors (don't loosen asset resolution).
