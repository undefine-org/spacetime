* Symptom
A top-level `@`-directive the compiler does not recognize (a typo, a wrong
construct name, or a misremembered API like `@style { ... }`) compiles CLEANLY
with NO error or warning. Its body is swallowed (leaks into page HTML as inert
text or is dropped), so the author silently loses the construct.

Reproduction (`cargo run -- check`):
  @template &card($title) { <div>`$title`</div> }
  @bogusdirective { foo: bar; }
-> `✓ All 1 file(s) passed` (no diagnostic for @bogusdirective).

Real-world trigger that surfaced this (2026-06-21, MCP builder showcase): a guest
authored CSS as `@style { .c { color: … } }` (NOT a Spacetime construct — real
Spacetime uses BARE top-level selectors `.c { … }`). The `@style` block was
swallowed: `compile_to_bundle(...).css` came back EMPTY (0 bytes) while bare
`.c { … }` yields the css correctly. The author sees an unstyled page with zero
indication that `@style` is wrong. (This was misdiagnosed as a region-compose
"finding D — dropped @style"; the real cause is the silent swallow.)

* Why it matters (DX)
- A typo'd or misremembered directive name vanishes with no feedback — the
  opposite of the metasystem's "self-describing" intent (AGENTS).
- The compiler HAS the registry to know which `@`-names are defined (macros +
  primitives + built-ins); an unknown one is detectable.
- Pairs with W0712 (BUG-130) which warns on a DIFFERENT silent-swallow
  (inline @each in template markup) — same class of bug, same fix shape.

* Root cause (to verify during fix)
The parser treats an unknown `@name { … }` as opaque/file-scope content rather
than checking the name against the macro/primitive/built-in registry. Likely in
the directive/scope parse path (src/parser/mod.rs) where a `@`-led block with no
matching registered form falls through to HTML/opaque handling.

* Fix direction
1. At parse/expansion, when a top-level `@ident` block matches NO registered
   macro/primitive/built-in directive, emit a WARNING diagnostic (new W-code,
   e.g. W0713) naming the unknown directive + a hint ("not a known directive;
   did you mean bare CSS `.sel { }` / a defined macro?"). Mirror W0712's shape
   (src/diagnostics/codes.rs + the emit site).
2. Keep it a WARNING (not error): forward-compat with directives defined later
   in stdlib; a hard error could break valid-but-late-resolved forms. Verify
   against the registry AFTER stdlib load so a real stdlib directive isn't
   flagged.
3. Tests: fires on `@bogusdirective {…}`; SILENT for every real directive
   (@template, @style IF we decide to define it, @data, @each in valid position,
   @import, …). No false positives on examples/ + demos/ + stdlib/.

* Open question
Should `@style { }` actually BE defined (a real construct that routes its body to
`compiled.css`)? Many authors will reach for it by analogy to other frameworks.
Two options: (a) define `@style` as a stdlib macro that emits its body as CSS
(ergonomic, one construct), or (b) keep bare top-level CSS as the one true way
and let W0713 redirect `@style` users. Decision belongs with the owner (harmony:
one need = one impl). Filing as part of this bug's resolution.
