* Findings (each reproduced, see repro)

** F1 \u2014 @assert swaps condition and message (capture defect)
=@assert $condition:expr $message:string? = \"\"= (stdlib/testing/test.st:959-973).
Input =@assert (false) \"MYMSG\"= captures:
- =condition = Expr(\"\\\"MYMSG\\\"\")=  \u2190 the MESSAGE string
- =message  = String(\"\")=           \u2190 empty
So emitted JS is =const __cond = \"MYMSG\"; if (!__cond) throw\u2026= \u2014 a truthy string,
never throws. The =:expr= capture skips the parenthesized =(false)= and grabs the
trailing string. Same FAMILY as BUG-052 / BUG-047 (greedy inline value capture).
Repro:
#+BEGIN_SRC
.x { @assert (false) "MYMSG" }   // -> cond=Expr("\"MYMSG\""), message=String("")
#+END_SRC

** F2 \u2014 @then / @eval / @wait / @mock unmatchable in isolation
When a block body is compiled in isolation (PLAN-026 nested compile), these forms
produce ZERO matches even after registering all 23 testing macros into the
augmented SyntaxRegistry:
- =@then .foo should exist=        -> 0 matches
- =@eval (window.y = 1)=           -> 0 matches
- =@assert (false)=                -> 0 matches too when bare? (matched in body, see note)
Whereas a normal stdlib macro (=@reveal(split:\"chars\")=) DOES match against the
same registry. So =RegisteredForm::new= / =extract_prefix= / form-compilation
rejects or mis-keys these testing forms. Confirmed: =STDLIB_REGISTRY= (parse-time
SyntaxRegistry, 312 forms) does NOT contain the testing macros at all \u2014 they live
only in the test_runner's PREPENDED source. They register (form_count 312->335)
but still don't match. Suspect: their =%form= shapes (e.g. =@then $target:selector
should $assertion:ident $expected:expr?= with the bare keyword =should=, and
=@eval $expr:expr= with only a parenthesized expr) hit a gap in the events
form-matcher or prefix indexing.

** F3 \u2014 testing macros absent from the parse-time registry by design
=stdlib/testing= IS loaded into the expand-time MetaRegistry (compiler.rs:92) but
NOT into the parse-time =STDLIB_REGISTRY= (src/syntax/stdlib_registry.rs). The
test_runner works around this by PREPENDING stdlib/testing/test.st as source so
the outer parse sees the =%macro= defs and rematches. The PLAN-026 nested compile
adds =parser::rematch_with_registry= to re-derive matches from the live registry;
F2 shows that rematch path does not match @then/@eval even though it matches
@assert. Decide: either (a) include stdlib/testing in the parse-time registry, or
(b) fix the form-matcher so these forms register+match via rematch.

* Why the negative gate still fails (the acceptance for "assertions gate")
Because of F1+F2, NONE of @assert / @then currently emit a throwing check in a way
that fires. A test with =@assert (1===2)= or =@then .missing should exist= still
reports passed. The gate is: such a test MUST report FAILED.

* Fix plan (suggested order)
1. F2/F3 first: make @then/@eval/@wait/@mock MATCH (audit RegisteredForm::new +
   extract_prefix for the =should= keyword form and bare-expr forms; or load
   stdlib/testing into the parse registry). Without matching, nothing else matters.
2. F1: fix @assert =$condition:expr $message:string?= so =(expr) "msg"= captures
   condition=(expr), message="msg". Likely the :expr extractor greediness; may
   share a fix with BUG-052.
3. Re-run the negative gate: =@assert (1===2)= and =@then .x should exist= (on a
   missing element) MUST fail.
4. AUDIT every existing .test.st: with assertions now live, triage real failures
   (genuine product bugs that were hidden) vs bad tests. This audit is part of the
   deliverable \u2014 expect some currently-"green" tests to fail for real.
