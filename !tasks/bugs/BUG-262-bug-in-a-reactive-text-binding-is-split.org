* Symptom

: Uncaught SyntaxError: missing ) in parenthetical   runtime.js:17039

Reported from `cargo run -- serve projects/backdesk-new --port 3335 --debug`.
The whole comments dev widget is dead on any page that serves it — a
SyntaxError at load means the entire bundle never evaluates.

* Reproduced

The failing bundle is `/__spacetime/comments/runtime.js` (17197 lines), NOT
the page runtime. The other four served bundles (`runtime.js`,
`dev/runtime.js`, `host/runtime.js`, `inspect/runtime.js`) all pass
`node --check`; this one fails:

: /tmp/cm.js:17039
:       try { __v = ((ST.resolve(__node, 'comError')); } catch (e) { return; }
:                                                    ^
: SyntaxError: Unexpected token ';'

Two opening parens, one closing. And the sibling line names the cause:

: if (typeof ST !== 'undefined' && ST.filter) __v = ST.filter("| $comLoadError)", __v);

The FILTER NAME is `"| $comLoadError)"` — a fragment of the author's
expression, with the closing paren swallowed into the string.

* Cause

`stdlib/comments/__dev__/pill.st:183`:

#+begin_src spacetime
.st-comments-widget__error {
  .is-hidden: ($comError == "" && $comLoadError == "");
  text <- ($comError || $comLoadError);
}
#+end_src

The reactive-text emitter splits the expression on `|` to find a filter
pipe (`value | filter`), but `||` is the LOGICAL OR operator. It splits
between the two pipe characters, so:

- the value becomes `($comError ` — unbalanced, hence the `((` line
- the filter becomes `| $comLoadError)` — carrying the real closing paren

`src/emit/html_reactive.rs` around lines 790/831/836 is where `__v` and the
`ST.filter` call are formatted.

* Fix

The pipe split must not match `||`. A `|` immediately preceded or followed by
another `|` is an operator, never a filter separator. Same for a `|` inside a
string literal or inside parens/brackets — the split should be at DEPTH ZERO
only, which is the general form of the bug (`(a | b)` inside a call would break
identically today).

* Gate

A `--cdp` test whose page contains `text <- ($a || $b);` and asserts the
element renders — plus the NEGATIVE that makes it meaningful: the emitted
bundle must pass a JS parse. A bundle-level `node --check` (or the equivalent
in-process parse) over the served runtime would have caught this at build,
which is the more valuable gate: an emitted SyntaxError is silent at compile
and total at runtime.

That gate generalizes past this bug — it is the same class as FEAT-170 (a
primitive emit-block parse error being dropped rather than failing the build).
