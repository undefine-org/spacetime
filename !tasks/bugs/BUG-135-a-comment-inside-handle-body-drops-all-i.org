* Symptom
Placing a `/* … */` (or `//`) comment ANYWHERE inside a `@handle $sig { … }`
body causes the ENTIRE handle to emit with empty clauses:
=optimisticStmts = ""=, =handleArms = null=, =finalStmts = ""=. The handler
silently does nothing (no optimistic apply, no receive dispatch, no final).

Discovered wiring demos/liveview-kanban: a descriptive comment above the
=optimistic {= clause (still inside the =@handle { }= braces) made drag-and-drop
a no-op. Removing the comment fixed it.

* Repro (minimal)
#+begin_src
@handle $move {
  /* this comment breaks everything below */
  optimistic { $cards.update($card, { col: $to }); }
  receive { Moved(c) => { ... } }
  final { $dragging <- null; }
}
#+end_src
=> optimisticStmts/handleArms/finalStmts all empty. Remove the comment => all
three capture correctly.

NB: a comment in a *bare-statement* body (e.g. inside `optimistic { }` itself in
some isolated cases) behaved inconsistently — the demo's multi-line comment INSIDE
the optimistic block ALSO broke it, while a single-line comment in a trivial
isolated file did not. The reliable rule today: keep `@handle` bodies
comment-free; put explanation ABOVE the `@handle` line.

* Likely cause (to confirm)
The `@handle` form is captured by the handle_optimistic / handle_receive /
handle_final %capture_types (stdlib/capture-types/handle-block.st), each using
=balanced('}')=. The clause-group merge in the form matcher likely does not skip
comment trivia between/within clauses, so a comment token desyncs the
=( $optimistic:handle_optimistic )? ( $receive:handle_receive )? ( $final:handle_final )?=
sequence and every optional group fails to match -> all clauses default empty.
The matcher should treat comments as trivia inside a `@handle` body (parity with
how comments are ignored elsewhere in directive bodies).

* Where
- src/syntax/ form matcher for capture-type clause groups (the merge that lifts
  $optimistic/$receive/$final), and/or the lexer trivia handling feeding it.
- stdlib/capture-types/handle-block.st (the three %capture_types).

* Root cause (CONFIRMED)
Capture-type EXTRACTORS skip only =SyntaxKind::WHITESPACE= in their leading-skip
loops, NOT =COMMENT= — even though both are trivia (=SyntaxKind::is_trivia()=
covers =WHITESPACE | COMMENT=). The =@handle= body is matched as three optional
clause GROUPS =( $optimistic )? ( $receive )? ( $final )?= via
=match_body_groups= (src/syntax/events/form_compiler.rs), each compiled to a
=compile_pattern_with_defs= extractor over the body token slice.

A leading =/* … */= (or =//=) emits a =COMMENT= token at index 0. The
=LiteralExtractor("optimistic")= leading-skip loop only steps past =WHITESPACE=,
so it sees the =COMMENT= first, fails to match, the =OptionalExtractor= returns
=consumed=0=, and =match_body_groups='s cursor never advances. Every subsequent
clause group then re-starts on that same comment and likewise yields empty →
=optimisticStmts=""=, =handleArms=null=, =finalStmts=""=. The handler silently
no-ops.

Verified by emit-diff (compile() JS): with the comment the markers `col:`
(1→0), `dragging` (2→1), `Moved` (2→1) all drop.

* Fix
Make the extractor leading-skip loops trivia-aware: replace the six
=token.kind == SyntaxKind::WHITESPACE= leading-skip checks in
src/syntax/events/extractors/custom.rs with =token.kind.is_trivia()= (covers
=WHITESPACE | COMMENT=). One sigil, one meaning: a comment is trivia EVERYWHERE,
including between/within capture-type clause groups. No new mechanism; reuses the
existing =is_trivia()= predicate already used in form_compiler's cursor.

Sites fixed (custom.rs): BalancedExtractor, SkipBlockExtractor, LiteralExtractor
(leading + multi-token-literal interior guard), CharClassExtractor,
SequenceExtractor (inter-element skip), plus the one test helper.
