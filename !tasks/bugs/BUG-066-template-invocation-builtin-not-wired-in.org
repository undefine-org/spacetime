* Symptom
A `%capture_type` grammar referencing the builtin `template_invocation` leaf gets ExprExtractor
(raw `&name(args)` string), NOT TemplateInvocationExtractor (structured Named{name,args}). So
`$invocations:template_invocation` in a capture-type yields Expr("&signal-card($sig)") instead of
Named{name,args}, and `( $x:template_invocation )*` stops after the first (Expr swallows to its
boundary).

* Root cause
compile_pattern_with_defs -> compile_simple_extractor (src/syntax/events/extractors/custom.rs
~428) match on CaptureType has NO arm for TemplateInvocation (also likely PatternMatch/Union/
ParamList/Properties etc.) -> falls to `_ => ExprExtractor`. The registry HAS the extractor
(extractors/mod.rs:98) but this hand-written match doesn't dispatch to it. Macros work because
%form patterns use the full parser path (src/parser/mod.rs), a different code path.

* Fix (structural)
Dispatch the builtin extractors that exist in the ExtractorRegistry from compile_simple_extractor
instead of a hardcoded partial match: add the TemplateInvocation arm (and audit the other
registry-backed builtins) so the %capture_type engine and the macro %form path agree on builtin
leaf semantics. Found building cb_nested_each (FUP-038).

* Test
A %capture_type with $x:template_invocation reifies Named{name,args}; ( $x:template_invocation )*
collects all invocations.
