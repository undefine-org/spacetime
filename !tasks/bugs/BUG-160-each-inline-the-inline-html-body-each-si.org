* Found via
Round-2 pressure test (post FEAT-151/BUG-155 fix wave) — deliberately probed
`each-inline.st` (stdlib/primitives/data/each-inline.st), the inline-HTML-body
sibling of `each-with-templates` (backs `@each($x as $i) { <li>raw html</li> }`,
as opposed to `@each($x as $i) { &template($i); }`). BUG-155's fix only
touched `each-with-templates` — this is a SEPARATE primitive file that never
got the fix, and reproduces the identical failure class.

* Repro (isolated, confirmed RED on the pre-fix code, GREEN after)
#+begin_src
<div data-st-instance>
  <ul class="inline-each"></ul>
</div>
@data inline $wrap : { "items": ["x", "y"] };
.inline-each {
  @each($wrap.items as $item) {
    <li>`$item`</li>
  }
}
#+end_src
Rendered EMPTY (`.inline-each` innerHTML = `""`) before the fix; renders
`<li>x</li><li>y</li>` after.

* Root cause (same shape as BUG-155, traced independently)
`each-inline`'s reactive channels + initial-paint lookup were ALL keyed by
the literal `sourceName` string (`"wrap.items"`), never split into head +
path:
- `document.addEventListener(\`data:${sourceName}:loaded\`, ...)` — never
  fires (ST.setData registers under the HEAD name only).
- `document.addEventListener(\`local:${sourceName}:updated\`, ...)` — same.
- `window.SpacetimeLocal[sourceName]` (initial paint) — a dotted string is
  never a real property key on SpacetimeLocal.

* Fix (mirrors each-with-templates' BUG-155 fix exactly)
`stdlib/primitives/data/each-inline.st`: derive `headName =
sourceName.split('.')[0]`, `isDotted = sourceName !== headName`; key both
event-channel subscriptions off `headName`; add a `resolveSourceData()`
helper trying, in order: `ST.resolvePath(containerEl, sourceName)` (scoped
resolve + dotted walk), then the `ST._dataRegistry` fallback (also walking
the dotted path from the HEAD entry), then `window.SpacetimeLocal[headName]`
walked the same way. For a plain (non-dotted) source, channel payloads
(`e.detail`) are still trusted DIRECTLY (unchanged behavior, no regression
risk) — only a dotted source re-derives via `resolveSourceData()`.
