* Summary

A file-scope signal declared with an OBJECT literal does not parse:

#+begin_src spacetime
$u object: { name: "Ada" };
#+end_src

#+begin_example
error[E0946]: directive does not match its declared grammar:
             Expected capture `$value:Expr` but no tokens remaining
#+end_example

The sibling collection type parses fine, which is what makes this a bug and
not an unimplemented feature:

| decl                        | result |
|-----------------------------+--------|
| ~$n number: 3;~             | ✓      |
| ~$a array: [1, 2];~         | ✓      |
| ~$u object: { name: "A" };~ | E0946  |
| ~$u object: {name:"A"};~    | E0946  |

So the `expr` capture consumes a bracketed `[...]` run but stops at the
opening `{` of a brace run, leaving "no tokens remaining" for `$value`.

** Where it is NOT

Ruled out by reading the code, so the next person does not re-walk these:

- NOT `ExprExtractor` (=src/syntax/events/extractors/simple.rs:486=). It tracks
  `L_BRACE`/`R_BRACE` depth correctly and only breaks on a boundary token at
  depth 0. Given the tokens it would handle `{ name: "Ada" }` fine.
- NOT the `%form` in =stdlib/syntax/local-state.st:92=. The earlier suspicion
  that `$value:expr` should be `$value:balanced(';')` was TESTED with a full
  rebuild and had NO effect \u2014 recorded previously, restated here because the
  original report still reads as if it were the lead.
- NOT the type NAME. `object` and a user type `Foo` fail identically, so no
  keyword/registry lookup is involved.

** Where it IS

=src/syntax/cst/parser.rs::parse_variable_decl= (:2274). It bumps an optional
type by taking a SECOND bare `IDENT`:

: // Name
: if self.at(SyntaxKind::IDENT) { self.bump(); }
: // Optional type
: if self.at(SyntaxKind::IDENT) { self.bump(); }
: // : value
: if self.at(SyntaxKind::COLON) { self.bump(); self.parse_arg_value(); }

`parse_arg_value` DOES dispatch `L_BRACE` to `parse_object_or_body` (:1615), so
the object path exists. The failure is therefore in how the typed variant hands
its value span onward \u2014 the form matcher then reports
"Expected capture `$value:Expr` but no tokens remaining", i.e. it received an
empty token run for the value.

`inspect --layer parse` shows ZERO ast nodes for the failing file, so the whole
declaration is being discarded before form matching, not mis-captured after it.

Next step: instrument `parse_object_or_body` for the typed case \u2014 it likely
treats the `{` as a BODY (a scope block) rather than an object literal when a
type was consumed, since that is the one branch the untyped case never takes.
