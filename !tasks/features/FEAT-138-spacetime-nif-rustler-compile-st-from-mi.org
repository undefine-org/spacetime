* AMENDED 2026-07-24 — AGPL pivot: NO NIF. CLI-native, arms-length subprocess.
Spacetime is going **AGPL**. A Rustler NIF links the AGPL compiler *into the
BEAM VM* of the user's Phoenix app — a combined/derivative work that would push
AGPL onto the whole host application. We refuse that footgun.

The integration MUST treat the compiler as a **separate program** invoked at
arm's length (OS subprocess / Erlang port), exactly like Phoenix already shells
out to `esbuild` and `tailwind`. "Mere aggregation": the app EXECUTES the
`spacetime` binary, it does not LINK it. No derivative-work question; AGPL stays
contained to the compiler binary.

** Consequence — the goal is unchanged, the mechanism changes
Everything FEAT-138 promised (mix-driven build, auto-stage, dev hot-reload) is
still in scope. It is now delivered through **the CLI's own surface + a thin
Elixir mix compiler that spawns it** — never a NIF. Any capability the NIF would
have given us that the CLI cannot yet express becomes a *CLI feature request*,
not a reason to reach for a NIF.

** Revised scope (supersedes the original ~spacetime_nif~ crate scope)
- *CLI, verse side (new/confirmed subcommands):*
  - ~spacetime build <dir>~ already compiles a page dir → confirm it can take a
    project root and build EVERY page dir in one invocation (batch), emitting
    each ~<page>/{spacetime.js,spacetime.css}~ + the skeleton artefact (FUP-121).
  - ~spacetime build --watch~ (or reuse ~serve --dev~'s watcher): on ~.st~ save,
    recompile the affected page and print a machine-readable line
    (e.g. JSON on stdout: ~{"event":"built","page":"board","js":"…","css":"…"}~)
    so an external supervisor (mix / phx reloader) can react. This is the
    hot-reload signal WITHOUT a NIF or an in-VM callback.
  - Exit codes + structured diagnostics on stdout (JSON) so the mix compiler can
    surface ~.st~ errors as mix compile errors.
- *Elixir, spacetime_lv side:*
  - A ~Mix.Task.Compiler~ (`:spacetime` in the `:compilers` chain) that runs the
    ~spacetime~ binary as a ~System.cmd/Port~ over the app's page dirs, stages
    output into ~priv/static~, and maps structured diagnostics → mix errors.
    Mirror `Mix.Tasks.Compile.Esbuild`/`Tailwind` — the canonical arms-length
    pattern already blessed in the Phoenix ecosystem.
  - Dev hot-reload: run ~spacetime build --watch~ under the app's supervision
    tree (a `Port` in a `GenServer`, dev-only), and on each ~{"event":"built"}~
    line trigger a live bundle push (host-composition hot-swap) over the socket.
    All coordination is Elixir-side messages; the compiler stays a black-box
    process.
  - Binary discovery: resolve `spacetime` from PATH / a configured path /
    `:os.find_executable`; document install (cargo install / released binary),
    same story as esbuild's auto-download. Do NOT vendor the source into deps.
- *Prod:* ~mix spacetime.build~ AOT stages bundles into the release; the release
  ships bundles only (no compiler binary, no NIF) — unchanged from the original.

** Licensing note (record for future agents)
The reason this is NOT a NIF is legal, not technical: AGPL §13 + the FSF's
position that a NIF/linked library forms a single combined work. Subprocess
invocation is the FSF-sanctioned boundary ("mere aggregation" / "at arm's
length"). If anyone proposes a NIF again for perf, the answer is: measure the
subprocess cost first; a persistent `spacetime` daemon/port (still arm's length)
recovers startup cost without crossing the linking boundary.
