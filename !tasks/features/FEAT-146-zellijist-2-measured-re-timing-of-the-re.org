* CORRECTION — the initial "DONE" was wrong; a real geometry bug slipped past review

User called it out directly: "the demo is very, very, very, very, very, very
wrong." Re-inspecting the actual render (not just the earlier screenshot
crops) confirmed it — the tile column rendered as TWO disconnected, staggered
zigzag ribbons with a visible gap down the middle, not the video's single
continuous interlocking strip. This is a materially different, worse result
than what was reported as verified.

** Root cause (found by direct position/geometry inspection, not guessing)

`lib/three-tile-field.st`'s world-Y placement:

#+begin_src js
const colY = colTop - (i * H + built.cy);   // WRONG
#+end_src

Each triangle's local vertices already have its own centroid (`cy`)
subtracted out (baked into the geometry data itself, so it can rotate/tilt
around its own center during LIFT/SCATTER). Placing the MESH at `colY` then
re-subtracts `cy` a second time. The X-axis formula does this correctly
(`colX = built.cx - W/2` — ADDS `cx` to a base offset), but Y did the opposite
sign. Since the two triangles sharing one rectangular cell have DIFFERENT
local centroids (`cy = H/3` for one, `2H/3` for the other), they landed at
DIFFERENT vertical offsets within the same row instead of sharing the row —
splitting the single zigzag column into two visually separate staggered
ribbons.

Fix: `colY = colTop - i * H + built.cy` (match the X-axis sign convention).

** Why this passed review the first time (a real process failure, not just a bug)

- The CDP test only asserts RELATIVE motion between a tile's own keyframes
  (flush/lift/scatter), never inter-tile adjacency/seam continuity — it can't
  catch "two triangles that should share an edge don't."
- The screenshot review compared crops at a low zoom / low scrutiny level and
  the STAGGERED-RIBBON look was surface-plausible (still zigzag-shaped,
  still cream, still shadowed) — it took a full-frame, uncropped, direct
  side-by-side against the actual video frame to see the column was
  structurally split, not merely "slightly different."
- Lesson: a screenshot comparison must inspect exact topology (do edges
  touch? is it ONE ribbon or two?), not just overall gestalt/color/mood.
  Filed as a general lesson, see memory `CON-verify-topology-not-gestalt`.

** Re-verification after the fix

* CORRECTION 3 — SCATTER was tilted, not flat

User report (verbatim, frustrated): "the final layout of the scatter tiles is
FLAT but SPACED. NOT FUCKING SCATTERED." Confirmed directly against the
source: the video's true final frame shows every tile lying perfectly
face-up, zero foreshortening, rotated ONLY in the ground plane (yaw) —
not tilted.

** Root cause

SCATTER's quaternion still carried pitch/roll (Euler X/Y up to +-0.22 rad,
~12.6°) inherited from adapting the LIFT tumble code — so landed tiles read
as still airborne/settling, not "landed flat." Z-position jitter
(`rr(-0.08, 0.35)`) also kept some tiles slightly raised, the other visual
tell of "not landed."

** Fix

Euler X/Y -> near-zero (`rr(-0.02, 0.02)`); only Z (yaw) varies
(`rr(-0.9, 0.9)`) — tiles rotate freely in-plane but never tilt. Z-position
jitter tightened to `rr(-0.02, 0.04)`.

** Test hardening (this is the more important fix)

The CDP test's prior "flatness" check (`quaternion.w > 0.90`) was WRONG in a
way that let this bug through the automated gate: `w` conflates yaw (a valid
in-plane rotation, fine per the video) with pitch/roll (the actual
"tilted-not-flat" bug) — a genuinely tilted tile with near-zero yaw could
still score `w` close to 1 and pass. Replaced with a direct check on the
pitch/roll components themselves (`|quat.x| < 0.08 && |quat.y| < 0.08`),
required for ALL tiles (`=== tileCount`), not merely a majority. This is the
real fix: a test that only checks "mostly flat" for "over half the tiles"
will pass a scene that's visibly wrong to a human. Re-verified: CDP passes
(1 passed, 19.6s) against the STRICTER assertion.

** Pattern across corrections 1-3

Three user-caught misses in a row (disconnected ribbons → off-frame scatter
→ tilted scatter) share a root cause: I trusted a numeric fix (position math,
frame-bound math, rotation math) without re-deriving the ground-truth

test's assertions were loose enough to pass a visibly-wrong scene. Every
