** What's blocked, and why (the actual finding)
The directive rail (`@each($mcpInput.steps as $step)`) — the CORRECT, most
idiomatic syntax for this data shape — silently renders nothing due to TWO
independent, precisely-isolated runtime bugs, not a design mistake on this
demo's part:
- BUG-155: `@each` with a dotted-path source (`$sig.field`) never resolves —
  `each-with-templates`'s `resolveSourceData()` calls `ST.resolve` (exact
  name match) instead of the ALREADY-EXISTING `ST.resolvePath` (which
  correctly handles this, confirmed live: `ST.resolve(el,'wrap.items')` ->
  undefined; `ST.resolvePath(el,'wrap.items')` -> the array).
- BUG-156: a `@data derive` off an `@mcp-input`-sourced signal only works if
  some UNRELATED markup elsewhere on the page happens to interpolate that
  same signal directly first (accidental `ST._bridgeExport` triggering) —
  confirmed by bisection: removing one unrelated `<p>` line broke an
  otherwise-untouched derive+each chain.
Both have surgical fixes identified (reusing EXISTING runtime functions —
`ST.resolvePath`, unconditional `ST._bridgeExport` from `@mcp-input`'s
`setSource`) — filed, not left vague.

Two 3D-module gaps (the ones explicitly asked about) also confirmed by full
source survey (grep across every stdlib/3d/primitives file, zero exceptions):
- FEAT-152: zero pointer-pick/raycast affordance anywhere in stdlib/3d — a
  rendered mesh cannot be clicked/hovered without hand-written page JS
  (forbidden by repo AGENTS.md). Elegant target: `@on click`/`@on hover`
  valid INSIDE an `@object(...)  { }` / `@gltf(...) { }` body — reuses the
  existing `@on` event vocabulary + the `$children*` slot `@object` already
  has, backed by ONE shared raycaster registered once per `@stage` against
  the already-populated `canvas._stObjects`.
- FEAT-153: every 3D primitive param is write-once at mount — confirmed
  `@gltf(src: $modelPath)` never reloads when `$modelPath` changes (isolated
  repro, compiles clean, silently static at runtime); zero
  `ST.watch`/`ST.watchScoped` calls anywhere in stdlib/3d/primitives.
  Elegant target: a generic `ctx.onParamChange(names[], rebuildFn)` added
  ONCE to three-stage.st's shared engine-boundary `ctx`, opted into per
  primitive (start with @gltf src + @object color/roughness/metalness).

Plus a small Blender-tooling papercut (BUG-157, #C) hit while building the
step scripts: `set_face_material` crashes on a stray empty material slot left
by a boolean union (non-fatal — export still succeeded).
