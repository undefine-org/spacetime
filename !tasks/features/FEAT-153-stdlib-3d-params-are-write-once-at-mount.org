captures its =%param= values as plain JS =const=s at init time
(=grep -c "%emit js"= = 1 per file; =grep "const .* = %"= shows e.g.
=three-object.st= line 87-88: =const cRGBA = %color.rgba;= as a one-shot

=stdlib/3d/primitives/*.st= — confirmed via direct grep, no exceptions.

* Repro (isolated, compiles clean, fails silently at runtime)
File: =scratch/repro-each-dotted/repro4-gltf-reactivity.st=
#+begin_src
@data inline $modelPath : "/models/a.glb";
<canvas class="stage">
  @stage {
    @light(type: "ambient", intensity: 1)
    @gltf(src: $modelPath, size: 2)
  }
</canvas>
<button class="swap">Swap model</button>
.swap { @on click { $modelPath <- "/models/b.glb"; } }
#+end_src
Compiles with NO diagnostic. Clicking "Swap model" changes =$modelPath='s
signal value but the loaded mesh never changes — =three-gltf.st='s
=%emit js= reads =const url = %src;= exactly once, at primitive init, and
the =loader.load(url, ...)= call only ever fires that one time.

* Root cause
This is systemic, not a =@gltf=-specific bug: EVERY 3D primitive's =%emit js=
block treats its params as compile-time constants baked into the closure at
mount. There is no reactive re-run path at all in this primitive family —
contrast with the rest of the stdlib (=derived-signal.st=,
=each-with-templates=, the animation drivers) which ALL wire
=document.addEventListener('local:<dep>:updated', ...)= or
=ST.watchScoped(...)= to re-fire when a referenced signal changes. The 3D
primitives were built assuming "3D scenes are set up once at page load," which
was true for the demo gallery (=demos/3d/*=) but breaks the moment a 3D scene
needs to reflect application STATE (a forge pipeline, a product configurator,
a data-driven visualization) — exactly the class of use case an "agent-driven
3D control surface" needs.

* Elegant target design
** Don't retrofit reactivity into every primitive ad hoc — add ONE mechanism at the @stage boundary
=three-stage.st= already IS the acknowledged single "engine boundary" (its own
doc comment: "the ONE place three.js is touched directly per page; children
compose against the handle"). The fix belongs there, generalized, not
per-primitive:
- Every child primitive ALREADY declares its params via the normal
  =%primitive foo(&el, src: string = "", ...)= signature — the METASYSTEM
  already knows which of a primitive's args are signal-backed (bound to a
  =$x=) vs literal, because that's exactly what =%binds= / the compiler's
  param-binding resolution does for every OTHER primitive family already.
- Add a thin, GENERIC re-invocation contract: a 3D primitive that wants
  reactive params opts in by wrapping its body-build logic in a named inner
  function and registering it via the shared =ctx= (=canvas._stThree=) as
  =ctx.onParamChange(paramNames[], rebuildFn)= — implemented ONCE in
  =three-stage.st= using the EXISTING =ST.watchScoped= (already proven
  correct for exactly this: watch a signal in scope, re-fire on change) over
  each named dependency, calling =rebuildFn(newValues)= which disposes the
  old THREE object(s) and re-creates them (same dispose/rebuild pattern
  every primitive's own =%cleanup= already implements for unmount — REUSE the
  disposal code path, don't duplicate it).
- =@gltf='s fix becomes: wrap the =loader.load(...)= body in a =load(url)=
  function; on init call =load(%src)=; ALSO call
  =ctx.onParamChange(['src'], (vals) => load(vals.src))=. Same shape applies
  to =@object='s =color=/=roughness=/=metalness=/etc — wrap mesh-creation in
  a =rebuild()= that disposes + re-adds, register once.
- This is a SMALL extension of an EXISTING registry (the =ctx= object
  =three-stage.st= already hands every child), its variants are DATA (which
  param names to watch — a plain string array per primitive, not a Rust
  match-arm), and it DELETES the "3D scenes are static" special case across
  the WHOLE module in one primitive-level change (elegance-bar: passes all
  four checks — extension of existing =ctx=, data-driven param list, deletes
  the static-only assumption, testable by the same =stage.test.st= machinery).

** Scope for the first pass
Ship =onParamChange= support for =@gltf='s =src= FIRST (the concrete blocker
from FEAT-151 — hot-swapping a model mid-scene) and =@object='s =color=/
=roughness=/=metalness=/=emissive= (the next most obviously-dynamic case —
data-driven material state). Defer geometry-shape-changing params
(=shape=/=size=/=detail= on =@object=, which need full geometry disposal +
re-tessellation, a heavier rebuild) to a follow-up once the material/src case
proves the mechanism out.

Forge Deck currently routes around this ENTIRELY via
=spacetime/st_mount { host, region, input }= re-composing the WHOLE guest

* Implemented (2026-07-06) — @gltf's src, the concrete FEAT-151 blocker

Shipped the generalized mechanism exactly as designed: ONE `resolveReactive`
helper added to `three-stage.st`'s shared `canvas._stThree` context object
(the acknowledged "engine boundary" every child primitive already composes
against), reused by `three-gltf.st` for its `src` param.

** ctx.resolveReactive(rawValue, onChange) -> unsubscribe
- `rawValue` is the RAW captured param text (a literal string OR `"$sig"` /
  `"$sig.field"`) — the SAME shape `derived-signal.st`'s hand-rolled
  regex-rewrite already works with for `@data derive`, generalized into a
  reusable primitive-layer helper instead of every 3D primitive re-deriving
  its own copy.
- Literal value: calls `onChange(rawValue)` once, returns a no-op
  unsubscribe (unchanged behavior for every existing static-param call site).
- `$`-prefixed value: resolves via `ST.resolvePath` (BUG-155's fix — head +
  dotted-path walk) immediately, THEN watches the head signal via
  `ST.watchScoped` (fires on every subsequent change), re-resolving the full
  path and calling `onChange` again each time.

** three-gltf.st wiring
Restructured the load into a reusable `load(url)` closure (was a bare
`loader.load(...)` call inline): `disposeCurrent()` tears down the previous
mesh (unregisters spin, removes from scene AND `canvas._stObjects`, clears
`canvas._stObject` if it was the removed one) before each new load; a
monotonic `loadToken` guards a stale in-flight network response from landing
after a NEWER load already started (fixes a real race a naive hot-swap would
have). `ctx.resolveReactive(rawSrc, load)` replaces the old one-shot
`loader.load(url, ...)` call entirely.

** Verified end-to-end, live (real browser, not simulated)
- `@gltf(src: $modelPath)` where `$modelPath` starts at one real
  Blender-exported .glb (demos/mcp-forge's step-0.glb): loads correctly
  (`canvas._stObjects.length === 1`).
- Clicking a button that reassigns `$modelPath` to a DIFFERENT .glb
  (step-3.glb): the mesh UUID actually CHANGES (`16c9e5f9...` ->
  `9c37781b...`) while `_stObjects.length` stays at 1 (old mesh correctly
  disposed, not accumulated) — confirmed via direct puppeteer inspection of
  the live THREE.js scene graph, zero page reload, zero region remount.
- Literal `@gltf(src: "/models/helmet.glb")` (the existing demos/3d/gltf-studio
  usage) unaffected — regression-verified both at the compile-snapshot level
  (`three_gltf_literal_src_emits_quoted_url`) and via `cargo run -- check` on
  the real demo file.

Regression tests: `src/compiler.rs::three_gltf_signal_src_binds_and_carries_raw_reference`
pins that a signal-valued src routes through `resolveReactive`. Full suite
green: `cargo test --lib` (2564), `cargo test --test integration_tests` (181),
`cargo run --features headless -- test tests/ --headless` (603).

* Scope shipped vs. deferred
Shipped: `@gltf`'s `src` (the concrete FEAT-151 blocker — proves the
mechanism end-to-end). Deferred to explicit follow-up (not silently
dropped): `@object`'s `roughness`/`metalness` (same `resolveReactive`
mechanism applies directly, just needs the primitive restructured similarly
to rebuild the material on change) and `color`/`emissive` (a DEEPER gap —
`.rgba`'s compile-time hex-parsing field accessor needs runtime color
parsing to accept a signal value, a separate design question). Filing the
`@object` follow-up as its own item keeps this landed change reviewable and
focused on the one primitive that actually blocked FEAT-151.
