** THE FINDING — polarity. This is why the reverse join does not just work.

The `%scalar_type` table already declares the join: each row names its grammar in
`%capture` (stdlib/scalars/types.st). So inference looks like it should be the
REVERSE of a join that already exists: given a literal, find the scalar whose
production accepts it. Two lines of code.

Measured, it returns garbage. 17 of 19 sample literals come back AMBIGUOUS, and
the two "UNIQUE" answers are the WRONG ones:

  "#FF0020"               AMBIGUOUS  ["color", "date"]
  "8px"                   AMBIGUOUS  ["date", "length"]
  "600ms"                 AMBIGUOUS  ["date", "duration", "time"]
  "chartreuse"            AMBIGUOUS  ["date", "richtext", "string", "url"]
  "--ink"                 AMBIGUOUS  [all 13 scalars]
  "1px solid red"         UNIQUE     ["date"]      <- the only unique answers
  "garbage ~~~ nonsense"  UNIQUE     ["date"]      <- are both nonsense

The cause is not a bug in any grammar. It is that `capture_type_accepts`
(src/syntax/events/mod.rs:125) is a REFUSAL function wearing a recognition
function's name. Its terminal arms all default to ACCEPT:

  - a name that is neither a stdlib production nor a builtin
    (`date`, `url`) -> `CaptureType::Custom` -> `return true`, commented
    "genuinely unknown, and not ours to refuse"
  - `match_capture_type` returning None -> `!defs.contains_key(...)` -> true
  - a token reference (`--ink`, `var(--ink)`) -> true for EVERY scalar, by the
    deliberate rule that a scalar accepts a reference to itself

Every one of those defaults is CORRECT for the question it was written to answer.
"Should I refuse this value?" must answer no when it does not know, because a
false refusal blocks a build the author cannot fix and a missed diagnostic costs
five minutes. That asymmetry is load-bearing and must not be touched.

It is exactly inverted for "what type is this value?". Inference must default to
NO ANSWER when it does not know, and answer only on a POSITIVE match.

  refusal:     unknown -> accept   (never block a build)
  recognition: unknown -> abstain  (never invent a type)

One function cannot have both polarities. This is not a refactor of
`capture_type_accepts` — it is a SECOND function over the SAME grammars, and the
grammars are the shared substrate that keeps them aligned by construction. That
satisfies the two-parser rule the original FEAT set as a risk mitigation.

** Three consequences for the staged design

1. Tier 1 no longer reads lexer token kinds (W3 dissolved them). It runs the
   scalar productions the `%scalar_type` table names, with recognition polarity.
   The tier is unchanged in INTENT and completely changed in MECHANISM.

2. Inference must answer with a LATTICE, not a bool. The measured ambiguity is
   not all noise — some of it is real and structural:
     - `600` is genuinely both `number` and (in a duration slot) a time. Unit
       ambiguity is REAL; PLAN-122 C7 and the stagger incident are the scar.
     - `chartreuse` is genuinely both `color` and `string`. This one is
       resolvable: prefer the MOST SPECIFIC production. `string` accepts
       everything, so it must never win a contest.
     - `100%` matching both `length` and `percentage` is CORRECT — the length
       grammar includes percentage by design (documented in scalars/types.st).
   So the return type is not Option<Scalar>. It is a set, plus a specificity
   order, plus an explicit Ambiguous answer that downstream must handle. An
   inferrer that picks arbitrarily from a tie is the stagger bug with a new face.

3. A REFERENCE is not an inference failure, it is its own answer. `--ink` and
   `$brand.ink` are not "unknown type" — they are `Reference`, and the arc
   already has grammar for exactly this (`token_ref`, `binding`, `hole` in
   stdlib/capture-types/value-node.st). Inference should return Reference and let
   RESOLUTION take over. That is the one distinction from the syntax-inference
   doc worth keeping: recognition is total and local, resolution is partial and
   global, and they are different mechanisms — but recognition is NOT the whole
   story, which is what I overclaimed.

** The two mistakes worth keeping in the record

1. Deriving precedence from language inclusion does NOT work. `string` and
   `color` OVERLAP — neither language contains the other — so inclusion answers
   "incomparable" for exactly the pairs needing an answer. 17/18 -> 13/18.
   Precedence is a judgement (a MEANING beats a SHAPE) and must be declared;
   W5 moved that declaration into stdlib where a person can read it.
2. Mutation testing found two Wave-3 mechanisms no test could see. The gates
   written to close that gap failed on their first run and found a REAL bug:
   `slot_supplies_a_unit` was derived as "refuses a bare number", so a `color`
   slot swallowed `600`. A slot may supply a UNIT the spelling omits; it may not
   supply a KIND the value contradicts.

** Still open (deliberately, with reasons)

- BUG-367 (the dead validator).
- `date`/`url`/`string` name productions that do not exist; `production_exists`
  is a workaround for malformed rows. Either give them grammars or drop
  `%capture` from those rows.
- `CapturedValue` has no lossless home for `angle`/`percentage`/`easing` — they
  infer correctly and are dropped to `Expr`. Wants ONE general
  `Scalar { ty, text }` carrier, not a variant per scalar.
- Named colours do not infer. The fix is property-contextual grammar, never a
  list of 148 names in Rust.
- `tests/corpus_inference_scan.rs` is a crude line-splitter and says so; it
  sizes a population, it is not a parser.
