i want us to design a system where the stdlib has 'migrations', i.e. a macro that takes old st syntax and turns it to new st syntax. the macro should include the date so that we can order the migrations by syntax and apply syntax waves. It should be shown in all dev environments next to the current host pill, in the same style as the host pill

* Commit from pill (PLAN-076 follow-up, requested by user)
After a persisted apply, the migrations pill should offer a **Commit**
action that stages ONLY the migration's own changes and commits them —
git add by HUNK, not by file, so unrelated in-flight edits sitting in the
same files are never swept up.

* Design
- The apply route already knows exactly what it changed: the pending
  entries' {file, span, old_text, new_text} + the @version insertion.
- Build a unified patch from those recorded edits (they are span-exact by
  construction) and stage it with `git apply --cached`, leaving the
  working tree and every other hunk unstaged.
- Include the @version hunk. Commit message auto-composed from the wave
  date + migration ids/%docs lines.
- Server route: POST /__spacetime/migrations/commit {date} (dev-only);
  pill button appears next to a successful Apply result.
- Refuse cleanly when the tree state no longer matches the recorded edits
  (file changed since apply — re-run status first).
