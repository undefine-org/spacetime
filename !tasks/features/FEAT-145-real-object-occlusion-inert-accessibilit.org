* Research (verified via web_search, not guessed)
Three ways this problem is commonly solved (three.js forum "Hide labels behind gltf" thread,
drei's `<Html occlude>`, IGC's HTML/WebGL integration writeup):
1. Depth-buffer readback / render-target comparison — heaviest, fights post-processing passes
   (documented drei issue: occlude="blending" breaks with a composer in the pipeline).
2. Canvas-texture text (render text to a plane/sprite, participates in real depth) — loses
   "real, selectable DOM" which is a hard requirement of this whole spatial-ECS mechanism
   (FEAT-142's stated goal: "real DOM that tracks its object").
3. Camera→point RAYCAST against `scene.children` each frame — cheap (one ray, not a full
   depth pass), doesn't touch post-processing, and is literally what drei's own occlude
   implementation does under the hood. THIS is the blessed technique for our case (DOM
   labels must stay real DOM).

* The fix (small extension of the SAME `visible` signal, no parallel path)
`three-anchor.st` (both projects): new `occlude:bool=false` + `selfRadius:number=0.15` params.
When `occlude` is on, each frame: `raycaster.set(camera.position, dirTowardPoint)`,
`raycaster.far = distanceToPoint - selfRadius` (the self-exclusion zone stops an object's OWN
surface from occluding its OWN label), `raycaster.intersectObjects(scene.children, true)`. Any
hit → `$occluded = true` → folds into the EXISTING `visible = inFrustum && windowOpacity>0.01 &&
!occluded` expression (was already frustum ∧ window; now ∧ ¬occluded) — one boolean, same
downstream consumers (opacity, pointer-events). Raycast is only run when the point is already
in-frustum and in-window (skip when about to be hidden anyway) and only when `occlude:true` (a
call site that doesn't need it pays zero raycast cost). New `$occluded` signal exported for
forward use.

* Accessibility bonus (found while in this code, same signal)
Before this: `visible` only drove `opacity` + `pointer-events`. A screen reader still has the
occluded/faded label in its accessibility tree and tab order — `opacity:0`/`pointer-events:none`
alone is a purely VISUAL hide, not an accessibility hide (this is a well-known a11y footgun).
Fix: `el.inert = !visible` — `inert` is Baseline since April 2023 (Chrome/Firefox/Safari/Edge,
~96%+ coverage 2026), removes the element (and descendants) from BOTH the tab order AND the
accessibility tree in one standards-compliant boolean, doing in one line what would otherwise
need a per-child `aria-hidden` + `tabindex=-1` dance. Verified against MDN + the WHATWG HTML
spec's `interaction.html#the-inert-attribute` section.
