* Why

`is_color_value_position` (src/syntax/cst/lexer.rs:778) promotes `#hex` to ONE ATOMIC COLOR token after a COLON, inside a value function's parens, after a value comma, or mid-declaration-value. The extractor contract is `fn extract(&self, tokens: &[TokenData], source: &str)` returning tokens-CONSUMED — a whole number of tokens. A grammar can therefore never consume "the `#` of a COLOR token and then four of its characters": there is no half-token in the protocol.

The counted-class terminal I shipped in W0 (commit 05f83468) scans BYTES, so it can cross token boundaries — but only from a token START. It cannot begin inside a token. HASH+IDENT works (its gates prove it); atomic COLOR does not.

So the situation is exactly backwards from the plan's assumption: the counted terminal works in the position where nobody writes a colour (bare `#e8eef7` at statement level) and fails in every position where colours are actually written.

* Consequence for the plan — W3 is not "after W1"

FEAT-165 says "Blocked by W0"; FEAT-167 (W3, kernel lexer) says "Blocked by W1 (grammars must own the domains before the lexer stops pre-committing them)". That circularity is now proven REAL, not stylistic: the lexer pre-commits the domain by MERGING, and a merged token is opaque to any grammar. W1 cannot own a domain the lexer has already fused into a single token.

The dependency is not W1 → W3. It is: **the DEMOTION of the four tier-2 lexer passes must land WITH or BEFORE the grammars that replace them.** They are one cutover, not two waves.

Same argument applies to `NUMBER_WITH_UNIT` (lexer.rs:332-371) — `8px` is one token, so `$n:number $u:unit(length)` (two captures) can never match it. Confirmed by the same mechanism; no separate probe needed since it is the identical merge-then-opaque shape.

* An unexpected argument FOR the wave (user-visible, verifiable now)

There is NO hex validation anywhere in the pipeline today. Verified end to end:

: .probe { color: #e8ee1; background: #zzz; }
: $ cargo run -- check   → ✓ All 1 file(s) passed
: emitted spacetime.css  → .probe { color: #e8ee1; background: #zzz; }

`#e8ee1` is a 5-digit hex — not a legal CSS colour in any spelling — and `#zzz` is not hex at all. Both pass `check` silently and reach the emitted stylesheet, where the browser drops the declaration and the author sees an element that simply renders wrong with no diagnostic anywhere. lightningcss (src/validation/css.rs) validates at STYLESHEET level and does not catch it on this path.

So W1's counted grammar is not merely a refactor that relocates existing behaviour — it is the first thing in the system that would ever reject a malformed colour. `{3|4|6|8}` makes `#e8ee1` a PARSE ERROR WITH A SPAN. That is a real acceptance criterion to add:

- `color: #e8ee1;` and `color: #zzz;` produce a spanned diagnostic at the value.
- The 4-digit and 8-digit alpha forms (`#fffa`, `#11223344`) still pass — a naive "3 or 6" fix would regress them, which is exactly why the count set is DATA.

* Scope correction to the "Target" section

`stdlib/capture-types/` currently holds nine files (claims, component-body, handle-block, keyframes, on-actions, param_list, properties, signal-receive, type-variants) — no scalars, as the design said. But note the naming convention: this directory is grammar PRODUCTIONS. `%unit_set` and `%char_class` as written in the Change section DO NOT EXIST as directives — the parser recognizes only `%capture_type`, `%claims`, `%default`, `%hint` (plus the MetaDef variants: Primitive, Macro, Preset, RuntimeRegistry, CaptureType, Vendor, Migration, CommentType). Adding two new meta directives fails the AGENTS elegance bar (new subsystem, not an extension). Express unit sets as ordinary `%capture_type` unions instead — `%capture_type length_unit { "px" | "em" | ... }` — which is the mechanism `on.st` already uses throughout (`on_leaf`, `on_pat`, `on_consequence`). One directive, composed; no new grammar surface.

Likewise `$hex:xdigit{3|4|6|8}` in the Change section is not the shipped spelling. W0 attaches counts to a CHAR CLASS, so it is `[0-9a-fA-F]{3|4|6|8}` — deliberately, because a Group would compose per-character matches and lose the length constraint that IS the token shape. Update the grammar sketches before implementing.

* THE GATE CAUGHT A REAL DEFECT ON ITS FIRST RUN (and a design error of mine)

I first made the kernel path re-lex the `#…` remainder so `#123456` would demote to HASH + NUMBER rather than HASH + IDENT — "honest kinds". The parity test failed in 5 files, and the failure taught two things:

1. **COLOR promotion is ALREADY inconsistent at Domain tier.** `color: #6b7280` promotes, but `border-right: 1px solid #232634` does NOT — `solid` is not a recognized value position, so that hex is already HASH + IDENT today. The tier-2 pass does not mean "this is a colour"; it means "this is a colour in one of four syntactic neighbourhoods". Consumers reading COLOR are therefore already seeing a partial view. Worth carrying into W1.3: migrating them is not "replace COLOR with a grammar result", it is "start seeing the colours the lexer was silently missing".

2. My honesty pass widened the tier delta beyond the two fused kinds, destroying the bound test #2 exists to hold. REVERTED. The counted terminal scans BYTES from a token start, so the remainder's kind is irrelevant to matching, and a uniform shape is the easier one to write a grammar against. Reasoning recorded in the test so it is not re-attempted.
