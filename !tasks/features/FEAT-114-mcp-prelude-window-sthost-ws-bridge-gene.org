* Why (this is the original ask, made concrete)
The user's goal: "interfaces defined as functions loaded into the live environment …
a fully live environment from scratch, not just a 'prompt thing'." That requires a
HOST BRIDGE a served .st page can signal through — the runtime substrate that makes
`@host $mcp : ws($hostSocket)` real. This FEAT is that substrate (the prelude +
generic sink); FEAT-111 is the tool surface (st_mount/st_await + the library .st
functions) built on top.

* The bridge (mirror window.__stDevWs EXACTLY)
- __dev__ injects window.__stDevWs (a ws bridge: connected/lastMessage/error +
  send) into dev-served pages (stdlib/__dev__/primitives/dev-ws.st). The MCP prelude
  injects window.__stHost the SAME way: a ws Channel exposing
  { dispatch(envelope) -> reply, subscribe(handler) } over the MCP's ephemeral
  ws endpoint. `@host $mcp : ws($hostSocket)` binds to it; `@data signal/stream … to
  $mcp` send/receive route through it.
- ONE generic sink route on the MCP's ephemeral server: /__mcp/signal/{instance}.
  __stHost.dispatch POSTs/sends the decoded-OUT envelope here → stored keyed by
  instance + correlation id → unblocks st_await (FEAT-111). REPLACES the bespoke
  /__mcp/choose route + ChooseForm{option:usize} struct.
- correlation: the prelude stamps each outbound envelope with a correlation id and
  routes replies back to the originating signal's @handle (the runtime-invisible
  fiber id from §S1). One-shot signal = one reply; stream = many until `final`.

* Self-describing wiring (the introspection rail)
When st_mount(fn, input) compiles a .st page, it READS the page's @data-signal
registry (FEAT-110 binding facts; same rail as @data dispatch / FEAT-113) to learn
the interface's input + response sum, and serves the page with __stHost injected.
No hand-fed schema — the function's signal registry IS the schema.

* Verified ground truth
- dev-ws.st: %primitive dev-ws { %emit js { … window.__stDevWs = { … }; %yield
  connected/lastMessage/error } } — the exact pattern to mirror for __stHost.
- src/mcp/live.rs: already runs an ephemeral axum server + proposal store + the
  await poll. REUSE the server + store machinery; swap the bespoke /__mcp/choose
  route for the generic /__mcp/signal/{instance} sink + correlation map.
- src/mcp/state.rs: the store keyed by proposal id — generalize to instance+correlation.

* Scope (W2 substrate)
IN: window.__stHost ws-bridge prelude (demand-injected into MCP-served pages, like
__dev__); the generic /__mcp/signal/{instance} sink + correlation map on live.rs;
the store generalization (state.rs); the registry-read hook st_mount uses. Wire
`@host $mcp : ws(...)` + `to mcp` to the bridge.
OUT (→FEAT-111): st_mount/st_await tool surface + the stdlib/__mcp__/ library .st
functions + deletion of the old tools. (→W5): device hosts.

* Edge cases
- page served without the prelude (non-MCP context) → __stHost absent → `to mcp`
  emit degrades to console.debug noop (never throws); landing/web pages unaffected.
- ws disconnect mid-signal → __stHost surfaces error → @handle Failed arm fires.
- multiple instances live → instance id isolates stores; correlation id isolates
  in-flight calls within an instance.
- stream signal → prelude keeps the correlation open, routing every message to the
  same @handle until a `final` arm or cancel.
- reconnect → mirror dev-ws reconnect (configurable backoff).
