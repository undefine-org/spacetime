NOTE (2026-06-13): rescoped from "@signal" to the §S1 model. The library .st
functions (picker/form/confirm) are now written with `@data stream/signal … to $mcp`
+ `receive` decode + @handle, NOT @signal. An interface = a .st function whose
@data-signal REGISTRY is its schema (read via the same rail as @data dispatch).
st_mount(fn,input) compiles + reads that registry + serves (with __stHost from
FEAT-114); st_await returns the decoded variant. The 4 bespoke tools (st_propose/
st_proposal_status/st_await_choice/st_elicit) collapse to st_mount + st_await.
* Why
Today the human→agent signal path is THREE parallel Rust impls of one need
(picker route + ChooseForm + OptionDiagnostic precompute; st_elicit 100% Rust;
compile-only). Each new interaction = new Rust tool + descriptor prose + Spell
re-register + rebuild. That IS the "prompt thing." Harmony violation: one need,
N impls. Collapse to ONE generic transport; interfaces become .st FUNCTIONS.

* The collapse (cutover, DELETE the parallel impls — AGENTS: refactors are cutover)
  BEFORE (src/mcp)                          AFTER
  ----------------------------------------  --------------------------------------
  st_propose (compile+store+picker route)   st_mount(fn, input) → {url, instance}
  st_proposal_status (poll)                 st_await(instance) → declared payload
  st_await_choice (blocking poll)           (one await, same blocking mechanism)
  st_elicit (Rust server→client form)       form.st library function via st_mount
  /__mcp/choose/{id} + ChooseForm{usize}    /__mcp/signal/{instance} (generic sink)
  OptionDiagnostic + badge/url precompute   the FUNCTION declares its own payload
  picker.st (Rust-coupled data.json shape)  picker.st = a portable library function

* Mental model (functions-as-interfaces)
  An "interface" = a .st FUNCTION = { inputs (params via @data), UI (markup),
  signal-back (@signal emit … to mcp) }. The MCP is just a HOST that:
   1. st_mount(fn, input): fn = a library name (stdlib/__mcp__/<name>.st) OR inline
      .st code; input = JSON bound under @data for the page; compile + serve live;
      return {url, instance_id}.
   2. injects window.__stHost into every served page (symmetric with __dev__'s
      window.__stDevWs) so `@signal emit … to mcp` routes to the host.
   3. /__mcp/signal/{instance}: the ONE generic webhook. __stHost.signal(name,payload)
      POSTs here → store keyed by instance → unblocks st_await.
   4. st_await(instance): blocks until a signal arrives → returns the RAW declared
      payload (the function's shape, NOT a Rust struct). Re-callable on timeout
      ({decided:false}), same bounded-<30s pattern as today's st_await_choice.

* The library (stdlib/__mcp__/, the first functions)
  - picker.st  : choose 1-of-N options. @data fetch $input → options; @each cards;
                 each card fires `@signal emit $choose {idx number} to mcp` on click.
                 (rewrite of today's picker.st — drops ALL Rust-contract coupling.)
  - form.st    : typed input form. payload schema IS the @signal declaration;
                 replaces st_elicit's Rust form. (Native MCP elicitation stays as an
                 OPTIONAL fast-path when the client advertises it — see Decision.)
  - confirm.st : yes/no. `@signal emit $decide {ok bool} to mcp`.
  These are DISCOVERABLE (st_mount by name) and EXTENSIBLE (the agent can st_mount
  inline .st in the same turn — the "fully live from scratch" property).

* Decision — keep native elicitation as a fast-path?
  st_elicit (server→client elicitation/create) is a REAL second channel (no browser).
  KEEP it as a thin tool, but reframe: st_elicit pushes the SAME payload schema a
  form.st function declares. One schema vocabulary, two render hosts (native prompt
  vs browser form). Do NOT delete elicitation; DO delete the bespoke browser-form
  Rust. (If this proves redundant in practice, fold later — note as FUP.)

* Edge cases
- inline fn code that fails to compile → st_mount returns {ok:false, diagnostics}
  (the function's own diagnostics, surfaced both channels — reuse existing).
- multiple mounts live at once → instance_id keys keep them isolated in the store.
- human closes tab without signaling → st_await times out, re-callable (unchanged).
- a fn that emits MANY times (streaming UC6) → st_await returns latest; document
  that repeated await consumes a sequence.
- fn with no @signal (display-only) → st_mount still serves; st_await just blocks
  (warn in result).
