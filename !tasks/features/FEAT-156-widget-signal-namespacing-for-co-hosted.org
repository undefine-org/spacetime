* Initial Message

i want us to design a system where the stdlib has 'migrations', i.e. a macro that takes old st syntax and turns it to new st syntax. the macro should include the date so that we can order the migrations by syntax and apply syntax waves. It should be shown in all dev environments next to the current host pill, in the same style as the host pill

* Problem
Co-hosted widgets on one dev page (host pill + migrations pill in the dev
dock) share ONE global `SpacetimeLocal` (window-level reactive scope:
`window._localState` + its proxy). Any same-named signal in two widgets
collides — observed live: an unprefixed `$isExpanded` in the migrations
pill toggled BOTH panels; `$status` would have clobbered the host pill's
status fetch. PLAN-076 worked around it by prefixing the pill's signals
(`$mig*`).

* Direction
Compiler-level namespacing for separately-compiled widget bundles:
`Compiler::from_file` for widget compiles (compile_host_widget_raw,
compile_migrations_widget_raw, admin) could take a `signal_prefix:
Option<&str>` that rewrites emitted `SpacetimeLocal` keys + `local:*`
event names per bundle (host → `host:*`, migrations → `mig:*`). Check the
emit layer for how signal names + event names flow (the `local:<name>`
CustomEvent channels + SpacetimeLocal proxy keys) — ONE prefix point each.
Then drop the manual `$mig` prefixes in stdlib/migrations/__dev__/pill.st
and audit stdlib/__host__ + stdlib/__admin__ for the same latent hazard.
