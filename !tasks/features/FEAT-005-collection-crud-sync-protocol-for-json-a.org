* Implementation

** Step 1: Protocol extension (~src/sync/protocol.rs~)
#+begin_src rust
// Add to ClientMessage enum:
EditJsonArray {
    file: String,
    path: String,       // JSON path to the array (e.g., "" for root array, "products" for nested)
    op: ArrayOp,
    op_id: Option<String>,
}

enum ArrayOp {
    Insert { item: Value, index: Option<usize> },  // None = append
    Delete { index: usize },
    Reorder { from_index: usize, to_index: usize },
}
#+end_src

** Step 2: Handler (~src/sync/handlers.rs~)
- New ~handle_edit_json_array()~ function
- Validate file path (reuse existing validate_file_path)
- Read JSON file, parse, navigate to array via path
- Validate target is a JSON array (return error if not)
- Apply operation (insert/delete/reorder)
- Write file back (pretty-printed JSON)
- Broadcast DataUpdate to all clients
- Return Ack with op_id

** Step 3: Message dispatcher
- Add ~EditJsonArray~ branch to ~handle_message()~ dispatcher (line ~1204 in handlers.rs)

** Step 4: Client-side support
- Update ~stdlib/__dev__/primitives/dev-ws.st~ to handle new message type
- Add helper functions to ~stdlib/__dev__/primitives/dev-save.st~: ~saveArrayInsert()~, ~saveArrayDelete()~, ~saveArrayReorder()~
- These will be called by the admin panel and collection CRUD UI items
* Edge Cases
- Empty array: insert works, delete returns error, reorder is no-op
- Out-of-bounds index: return descriptive Reject message
- Array within array: path like ~[0].tags~ targets nested array
- Root-level array: empty path targets the file root
- File doesn't exist: return Reject (don't auto-create)
- Non-array target: path points to object/scalar, return Reject
- Large arrays (1000+ items): ensure no performance cliff
- Concurrent edits: two clients insert at same index simultaneously
