* Found via
FEAT-151 (Forge Deck) design pressure-test, per explicit ask: "the 3d module
especially is lacking semantic affordances." Confirmed by direct code survey —
searched every file in =stdlib/3d/macros/= and =stdlib/3d/primitives/= for
=click|raycast|pointer.*intersect|onClick|@on click= — ZERO matches anywhere
in the module. A three.js scene is a canvas with a WebGL context; without a
raycast primitive there is NO way to know which mesh a click/hover landed on.
This is the single biggest gap between "a rendered 3D scene" and "a 3D UI."

* Concrete failure mode this blocks
Forge Deck's original vision (per the task) was a UI where clicking the FORGED
OBJECT ITSELF (not just a sidebar button) could drive the agent loop — e.g.
click the boss/facet on the coin to inspect that feature, or click-to-rotate
inspection with per-face highlight. Every one of these needs "which mesh did
the pointer hit" — currently impossible without hand-written page JS, which
is EXPLICITLY FORBIDDEN by repo AGENTS.md ("Spacetime websites should NOT have
custom javascript"). Today a 3D scene is functionally output-only.

* What exists today (the affordances to build ON, not replace)
- =three-stage.st= already exposes =canvas._stThree = { THREE, scene, camera,
  renderer, registerFrame, setRender, size }= — the ONE shared engine handle
  every child primitive composes against (documented "engine boundary"
  pattern, the right place to add a raycaster).
- =three-object.st= / =three-gltf.st= already register every mesh onto
  =canvas._stObjects= (array) and =canvas._stObject= (last-added) — so a
  scene-wide raycast primitive can already enumerate pickable targets without
  any new registration mechanism.
- The page-level event grammar ALREADY has the exact right shape:
  =@on $event:ident $name:ident(...) { $body:keyframes }=
  (=stdlib/macros/on-event.st='s =on-event-dispatcher=) and the simpler
  =@on click { $sig <- value; }= imperative form (=examples/cart-demo/index.st=
  line 125) — ONE sigil, ONE meaning: =@on <event>= is already how Spacetime
  spells "when this happens, do this." A 3D click affordance should NOT invent
  a second event vocabulary.

* Elegant target design (reuses @on, zero new subsystems)
** Surface: extend @object / @gltf with an optional pick identity + reuse @on
#+begin_src
@object sphere(size: 1, color: #c0c5ff) => &boss
@on click &boss { $selectedPart <- "boss"; }

// or, for the common "just tell me what I clicked" case, a same-block form:
@object sphere(size: 1) {
  @on click { $selectedPart <- "boss"; }
  @on hover { $hoveredPart <- "boss"; }
}
#+end_src
- =@on click= / =@on hover= INSIDE an =@object(...)= { } or =@gltf(...)= { }
  body is the natural home — =@object= already accepts =$children*= (see
  =object.st= form, the =%template { $children }= slot exists TODAY for
  exactly this kind of nested directive), so this is a body-grammar
  EXTENSION, not a new top-level construct.
- Under the hood: ONE =%primitive three-raycast(&stage_el)= registered ONCE
  per =@stage= (not per-object — avoids N raycasters), wired to
  =canvas.addEventListener('pointerdown'/'pointermove', ...)=, using
  =THREE.Raycaster= against =canvas._stObjects= (already populated!) each
  event, mapping the intersected mesh back to whichever =@object=/=@gltf=
  instance registered it (each mesh gets =mesh.userData.stObjectId= at
  creation — one field, already have the creation site). The =@on click=
  inside the object body just becomes sugar that filters the shared
  raycast-hit stream to this mesh's id — SAME mechanism =event-driver=
  already uses for DOM events (trigger name + target), extended to a THREE
  target instead of a DOM element.
- Named-ref sigil (=&boss=) for referring to a specific object from OUTSIDE
  its own block (e.g. an external =@on click &boss= driving a DIFFERENT
  element's animation) can be a SEPARATE follow-up if the inline body form
  covers the Forge Deck use case — don't build both in one pass; validate the
  simpler form first (elegance-bar discipline: earn the second mechanism only
  after the first ships and proves insufficient).

** What this DELETES / doesn't add
No new sigil, no new keyword, no parallel event system — =@on= keeps its ONE
meaning (event -> body), now valid inside one more scope (=@object=/=@gltf=
body) the same way it's already valid inside a selector body today.

* Acceptance
- =@object icosahedron(...) { @on click { $sig <- true; } }= compiles + a
  real puppeteer click on the rendered canvas at the mesh's screen position
  flips =$sig= (headless =--cdp= layout-tier test per
  =docs/testing/CDP_BACKEND.md= — raycasting needs real layout/paint, refuses
  correctly on =--headless=).
- =@on hover= similarly fires enter/leave.
- Zero new custom page JS surfaces in any consuming demo — the whole feature
  is =%primitive= + =%macro=, same as every existing 3D affordance.
- A regression test lives in =stdlib/3d/tests/= (new =pick.test.st= or
  similar), following the existing =stage.test.st= conventions.

* Non-goals (explicitly deferred)
- Drag / gizmo manipulation (a much bigger feature — outline it separately if
  wanted later).
- Multi-touch / touch-specific pick refinements.
- Named external =&ref= click binding (see design note above — only if the
  inline form proves insufficient for a real use case).

* Partial progress (2026-07-06) — raycaster infra shipped, macro wiring blocked on a real compiler gap

Implemented and verified the HARDER, correctly-designed half: `ctx.registerPick`
in `stdlib/3d/primitives/three-stage.st` — ONE shared `THREE.Raycaster` +
ONE `pointerdown`/`pointermove` listener per `@stage` (not per-object),
matching by object IDENTITY via a `Map<Object3D, handlers>`, walking up the
scene graph to find the registered ancestor (so a loaded glTF's child mesh
still resolves to whichever `@gltf`/`@object` registered the ROOT). Symmetric
cleanup in `three-stage`'s own `%cleanup`. Compiles clean, zero regressions
(`cargo test --lib` 2564 passed including all `three_*` snapshot tests).

`registerPick(object3D, { click?, hoverStart?, hoverEnd? }) -> unregister`
is ready to consume — this is the "one shared raycaster" design goal from
the original ticket, done. What's BLOCKED is wiring `@object`/`@gltf`'s
SURFACE syntax to call it.

** The real blocker: no macro-grammar path for a nested `@on` body inside a typed-param macro

Tried the two straightforward-looking approaches; BOTH hit a genuine
compiler-architecture gap, not a syntax typo:

1. `@object(..., onClick: { $sig <- val; })` — a NAMED PARAM inside parens
   whose value is a `{ }` mutation body. `:mutation_actions` capture type
   ONLY gets its special `{js_statements:[...], macro_calls:[]}` structured
   conversion when used as the macro's OWN TRAILING body capture
   (`@effect(...) { $body:mutation_actions }`, `src/syntax/events/form_compiler.rs`
   line ~1472, inside `try_match_body`'s body-capture loop). A named
   parenthesized arg of the same capture type routes through the GENERIC
   `ExtractorRegistry` -> falls back to `ExprExtractor` -> raw `CapturedValue::Expr`
   text -> at the PRIMITIVE's `%emit js` substitution boundary, an `expr`-typed
   param gets JS-PARSED (`parse_emit_js`), which chokes on `$sig <- val;`
   (not valid JS) and produces garbage; a `string`-typed param instead runs
   `parse_object_literal`, which silently drops any pair without a literal
   `:` colon (a mutation statement has NO colon) -> emits `{}`. Neither
   primitive param type produces usable output; the ONLY place this capture
   shape compiles correctly is the trailing-body form. Traced to source, not
   guessed — confirmed with `cargo run -- build` + grep on the emitted JS for
   both the `expr` and `string` param-type variants.
2. `@object(...) { @on click { $sig <- val; } }` — a GENUINE NESTED CHILD
   directive (using `@object`'s EXISTING `$children*` Block capture, the
   SAME slot procedural sub-shapes use). This compiles with ZERO error/warning
   — but `@object`'s `%template { $children }` only knows how to render
   children as 3D scene sub-objects; there's no metasystem-level mechanism
   for a macro to FILTER its `$children*` Block for a specific nested
   directive (`@on`) and thread its ALREADY-CORRECTLY-COMPILED mutation body
   (which the child's OWN form, `on-mutation-dispatcher-simple`, DOES produce
   correctly) into a sibling `%binds` primitive call as a param. This is a
   register-level gap, not a one-line fix — `%binds`'s `BindValue` grammar has
   no "extract matching child from $children by macro name" primitive.

** Decision: ship the working raycaster infra now, defer the surface syntax
Committing `ctx.registerPick` (real, tested, currently-unused-but-harmless
dead code from the page's perspective — no existing primitive calls it yet,
so it changes nothing observable) rather than holding it hostage to the
harder problem, and filing the REMAINING work as its own ticket with the
exact architecture question spelled out (see follow-up below) instead of
rushing a broken `onClick:`/`onHover:` param into two widely-used stdlib
macros. Per this repo's elegance-bar discipline: a half-working feature that
silently drops the user's click handler is WORSE than no feature — it fails
"reviewable / self-explains in diff" and would ship an invisible landmine.

* Follow-up needed (do NOT re-attempt without resolving this first)
File a follow-up scoped EXACTLY to: "add a metasystem mechanism for a macro
to extract a specific nested child directive's compiled output by macro
name from its `$children*` Block capture, for use in a sibling `%binds`

`@object`'s/`@gltf`'s `@on click`/`@on hover` children to `ctx.registerPick`
is a small, mechanical stdlib-only change (the primitive-side handler
plumbing already works, proven by `ctx.registerPick`'s own tests). Do NOT
retry the named-param-with-mutation-actions-value approach (option 1 above)
— it's a dead end confirmed twice over, not a "try harder" situation.
