* Origin
FEAT-152 (stdlib/3d pointer-pick). Needed so `@object(...) { @on click { … } }`
can thread its nested `@on click`'s ALREADY-CORRECTLY-COMPILED mutation body
into `@object`'s sibling `%binds three-object(...)` primitive call as a
param — the `@on` child's own macro form (`on-mutation-dispatcher-simple`)
already compiles its body correctly (`{js_statements:[...], macro_calls:[]}`
via the trailing-body `mutation_actions` capture path,
`src/syntax/events/form_compiler.rs` ~line 1472); the gap is PURELY that
nothing lets `@object`'s `%binds` reach into its `$children*` Block and pull
out "the compiled output of whichever child matched `@on click`".

* Why this generalizes beyond FEAT-152
This is a real, reusable metasystem gap, not FEAT-152-specific: ANY macro
that accepts arbitrary `$children*` (procedural composition, e.g. `@object`,
`@stage` itself, `dnd`'s `@drop-zone`) has no way to special-case ONE
specific child directive among its children and route its compiled value
to a `%binds` param. Today the only two body-capture shapes are (a) render
ALL children uniformly via `%template { $children }`, or (b) a SEPARATE
named-param-in-parens capture (which, per FEAT-152's finding, does NOT get
the trailing-body-only structured conversion for capture types like
`mutation_actions` that need it).

* Design sketch (starting point, not a final answer — needs a plan pass)
A new `%derives`-like clause or `$children*` sub-capture syntax:
#+begin_src
%form {
  @object(...) {
    $children*
  }
}

%derives {
  $onClickBody: $children | find(@on, event: "click")
}

%binds {
  three-object(&self, ..., onClick: $onClickBody)
}
#+end_src
Or, simpler: a capture-type MODIFIER on `$children*` itself —
`$children:children(exclude: [on])` to split "renderable children" from
"special-cased directives" — then a second capture
`$onClick:mutation_actions? from $children[on click]` reads directly. The
EXACT grammar is an open design question; whichever shape wins should reuse
the EXISTING `$children*` Block infrastructure (never re-parse child source
text) and the EXISTING `mutation_actions` structured-conversion logic
(`js_statements`/`macro_calls`) already proven correct at the trailing-body
site — don't invent a THIRD way to produce that shape.
