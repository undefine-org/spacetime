* Items (each independent)
1. ENVELOPE ALIAS left of `to`: `receive Response to AddResult { … }` — the optional
   envelope alias (cosmetic; @host fixes the envelope type, so the alias only buys
   `Response.status` self-doc). Dropped from recv_head in W1 because an optional
   LEADING capture inside a capture-type grammar (`( $alias:ident )? "to" $sum`) didn't
   compile cleanly. Revisit the capture-grammar's optional-leading handling, then
   restore `( $alias:ident )?` before `"to"` in receive_block/handle_receive. §S1
   POSITION DECIDES ROLE: name LEFT of `to` = envelope alias; RIGHT = sum.

2. WS TRANSPORT in signal-call: only HTTP is wired (stdlib/primitives/signal.st). Add
   the ws path — resolve @host ws($sock), send `{ type, payload }` over the socket,
   correlate the reply by a runtime-invisible correlation id (≈ makeAff fiber), route
   to the receive arms by message `type`. The @host ws envelope = Message{type,payload}.

3. POLICY threading: the policy mode ($mode) is captured but not threaded to runtime
   (signal-call defaults policyMode='latest'). Wire queue/parallel/drop + the optional
   `timeout T` / `retry n` tails (policy_clause already parses them).

4. @host RUNTIME registration: @host currently only %registers a fact. For signal-call
   to resolve `window.__stHosts[key]` at runtime, @host must EMIT JS that populates
   __stHosts with { url, headers } (or { socket }). Add a host %primitive (sibling of
   dev-ws) bound by @host, OR have signal-call read the registered host fact at compile
   time and inline the config. Decide which is harmonious.

5. SCOPED-SUM registration from receive arms (§S1 TYPE CREATION): `receive to AddResult
   { … }` should DEFINE a named sum `AddResult` in the signal's scope (arms ARE the
   variant definition). Today the arms are captured but not reified into a named registry
   sum. Reuse the W0 sum-@type variant-gathering (TypeRegistry) to register the scoped
   sum, so reference.st / the MCP registry can introspect the response interface.
