* Goal
`stdlib/3d` (vendored three.js, ~0.82MB) MUST require an explicit `@import "stdlib/3d"`
and MUST NOT be pulled in by the default prelude / `stdlib/index.st` auto-imports. A page
that never touches 3D must ship ZERO bytes of three.js.

* Why
three.js is by far the heaviest stdlib dependency. The whole point of the demand-driven
%vendor emission (lean law) is that the engine ships only when a 3D primitive actually
fires. But if `stdlib/3d` is ever added to the always-loaded prelude (the way text/responsive
macros are), then merely being in the registry risks: (a) the %vendor being registered on
every page, and (b) future refactors accidentally tree-including it. Keep 3D strictly opt-in.

* Current state (PLAN-050, 2026-06-20)
- `stdlib/index.st` was EDITED to REMOVE the old `@scene`/webgl auto-imports and explicitly
  does NOT import `stdlib/3d` — it carries a note: "3D is now an opt-in module, pulled in
  with `@import \"stdlib/3d\"`". So today 3d is already opt-in by omission. GOOD.
- Verified by the Rust emit test `three_unused_module_ships_no_engine`: a page that imports
  stdlib/3d but renders no 3D directive ships no WebGLRenderer/THREE bytes (lean law holds).

* What this FUP must guarantee (make it STRUCTURAL, not just "by omission")
1. Add a guard test: compile a MINIMAL page that imports NOTHING 3d (e.g. just
   `body { color: red }` with the default prelude active) and assert the emitted JS contains
   no `WebGLRenderer` / `THREE.REVISION` / `three.bundle`. This locks the prelude boundary so
   a future prelude edit can't silently pull in three.
2. If/when a prelude or "kitchen-sink" stdlib aggregate import exists, confirm `stdlib/3d` is
   explicitly EXCLUDED from it and documented as opt-in (mirror how heavy optional modules are
   treated).
3. Document in stdlib/3d/MODULE.st (already states opt-in) + stdlib/AGENTS.md that 3d is
   never auto-loaded.
