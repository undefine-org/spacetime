* Context
W1 of editable-everything (commit 7b2fb1ba) shipped the on-page STRUCTURED rich-text
surface: @richtext renders a published page that reads as a blog and edits in place
(gate:edit-mode + the schema bake). Typing routes beforeinput → AST op → reproject, and
the surface stores the doc AST on the host (host.__stDoc) + fires a bubbling `input`
event (editable-surface.st publish()) — exactly the hook the admin's @on input uses to
send EditJson.

* Gap
On a PAGE (not the admin drawer) nothing LISTENS for that input event, so an on-page
edit updates the live doc + DOM but is NOT persisted back to the data file. The admin
wires `.ad-form @on input [data-path] → ST.adFieldInput → EditJson → dev-ws → disk`;
a page has no equivalent. The round-trip is open at the last hop.

* Fix (small, reuses everything)
Add a default persist listener for @richtext hosts on a page — when edit-mode is on and
a `[data-st-editable]` host bound to a `$`-path fires `input`, send an EditJson patch for
that data path (the host already knows its bindPath; the doc AST is host.__stDoc). This
is the page-side analogue of adFieldInput. Likely a small primitive in stdlib/editable
(or fold into @edit-toggle / a new @editable-persist that the page includes), riding the
existing dev-ws + EditJson + server schema-validation + sanitize path (no new channel).
EditJson already validates the doc against the editable schema server-side (FEAT-099).

* Acceptance
Edit a paragraph on the editable-blog demo with edit-mode on → reload → the change
survives (written to the post's data file). A headless/CDP test drives an input on a
$-path @richtext host and asserts an EditJson message was dispatched with the doc AST.
