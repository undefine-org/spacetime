* The reframe (the key insight)
Earlier design proposed rich text as "an html5ever document tree + bespoke Spacetime
traits, serialized over the wire," implying (a) a NEW wire schema and (b) a NEW
sanitizer. The user asked the decisive question: *what is the difference between that
and a Spacetime AST stripped of =%=-directives, with an allowlist/denylist?*
ANSWER: none — the AST framing is the correct primitive. The html5ever-tree framing
was over-engineering a thing the IR already is.

* The key fact (verify)
Spacetime ALREADY parses HTML into its own IR via an html5ever custom TreeSink:
- src/html/treesink.rs:1 — "html5ever custom TreeSink → ir::HtmlExpr"
- src/ir/code.rs:299 —
  =HtmlExpr = Element{tag, attrs: Vec<(String, Vec<AttrPart>)>, children} | Text(String) | Hole(JsExpr) | Raw(String)=
- =AttrPart= (src/ir/code.rs:316) = =Lit(String) | Hole(JsExpr)= — so =src=$.image=
  (literal+hole+literal) round-trips losslessly.
∴ html5ever is NOT a parallel tree; it is the front-end that PRODUCES the HTML portion
of the Spacetime AST/IR. The "traits" the earlier draft invented (a =@scroll= on a
quote, a =$binding= on an image src) ARE just AST nodes (an Element with a directive
child; an AttrPart::Hole). ∴ Rich text = a Spacetime AST subtree, CONSTRAINED by an
allowlist/denylist of node kinds.

* Scope
1. Define the rich-text POLICY as an allowlist/denylist over AST/HtmlExpr node kinds
   (and attributes):
   - ALLOW structure: h1 h2 h3, p, ul/ol/li, blockquote, img, a, figure/figcaption
   - ALLOW inline marks: strong, em, code, br  (the "hard 20%" — native AST, free)
   - ALLOW Spacetime: AttrPart::Hole ($.field bindings); a curated set of motion
     directives on blocks (@scroll/@reveal) — "animatable prose"
   - DENY: %primitive, %emit js, %macro, <script>, <style>, <iframe>, on* event attrs,
     javascript: URLs, form controls
2. Decide & implement WHERE the policy is enforced. Likely all three:
   (a) admin editor only OFFERS allowlisted kinds (UX),
   (b) server VALIDATES an incoming EditAst body against the policy before persisting
       (SECURITY-BEARING — mandatory),
   (c) the compiler/TreeSink already rejects =%=-directives in this context.
3. Add a =richtext= type signal: a field typed =richtext= tells the admin "render the
   block editor for this allowlisted-AST field." Smallest form: a new primitive type
   name; alternatively a Reference to a built-in.
4. Storage locus: inline serialized AST subtree in the entry JSON, vs a sidecar
   .st/.html fragment addressed by provenance (data-st-id/origin). Inline = simple,
   one file; sidecar = cleaner git diffs + reuses provenance addressing. Provide a
   recommendation; do not pre-bake.

* What this explicitly does NOT need (consequences of the reframe)
- NO bespoke document wire schema — reuse the EXISTING AST/JsonValue serialization that
  EditAst already round-trips (src/sync/protocol.rs, handle_edit_ast; user confirms
  EditAst is "taken care of"). Schema work shrinks to "define the allowlist."
- NO bespoke regex sanitizer — sanitization IS the denylist (a node-kind filter over
  the AST). Honours AGENTS.md: don't write a Rust HTML parser/fallback; the metasystem
  is self-describing; the list is the policy. (The seed =__stSanitizeContentHtml= in
  stdlib/__dev__/primitives/dev-save.st is the regex stopgap to replace.)
- NO object-union TypeExpr for blocks — blocks are AST nodes, not union variants.

* Dividends to preserve (do not regress)
- inline marks native (<strong>/<em>/<a> are ordinary Element nodes).
- animatable prose (a block Element can carry an allowlisted @scroll/@reveal) — no CMS
  has animated structured content; their rich text is inert.
- $data bindings in prose via AttrPart::Hole (<img src=$.image>).
- provenance addresses every node (docs/CONTENT_EDITING.md) — editing round-trips.
- the block-type menu IS the allowlist; allowlist a new node kind (or register a block
  @template) → it appears in every writer's menu. Extensible by editing a list /
  declaring a type — never by editing the editor. The metasystem dividend, on prose.

* Open questions
- Where exactly is enforcement centralized (editor/server/TreeSink)? Server is the
  security-bearing point.
- inline vs sidecar storage (Q7).
- distinct =richtext= TypeExpr vs Reference to a built-in (smallest viable signal).

* Acceptance
- A documented allow/denylist policy exists, with the enforcement point(s) chosen.
- Server REJECTS a denylisted node (e.g. <script>, %emit) in an EditAst rich body with
  a clear Reject reason; ACCEPTS an allowlisted body.
- A field typed =richtext= drives the admin to render the block editor.
- A rich body with =<strong>=, =<a>=, an =<img src=$.image>=, and a block-level
  @reveal round-trips edit→persist→render.
