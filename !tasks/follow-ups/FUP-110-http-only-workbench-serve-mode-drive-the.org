* Initial Message

Verifying the live workbench today requires the FULL MCP server (`spacetime mcp`), which couples the HTTP live surface (the region pipeline + workbench host page + signal sink) to the MCP stdio JSON-RPC transport. That transport is harness-managed (one long-lived process, in-process compile), so:
- an agent cannot spin up a throwaway instance to drive with puppeteer without either racing the harness process or reimplementing the whole MCP handshake;
- a stale in-process binary (compile happens in-memory) means on-disk rebuilds don't take effect until a harness-managed restart;
- there's no way to exercise the live HTTP surface in a test/automation loop WITHOUT the MCP part we don't need for UI-driving.

** Ask
Add an HTTP-only serve mode that boots the SAME live surface (LiveServer / region pipeline / workbench env.st host / /__mcp/instance/{id}/ + /bundles + /__mcp/signal/{id}) on a chosen port, WITHOUT the stdio MCP transport. Something like `spacetime workbench-serve --port N` (or `spacetime mcp --http-only --port N`). Then st_fn_put/st_mount-equivalent operations are driven over plain HTTP (or a small seed file), and an agent/CI can launch its own instance, compose a guest, and drive it with puppeteer deterministically.

** Why it matters (surfaced during PLAN-065)
The whole reason the prior "live verification" degenerated into calling handlers directly + synthetic events was that the real server was unreachable/stale and un-launchable independently. A driveable HTTP-only mode makes real end-to-end click-through the DEFAULT verification, not a fallback. Also unblocks docs/testing/AUTOMATION.md driving the workbench with @drive against a self-launched instance.

** Acceptance
`<serve-cmd> --port N` serves a working workbench instance an agent can open in a browser, compose a registered/inline function onto the stage, and drive with real clicks — no MCP stdio client, no harness process. Document the invocation in docs/testing/AUTOMATION.md.
