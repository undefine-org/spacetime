* Symptom
A bare identifier passed to a NAMED `:string` macro argument (`@mm(mode: hello)`) makes the
whole page's runtime JS emit empty (HTTP 200, 0 bytes). Quoting works (`mode: "hello"`).
`cargo run -- check` passes either way — silent, no diagnostic. Reproduced minimally
(2026-06-20) with a trivial `%macro mm { %form { @mm(mode: $mode:string) } }`, independent
of stdlib/3d.

* Contrast: leading-token capture accepts bare idents fine
`@object $shape:string(...)` and `@light $type:string(...)` (stdlib/3d) capture a LEADING
bare keyword (`@object icosahedron`) and emit correctly. Only NAMED string args
(`key: bareident`) break. So the form-pattern leading capture and the named-arg capture
diverge for the same `:string` type — a sigil-harmony gap.

* Impact / why it matters for ergonomics
Enum-ish params read best unquoted (`material: glass`, `tone: aces`, `drive: morph`).
Today authors MUST quote them or the page silently goes blank. stdlib/3d (PLAN-050) works
around it by (a) using leading-token for the main discriminant and (b) quoting other
string args in showcases. The proper fix unlocks the nicer unquoted surface.

* Wanted
Either: (1) accept a bare ident as a string literal in named-arg position (preferred —
matches leading-token behavior, one rule), OR (2) hard error at compile (E-code) so it's
never silent. A first-class enum/choice capture type (cf. FUP-074) would also resolve it.
Needs a failing test (bare-ident named string arg -> non-empty emit OR diagnostic).
