* Context

PLAN-122 §Unlocks item 3. Contrast ratio is computable from two TYPED colours; it is not computable from two opaque strings. src/analysis/visual_lint.rs already gropes toward this with its own hex-scanning classifier (one of the five shadow value-classifiers named in PLAN-122 / FEAT-109).

* Change

With `@type Brand { ink: color; bg: color; ... }` typed and parsed, a lint pass computes over VALUES rather than text:

- WCAG contrast: `ink` on `bg` at 3.1:1 → diagnostic "below 4.5:1 for body text" with the span of the offending token, plus the nearest passing value as a suggestion.
- Token-set conformance: a colour literal used in a declaration that is NOT in the brand token set → warning ("use $brand.ink or add it to the type").
- Scale conformance: 13px on an 8px spacing scale; a font size off the type ramp; a duration off the motion scale.

The scale/ramp/token-set are DATA the project already declares (its @type + tokens) — the lint reads them, it does not carry its own config.

* Why this is distinctive

Every other stack needs a separate linter with a parallel config file that drifts from the design tokens. Here the tokens ARE the type, so the check has no second source of truth to disagree with. Accessibility becomes a property of compilation.

* Edge

- Severity default: warning, not error (a deliberate low-contrast decorative case must be expressible) — with an explicit opt-out marker rather than a magic comment.
- Only decidable for STATIC pairs; reactive values ($brand.ink under a theme signal) check every declared theme, or report "not statically decidable" rather than guessing.
- Dynamic captures (calc/var/color-mix) are exempt by construction (PLAN-122 tier-b).
