Surfaced by PLAN-005 W3-2 (2026-07-20): the ratified Deploy Protocol v2 design has the browser widget upload large blobs directly to R2 via per-blob presigned PUT URLs returned at push time. This is NOT expressible in Spacetime today: @data fetch/signal targets are literal URLs in the source — a URL carried in a signal (fetched at runtime from push-v2/start's pending[] list) cannot serve as a fetch target, and the "zero custom JS" rule forbids hand-written fetch() in a .st site.

Current workaround: the dev server's grace timer (W3-1, src/host_push_v2.rs) performs the large uploads itself — still direct-to-R2 over presigned URLs, so the orchestrator never transits large blobs; only browser-side parallelism is lost.

What's needed to unblock the ratified design (one of):
1. Dynamic fetch targets: `@data fetch $urlSignal` where the URL comes from a runtime signal (reactive-source already re-fetches on URL signal change — the gap is an imperative "PUT these bytes to that URL" action).
2. An upload primitive: `%primitive upload(url: string, body: bytes)` with the same vendored-rail discipline as event-source, so an @each over pending[] can drive per-blob PUTs with per-entry progress.

Constraint either way: the primitive must report per-blob progress so the pill stays live, and must not bypass the "the widget never talks to the orchestrator" rule (presigned R2 URLs are exempt — scoped one-key capabilities, ratified 2026-07-20).
