* Context
FEAT-153 shipped `ctx.resolveReactive` (stdlib/3d/primitives/three-stage.st)
and wired it into `@gltf`'s `src` param only, deliberately scoped to the
concrete FEAT-151 blocker. This follow-up extends the SAME proven mechanism
to `@object`.

* Straightforward part: roughness / metalness
Both are plain `number`-typed params (same class of BUG-159 capture-type gap
as `@gltf`'s `src` — `NumberExtractor` also rejects a `$`-prefixed token).
Fix shape, mirroring what already shipped:
1. `stdlib/3d/macros/object.st`: change `roughness: $roughness:number` /
   `metalness: $metalness:number` captures to `:expr` (accepts literal OR
   `$signal`).
2. `stdlib/3d/primitives/three-object.st`: keep the PRIMITIVE param types as
   `number` (mirrors `three-gltf.st`'s `src: string` staying `string` even
   though its macro capture is `:expr` — the primitive receives the raw
   text, a literal number OR `"$sig"`, and resolves it itself).
3. Restructure material creation into a `rebuildMaterial()` closure (parallel
   to `three-gltf.st`'s `load()`) that disposes the OLD material
   (`mat.dispose()`) and constructs a new one with the current
   roughness/metalness values, called once via
   `ctx.resolveReactive(rawRoughness, (v) => { roughness = v; rebuildMaterial(); })`
   and again for metalness (or a combined resolver reading both — avoid
   double-rebuilding on simultaneous changes if both are reactive).

* Harder part, needs its own design pass: color / emissive
`color: $color:color` / `emissive: $emissive:color` currently read via a
COMPILE-TIME `%color.rgba` field accessor (`src/emit/js.rs::apply_param_field_accessor`,
the `(Some("color"), "rgba")` arm) — this parses a color string to normalized
RGBA at RUST COMPILE TIME, which is fundamentally incompatible with a runtime
signal value (the compiler can't know a signal's future value ahead of time).
Making `color`/`emissive` reactive needs a RUNTIME color-parsing path (JS-side
hex/named-color -> RGBA, mirroring `src/color.rs`'s Rust parser logic in JS,
or exposing a `ST.parseColor(str)` runtime helper the primitive calls instead
of the compile-time `.rgba` accessor when the captured value is a `$signal`
reference). Investigate whether a JS-side color-parse helper already exists
in `public/runtime/st.js` before writing a new one (unlikely, but check —
duplicate logic between Rust and JS color parsing is exactly the kind of rot
`stdlib/AGENTS.md`/repo elegance-bar discipline flags).

- `@object(color: $liveColor)` — file a DESIGN note (not a hasty

  adds a parallel color-parsing implementation).
