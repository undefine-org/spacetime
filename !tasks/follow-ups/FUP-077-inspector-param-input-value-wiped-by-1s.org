* Summary
The inspector's param-input row is re-rendered every ~1s when the host page polls
input.json and the contract_params @each re-runs. If the user is mid-typing (has
not yet fired `change` via blur/enter), the re-render WIPES the in-progress value
back to empty/seed. The commit only lands if the user types + blurs FAST. A
property panel that erases what you're typing mid-keystroke isn't Framer-grade.

Verified round-4: synthetic value-set + change landed server-side ("name=Trusted"
in the bundle), but a slower type-then-blur read back empty because the poll
re-rendered the input between keystroke and blur.

* Direction
- Don't re-render a param input that currently has FOCUS (skip the @each row
  rebuild for the focused control, or reconcile by key instead of replace), OR
- Bind the input value to a LOCAL signal that the poll does not overwrite while
  the field is dirty/focused (a dirty-guard mirroring BUG-114's isTrusted guard
  on the source editor), OR
- Debounce/skip the contract_params re-render when a param input is focused.

Prefer focus-aware reconciliation (don't rebuild the focused control). This is the
same class as M6's source-editor self-mutation (BUG-114) — hydration/poll vs. live
user input — so the fix should rhyme with that guard.

* Acceptance
- Typing a multi-character value into a param input at normal speed (with poll
  running) preserves the full value; commit on blur applies it to the guest.
- The guest still live-updates on commit (no regression to the M4 loop).
- No spurious mcp_param writes from the poll re-render (mirror BUG-114).
