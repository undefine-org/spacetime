Oracle-flagged during PLAN-065 W_commit scoping (agent://25-ValidateWcommitScope). The single genuine escalation-case risk under the new client-owned editor model.

** Risk
mcp_node_param (the SELECTED-node param editor, the G2 source-WRITE rail) carries frozen span_start/span_end from $activeParams (projected at selection time, PLAN-065 W_session). If the guest SOURCE changes while a node-param row remains selected (e.g. an agent st_fn_put / a source edit / a recompile), a later commit addresses a STALE byte span -> patches the wrong bytes.

Under the current SINGLE-USER design-tool assumption this is exceptional (the human is the only editor; agent/server edits to the exact selected node's source while the inspector is open are not a normal workflow), so it is NOT built now (elegance bar: no reproduced incident). But it is the strongest case for a targeted server-side guard.

** Fix (when earned)
On mcp_node_param, send {node_id, revision, span_start, span_end}; the server rejects a stale/mismatched span (function revision + span validation) instead of patching. Keeps span as the write address; adds a safety check, no client reconciliation system. This is a SERVER-side source-revision guard, NOT a broad optimistic-reconcile plane.

** Escalation triggers (oracle)
- A real workflow has another actor/action changing the same selected field/source while the inspector is open, and it causes a stale-span write in practice.
- Multi-editor / collaborative workbench instances become a requirement (then revisit the whole state model; baseRevision/CRDT may be justified).
