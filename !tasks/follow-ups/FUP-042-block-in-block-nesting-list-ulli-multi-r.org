The editable AST model (public/runtime/editable.js) currently has a FLAT block
model: doc → Block[] → Inline[]. Two constructs need a deeper model:

1. LIST nesting (ul>li, ol>li, nested lists): a block that CONTAINS blocks. The
   position model (ProseMirror integer positions, docSize/resolve) assumes one
   level of block nesting; a list needs recursive block content + the position
   bridge (posFromDOM/domFromPos) extended to descend.
2. MULTI-REGION blocks (&columns(&left, &right), &figure with editable caption AS
   a nested editable region): blocks with MORE THAN ONE selection hole. The
   schema/invertibility check already allows exactly-one &sel; multi-region needs
   each &hole to be its own nested editable region with its own position subrange.

Both are the "deferred hard part" called out in PLAN-031 round 3. The flat model
covers paragraphs, headings, blockquote, figure (single nested caption),
code blocks + all inline mark nesting — the 90% case. Lists + columns are the
remaining 10% and need the recursive position-map work.

Approach when picked up:
- generalize Block.content to allow Block[] | Inline[] (a `blocks` vs `inlines`
  content kind per block, from the schema)
- make resolve/docSize/posFromDOM/domFromPos recursive over the block tree
- extend liftHtml to recover ul>li nesting
- @property fuzz: nested op sequences keep the tree valid + positions monotone
