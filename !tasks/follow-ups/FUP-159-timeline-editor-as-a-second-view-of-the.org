* Context

PLAN-122 §Unlocks item 1. stdlib/macros/score.st (PLAN-128 W4) states the design intent verbatim: "the trailing words are exactly the surface a timeline editor drags, so dragging a clip's edge rewrites `in 4s` to `in 5.2s` in the source. The editor is a second view of the language, not a layer over it."

That rewrite is EditAst over a TYPED LITERAL. It is the identical mechanism as the cms-testbed Brand colour picker (PLAN-122 W2 / FEAT-166 demo): a UI gesture rewrites a typed literal in place, in source, and the file stays the database.

* Blocked on

FEAT-165 (W1) — `score_measure` composes `length`/`duration`; while those are Rust extractor terminals the editor must regex the source to find the span to rewrite. With typed capture spans, `at 2s` has a structural span the editor addresses directly.

* Scope

- Editable-span protocol: a typed literal capture exposes {span, type, current value} to the editing surface (shared with FEAT-107 widget mapping — ONE affordance, not a timeline-specific one).
- Drag → rewrite `at`/`for`/`in`/`out` measures; snap to the driver's domain (PLAN-128 R1: a `&.scroll` score measures in %, a `&.time` score in s/ms — the registry already declares the domain).
- Round-trip guarantee: editor output MUST re-parse (the widget↔parser round-trip property from PLAN-122 §Novelty — the picker and the grammar come from one %scalar_type entry, so a produced value cannot fail to parse).

* Why one mechanism, not three

The colour picker (FEAT-107), a spacing stepper, and the timeline scrubber are the SAME operation on three scalar types. If this ships as timeline-specific code it will be the fourth shadow implementation of "edit a literal in source". Build it as the editable-span protocol; the timeline is its first consumer.
