* Idea (user)
"Parameterised scopes — e.g. let certain %macro scopes only apply within other named scopes."

Today scope is BINARY: macro_scope_matches (src/metasystem/registry.rs:764) keys on
None→File / Some(selector)→Selector; a macro declares `%scope file | selector`. There is no
way to express "this macro is valid ONLY inside an @each body / a template scope / a named
scope X." Generalise scope to a (kind, name, params) identity in the containment tree the
matcher ALREADY walks (assign_match_to_nested_scopes), and let a %macro declare a scope
RESTRICTION, e.g. `%scope within(template)` / `%scope within(each)`.

* Why it matters (ties to PLAN-039)
PLAN-039 makes a template body a SCOPE. It needs, MINIMALLY, a scope identity richer than
"Selector" (a param environment + a template kind). That minimal form is IN PLAN-039. The
GENERAL form here would let MORE component_body special-cases die into the scope mechanism:
- @exports (template-only) → "a macro scoped within(template)" instead of a component_body field
- &ref.$count cross-instance access, &cards[] collection refs (template-component-model.org)
  → macros valid within(template)/within(each), not bespoke fields
So parameterised scopes could make the PLAN-039 break CLEANER (more deletions), not wider.

* The ELEGANCE BAR (fold into PLAN-039 only if ALL hold; else ship PLAN-039 minimal + do this later)
1. Expressible as a SMALL extension of the existing %scope grammar (`%scope within(<kind>)`),
   no new subsystem.
2. macro_scope_matches generalises from a 2-case match to a containment-tree query with the
   scope KINDS as DATA, not a Rust match arm per kind.
3. It DELETES at least one existing special case (target: @exports's component_body field) —
   proof it REDUCES net complexity.
4. Testable by the SAME scope-assignment machinery: a macro scoped within(each) MATCHES inside
   an @each scope and is REFUSED outside (a parse diagnostic), gated by a unit test.

If any fails → this stays a separate arc AFTER PLAN-039. If all pass → adopt as a PLAN-039 wave
(it strictly improves the refactor's cleanliness, the user's stated condition).
