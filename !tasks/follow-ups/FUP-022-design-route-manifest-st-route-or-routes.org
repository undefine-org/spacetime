* Intention & Purpose

Once filesystem discovery works (BUG-025), some sites will want *explicit* control: virtual routes, redirects, route metadata (title, locale set, doctor budget, prerender hints), and a single source of truth that =build=, =serve=, and =doctor= all agree on. This FUP commissions the architectural decision: do we extend =index.st= with a =@route= form, or introduce a sibling =routes.kdl=, or both? And how does explicit declaration interact with implicit discovery?

* Scope

Dispatch a subagent (code-architect or plan) to produce a design doc covering:

1. *Format choice*: =@route= directive inside =index.st= vs. =routes.kdl= sidecar. Tradeoffs: discoverability, parser ownership, KDL dep cost, ability to express non-HTML routes (data endpoints, locale variants).
2. *Schema*: path, source file, layout/template, locale set, status (=draft= / =published=), redirect target, prerender flags, per-route bundle policy.
3. *Precedence model*: when both manifest and filesystem are present, who wins? Default: manifest is authoritative if present; otherwise fall back to BUG-025 discovery. Document the failure mode when a manifest entry points at a missing file vs. when a file has no manifest entry (warn? error? include?).
4. *Integration points*:
   - =build= → ExportReport reflects manifest source.
   - =serve= → router resolves URLs through the same manifest layer (today =serve= compiles per-route on demand from filesystem).
   - =doctor= → iterates manifest routes for headless checks.
   - =inspect= → new layer? Probably yes: =--layer routes=.
5. *Migration*: how do =projects/unkn/= and =projects/undefine.org/= adopt this without breaking existing deploys.

* Deliverables

- Design doc under =@tasks/drafts/= (or =!tasks/drafts/=).
- A follow-up PLAN item with concrete implementation tickets and an Execution Manifest.
- Optional spike: prototype parser + 1 fixture site.

* Acceptance

- Design doc reviewed; format decision made with explicit rationale.
- PLAN item created, linked back to this FUP.
- Existing projects have a documented migration path (or a tool to generate the manifest from current filesystem layout).
