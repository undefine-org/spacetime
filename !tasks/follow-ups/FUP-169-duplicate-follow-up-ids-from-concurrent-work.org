** The claim was false

This item claimed follow-up IDs were colliding: that four files "claimed two
ids", that four older pairs (138, 139, 151, 152) proved the problem was
chronic, and that an allocator race needed a validation gate.

NONE OF THAT WAS TRUE. Measured:

- A follow-up's =CUSTOM_ID= is the FULL =FUP-<n>-<slug>=, not the bare number.
  173 of 181 files follow this; the deviations are almost all mine.
- Checking for genuinely duplicate =CUSTOM_ID= values across the whole
  directory returns ZERO.
- So =FUP-138-a-build-time-file-read-that-fails-should= and
  =FUP-138-primitive-exports-never-reach-file-sco= are DISTINCT ids that share
  a numeric prefix. Nothing is ambiguous. Nothing needs renumbering.

The number is a chronological prefix, not the identity. Two items filed at the
same time sharing a prefix is exactly what the scheme permits.

** How the mistake was made

The check was =ls | grep -o "FUP-1[0-9]*" | sort | uniq -d= — which truncates
every filename to its numeric prefix and then reports prefix collisions as
duplicates. It measured the truncation, not the ids. The tool answered the
question it was given and the question was wrong.

Worse, the "evidence" was self-reinforcing: finding four more prefix pairs felt
like confirmation, so a false premise got promoted from "a collision happened"
to "collisions are chronic and invisible". The right move at the point of
surprise was to check what an ID ACTUALLY IS, in a file, before scaling the
claim. Reading a single =CUSTOM_ID= line would have ended it.

** Damage, and what was done about it

REAL CHANGE MADE ON A FALSE PREMISE: FUP-166 and FUP-167 (the comments picker
and the parser fix) were renumbered to FUP-171 and FUP-172, with references
rewritten across =parser.rs=, =mcp/tools.rs=, =comments/tests.rs=, =main.rs=,
=server.rs=, =pick.st=, =locate.st=, =pill.st=. Commits =8f0ff3b9=, =17e0e952=.

That renumbering was UNNECESSARY. It is NOT being reverted: the new ids are
already referenced from source comments and commit messages, and a second
rename to undo a first would add a third set of stale references to a problem
that does not exist. The tombstones in FUP-171/172 already explain the history.

ALSO FIXED (a real, if minor, defect this exposed): five of my follow-ups used
a BARE =:CUSTOM_ID: FUP-170= instead of the =FUP-<n>-<slug>= convention every
other file uses. Those are now conventional, so an =org= lookup resolves them
the same way as everything else.

** What to actually take from this

Nothing to build. The lesson is procedural and belongs in review, not in a
backlog item:

VERIFY WHAT A THING IS BEFORE MEASURING HOW OFTEN IT IS BROKEN. A grep that
truncates its input will happily report a pattern in the truncation. This is
the third factual error in this stretch of work — "replies aren't built",
"agents cannot reply", and now this — all with the same shape: asserting from
NAMES and SHAPES instead of reading the artifact.

This file stays as the record. Do not implement W-a..W-d; they described work
for a problem that was never there.
