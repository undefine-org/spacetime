* Summary
Both the workbench host page and standalone instance pages render a BLANK body
until the first 1s input.json/bundles poll resolves. The headless driver needed
an explicit networkidle2 nav to capture anything; a real user sees a flash of
empty espresso background on every load. Squarespace/Framer/Figma never flash
blank — first impression matters for the "studio" feel.

Verified round-4: inst-2 (standalone) `document.body.innerText.length === 0` on
first paint; populated only after a ~800ms-2000ms wait. The autostage <main> +
<script> are present in HTML, but the region content mounts only after the poll.

* Direction (not a new subsystem)
- Server-render the FIRST frame of the shell (the chrome: wordmark, edges, empty
  stage) so the page is never empty, OR
- Render a warm skeleton (a few shimmer blocks in the stage) that the first poll
  replaces, OR
- For autostage standalone pages: server-render the &main invocation inline (the
  contract + bundle are known at request time) so the content is in the initial
  HTML, with hydration taking over — removes the poll-to-first-paint gap entirely
  for the standalone case.

Prefer the last for standalone (the data is available server-side at
instance_page time); a skeleton is the floor for the polling host page.

* Acceptance
- Loading any MCP instance page shows non-blank content in the initial HTML
  response (chrome or skeleton), verified by fetching the page and asserting body
  is non-empty BEFORE any JS/poll runs.
- No regression to the live poll/hot-swap loop.
