* Context

PLAN-121 W2 review found BUG-245: =@form= kind inference does not discriminate.
Two macros declaring the same surface with different body capture types
(=$body:properties= vs =$frames:keyframes=) both accept the same input; the
matcher takes the first successful body-consuming candidate
(src/syntax/events/match_sink.rs:164), equal-permissive body types tie on
specificity (src/syntax/registry.rs:103), and =keyframes= accepts any nonempty
body as raw text (src/syntax/events/form_compiler.rs:1509). "Kind inferred from
body" was registration order in disguise.

User decision (2026-07-26): SIP-001 ships an EXPLICIT KIND MARKER on =@form=
declarations. This FUP is the research spike for restoring inference LATER, on
solid foundations.

* Research question

Can lightningCSS (already the model for "vendor + own behind a primitive", cf.
snarkdown in stdlib/md) parse a form body and classify it into the SIP-001c kind
vocabulary — style | value | motion | easing | score-fragment | markup — with
enough reliability to drive inference?

Specifically investigate:
1. Which lightningCSS parse entry points discriminate these bodies
   (DeclarationBlock vs StyleRule vs keyframes parsing)?
2. Whether Spacetime-only bodies (=->= chains, score lines, =easing:= slots)
   have any CSS parse at all — likely NOT, so inference would be partial by
   construction. What is the fallback story for the Spacetime-native kinds?
3. Cost of vendoring lightningCSS behind a compile-time-only primitive.

* Hard constraint (user ruling)

Even IF inference works: an uninferrable body is a COMPILE-TIME ERROR, never a
silent default. Inference is a convenience layered on the explicit marker, not
a replacement for it. The marker grammar must remain valid and accepted
forever — inference only ever makes the marker OPTIONAL where the body is
unambiguous.

* Acceptance

A written report in docs/research/ answering (1)-(3) with a prototype
classification of the six SIP-001c example bodies. NO production changes.
Reopening SIP-001c's kind-inference section requires the report AND a user
decision.
