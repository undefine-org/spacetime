* Problem
The CST lexer (src/syntax/cst/lexer.rs) tokenizes `'`/`"` strings as single STRING
tokens (so their contents, including braces, are opaque), but has NO token for:
- TEMPLATE LITERALS (backtick `` `…` ``) — backtick lexes as an unrecognized/ERROR char,
  and the template's contents (including `${…}` interpolation and any literal `{`/`}`)
  lex as ordinary tokens.
- REGEX literals (`/…/flags`) — `/` lexes as Slash; regex body lexes as ordinary tokens.

∴ a literal brace inside a template or regex becomes a real L_BRACE/R_BRACE token. This
corrupts any consumer that balances raw braces — notably parse_arrow_fn_balanced (the
BUG-095 fix): an arrow @eval body like
  @eval (() => { el.innerHTML = `<b>}</b>`; })
  @eval (() => { s = s.replace(/}/g, ''); })
mis-counts brace depth → the body terminates early (reviving the BUG-095 spill) or
over-consumes to EOF.

* Severity
P2-latent. Reviewer (BUG-095 review, agent 16, conf 0.7) flagged it. NO current `.st`
arrow payload uses a template/regex with an unbalanced-looking brace (the editable tests
avoid them), and the BUG-095 fix strictly improves on the prior fully-broken behavior —
so it's a bounded limitation, documented in parse_arrow_fn_balanced's doc-comment, not a
release blocker.

* Fix
Teach the lexer a TEMPLATE_STRING token (backtick-delimited, callback-scanned like the
quoted-string callbacks) so a template's braces are opaque. Template literals legitimately
span NEWLINES and nest `${ … }` (balanced interpolation that itself contains real tokens) —
so this is more than the single-line string callback (mind BUG-072: the single-line rule
exists so a lone quote in HTML prose doesn't swallow the file; backtick is far rarer in
prose, but the callback should still bound runaway). Regex is genuinely ambiguous (`/` =
divide vs regex-start) and lower-value; can be deferred or handled with a heuristic
(regex only after `(`,`,`,`=`,`return`,`=>` etc.).

* Provenance
Surfaced by the BUG-095 reviewer. The arrow-body brace balancer counts raw braces; the
real fix is at the lexer (opaque template/regex spans), not the balancer.

In Spacetime the backtick is THE HOLE SIGIL (AGENTS.md: "=`= is THE hole form
everywhere"). The corpus has *4,934* of them. A token consuming one backtick to
the next swallows every hole in the language.

** The structural fix (commit 71de8e55)

The item mistook a SIGIL for a DELIMITER. Every other sigil in this lexer is
one-or-two chars, =#[token]=, and NON-CONSUMING — =$= =&= =~= =@= =%= =#=, =->=
=<-= =>=. None decides how far it reaches; the PARSER decides, from grammar. The
only span-consuming tokens are strings and comments, and they are precisely
where this lexer's scar tissue is (BUG-040, BUG-041, BUG-072, BUG-224 — every
one an "it swallowed the rest of the file" bug). The item proposed a fifth.

So: the backtick is now a one-char =BACKTICK= token, beside its siblings.

** The actual leak, which the item did not name

=raw_tokenize= had NO error category. An unrecognised byte was pushed as
=RawToken::Minus /* placeholder */= — keeping its span, wearing another token's
identity. =refine= then applied the vendor-prefix merge rule (MINUS + IDENT fuse
for =-webkit-*=) to it:

: "a `b` c"  ->  IDENT("a")  IDENT("`b")  MINUS("`")  IDENT("c")

The hole sigil absorbed INTO an identifier, its partner a minus sign. *That* is
how Spacetime syntax leaked onto the meta-transpiler — not a missing token, a
token that lied and inherited arithmetic's merge rules.

Unknown bytes now get =RawToken::Unknown=, refining to =ERROR=: visible, one byte
wide, fusing with nothing. =parse_arrow_fn_balanced='s documented limitation was
one symptom of this general fault.

** What is NOT fixed, and where it went

A JS template literal inside an =@eval= body still lexes its contents as ordinary
tokens, so a literal ={=/=}= there still mis-counts in a brace-balancing consumer.
That is the item's original motivating defect and it is REAL — but it needs a
lexer MODE (lex JS rules only inside a foreign-code island: an =@eval= payload, an
=%emit js= body), not a token, because the same character means something else and
far more common in Spacetime source. Filed as FUP-193.
