* What this tracks
A Figma/free-canvas view where MANY frames live on one pannable/zoomable plane,
each frame = a PAGE or a page BREAKPOINT of the site under cultivation. Builds on
the builder view (PLAN-051): the single device-frame + $breakpoint vocabulary
generalizes to N frames, each its own breakpoint/page.

* Source-verified enablers (already shipped; from the design doc substrate)
- region_mounts: HashMap<region,fn> + clear_region + /bundles?region=X take ANY
  region -> N frames is a server non-issue.
- A parallel region_layout: HashMap<region,{x,y,z}> would carry frame position
  (mount=what, layout=where; two concerns, two maps).
- Drag is pure-Spacetime: stdlib/macros/drag.st (@drag axis/bounds/threshold/
  on-drop) over stdlib/primitives/gesture.st (pointer-capture, deltas, velocity).
- Hybrid position model (recommended when designed): client owns the live drag
  (@drag + element signal + GPU transform), COMMIT final x/y/z on drop
  (mcp_frame_move) — Figma-style optimistic; matches @drag's on-drop hook.

* UNVERIFIED keystone (must be the de-risking first slice when this is taken up)
Whether @view $sig + @mcp-region function INSIDE an @each-rendered template body
(a region root created per data row). Drawers prove STATIC sibling regions;
@each-of-regions is unproven. The builder view (PLAN-051) deliberately AVOIDS
this (single frame); the free canvas REQUIRES it.

* Open design questions (the "lot of design" the owner flagged)
- frame = page vs breakpoint vs both; how a frame declares which.
- pan/zoom: infinite plane mechanics, viewport transform, min/max zoom (wheel-
  zoom needs one owned primitive — @on has no wheel kind today).
- z-order / focus / click-to-raise semantics.
- layout persistence shape (region_layout) + multi-frame snapshot projection
  (generalize stage_frames beyond the single stage host).
- how breakpoints of one page relate (linked content, independent layout).
- selection across frames; per-frame vs global inspector.
