* Problem

The MCP server target-dir isolation fix (commit fb944a4f, spell.kdl `--target-dir
/home/user/.cache/cargo-target-mcp`) stops the AGENT's default-dir verification
builds (`cargo check|test|build`) from crashing the live server. That half is
solid and proven.

But it leaves a BLIND SPOT: there is no safe way to make a `stdlib/__mcp__/*` or
`src/mcp/*` change take effect LIVE while the server is running.

Mechanism (observed 2026-06-18):
- The live server runs from `cargo-target-mcp/debug/spacetime` (the isolated binary).
- stdlib is compiled INTO that binary via `include_str!` in src/stdlib_embedded.rs,
  so an edited kit/workbench/.st file is invisible to the running server until the
  binary is rebuilt.
- Rebuilding the ISOLATED dir (`cargo build --target-dir <isolated>`) relinks the
  running server's OWN binary under it -> the SAME relink/mmap crash the isolation
  fix was meant to prevent, just deliberately triggered. Nearly did this; caught
  and cancelled the background build in time; server survived.
- A running process also cannot hot-swap its embedded stdlib regardless.

Net: the isolation fix prevents ACCIDENTAL crashes (agent verification builds) but
the INTENTIONAL refresh of MCP source is still a stop-the-world operation. This
session committed two MCP fixes (confirm-kit class collision 5698cb41, workbench
right-rail occlusion fa7febd7) that compile clean but could NOT be shown live --
they are deferred-live until a server restart.

* Current (only) correct refresh path
1. stop the MCP server,
2. rebuild the isolated dir,
3. reload Spell (respawns the server from the fresh binary).
Steps 2-3 cannot happen under the live session that is serving the workbench.

* Why this matters
The whole value of the live MCP environment is tight edit->see-it loops. Today a
stdlib/__mcp__ or src/mcp change has a cold, manual, stop-the-world refresh -- the
opposite of live. Worse, the safe path is non-obvious (the naive "just rebuild"
crashes the server), so it is a foot-gun for the next agent/session.

* Options to evaluate (not yet decided)
- A. Hot-reload stdlib from disk: have the MCP server read stdlib/__mcp__/*.st from
  the FILESYSTEM at mount time (dev mode) instead of only from embedded include_str!
  bytes. Then a kit/workbench edit is live on the next st_mount with zero rebuild.
  Likely the real fix -- removes the rebuild from the inner loop entirely. Scope it:
  a `--stdlib-dir` / env flag on `spacetime mcp` that overlays embedded stdlib with
  on-disk files; production still uses embedded.
- B. Blue/green server: build the new isolated binary to a SECOND dir, launch it on
  a new port, hand off, retire the old. Heavier; needs Spell-side reload orchestration.
- C. Document-only: codify the stop->rebuild->reload runbook in spell.kdl + docs and
  accept the cold loop. Cheapest, but leaves the foot-gun and the slow loop.

Recommendation: A (filesystem stdlib overlay in dev) is the principled fix -- it
makes the live environment actually live for its OWN source, and matches the repo
ethos (the metasystem is self-describing; the server should read its stdlib, not
freeze it at compile time). B/C are fallbacks.

* Acceptance (when picked up)
- Editing a `stdlib/__mcp__/*.st` file and calling `st_mount`/`st_workbench` again
  reflects the change with NO binary rebuild and NO server restart (option A), OR a
  documented, crash-free one-command refresh (option B), OR at minimum a written
  runbook + guard that makes the crash path impossible to hit by accident (option C).
- The confirm-kit (5698cb41) and right-rail occlusion (fa7febd7) fixes are verified
  live once the path exists.
