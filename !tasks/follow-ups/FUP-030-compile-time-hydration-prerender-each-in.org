* Why
=@data= is purely CLIENT-side today. Verify:
- =data-source= primitive (stdlib/primitives/data/source.st) emits a runtime =fetch()=.
- =@each= renders into empty =data-st-source= containers IN THE BROWSER.
- the static export pipeline (src/export/, layers discover→bundle→html→emit) STRIPS
  dev attributes (src/export/html.rs) but NEVER pre-renders content into static HTML.
∴ "compile-time hydration" is a MISSING PIPELINE STAGE, not an optimization.

Stage 3's page-builder canvas must show the REAL rendered page (real data, real
layout) so "edit on the real page" is truthful and the canvas == shipped output. That
FORCES compile-time hydration. It also gives the whole framework SSG/SEO benefits
independent of the CMS.

NOTE: V1 and Stage 2 explicitly DEFER this (they use the existing client-side @each
re-render via DataUpdate → ST.setData for preview). This FUP is the Stage-3 trigger.

* Scope
1. New export stage in src/export/: read =data/*.json= → evaluate =@each= / template
   invocations at build → bake static HTML into the page output.
2. Make hydration a PER-=@data= MODE (compile-time vs live runtime fetch), so it is a
   FLAG, not a fork. (Reuses the @data macro surface in stdlib/macros/type-data.st.)
3. THE FORK (decide here):
   - prerender-only: bake HTML, no client re-attach. Simple. Canvas = static truth.
   - prerender + hydrate-adopt: runtime re-adopts baked DOM for live filtering /
     animation. The SSR "difficulty cliff."
   RECOMMENDATION: prerender-only FIRST (sufficient for the builder canvas; keeps us
   off the cliff). Defer hydrate-adopt until a concrete feature demands it.

* Insights / challenges
- The evaluation engine for @each at build time may overlap with the existing pipeline
  Evaluate/Expand layers (src/pipeline/) — investigate reuse vs a dedicated SSG pass.
- Templates already register their structure (stdlib/macros/template.st) — baking is
  "instantiate template per data row," which the runtime already does client-side; the
  task is doing it in Rust at build.
- Locale interaction: data-source resolves ={locale}= at runtime; the prerender stage
  must bake per-locale (projects already ship locales/en.json + fr.json).

* Acceptance
- Building unkn bakes the talent roster (and other @each sections) into static HTML in
  dist/, matching the live-rendered DOM.
- A per-@data flag selects compile-time vs live hydration.
- The page-builder canvas renders the baked page (parity with shipped output).
