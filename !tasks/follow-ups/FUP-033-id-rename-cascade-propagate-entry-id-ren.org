* Why
=id(Agent)= relations store the bare entry id string (matches unkn convention, chosen
for simplicity over a {"$ref":…} envelope). CONSEQUENCE: renaming an entry's id breaks
every field that references the old id (dangling refs). For local single-user V1 this
is tolerable; as content grows it bites. (If we had chosen typed envelopes in the
id(T) FUP, rename would be cheaper but authoring heavier — this FUP is the cost of the
bare-id choice.)

* Scope (when picked up)
1. On an id change, scan all collections for =id(T)= / =id(T)[]= fields whose type
   targets the changed entry's type, and update matching values.
2. Surface as an explicit, PREVIEWABLE action ("Rename id maria-fontes → maria-f?
   3 talents reference it.") — not a silent global rewrite.
3. Pairs with delete-time integrity (warn-on-delete from the id(T) FUP).

* Acceptance
- Renaming an entry id offers to update referrers; on confirm, all matching =id(T)=
  values are updated; refs stay valid.
