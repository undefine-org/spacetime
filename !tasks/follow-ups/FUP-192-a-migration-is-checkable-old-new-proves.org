* Why — this is the maximalist payoff

A `%migration` that retypes a parameter is, today, an act of faith. Someone
decides `$easing:string` should become `$easing:easing`, edits the declaration,
and finds out from the corpus whether every call site survived.

With `≤` it becomes a THEOREM:

    old ≤ new   →  the migration is a WIDENING. Every value that satisfied the
                   old type satisfies the new one. PROVABLY safe, no sweep.

    otherwise   →  it is a NARROWING, and the table can enumerate exactly which
                   corpus values fall outside the new type — a list, before the
                   change lands, rather than a build failure after.

* Why this matters more than it sounds

This arc measured the cost of getting it wrong. A `:string` -> `:easing`
migration is an UNQUOTING, not a retyping — measured: `easing <- "ease-out"` is
FALSE, `easing <- ease-out` is TRUE. Declaration and every call site must move
TOGETHER, and nothing checks that today.

And the `number ≤ time` trap is the same question from the other side: a blanket
numeric migration made staggers 1000× too slow across twenty files, SILENTLY,
with a green build, because `stagger: 0.05` is seconds and `duration: 600` is
milliseconds. A migration checker that understood the relation would have
refused to call that a widening.
