* Parent: FEAT-137. Design: @research/spacetime-phoenix-liveview-bridge.org §2 Tier 3 / §10.1.

Phoenix push_event (server→client, transient, name-discriminated) is the third
server→client kind — an EVENT, not state (toasts, highlights, confetti).
Modelling it as an assign re-introduces the sticky-state bug (toast re-fires on
reconnect).

* Fix
Server: a declared `pushes` section (symmetric with `events`) — typed,
introspectable, feeding the contract. Page: `@data stream $fx from $lv {
receive to Effect { "flash" => Flash($.payload as FlashMsg); … } }` consumed by
@handle — the SAME receive matcher as signal replies, discriminator = event
name. Bridge: route push_event through to the stream's publishReply
(uncorrelated, fire-once, NOT replayed on reconnect).
