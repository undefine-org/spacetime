* Why
In the Stage-3 page builder, the project's =@templates= ARE the component palette
(auto-discovered from the template registry; each shows its typed signature — binding
params = data needs, element params = slots; verified at stdlib/macros/template.st:110
=%registers template($name) { params: $params … }= where param_list =
[{name, kind: binding|element, optional}]). The way a project's component library GROWS
is a designer selecting a chunk of canvas and promoting it into a new =@template=. This
CLOSES THE LOOP: the builder doesn't just USE the component model, it GROWS it.

* The hard part: generalization
Extracting a selection into =@template &name($params) { … }= requires INFERRING which
sub-parts become parameters:
- literal text that varies per use → a =$binding= param,
- a nested arbitrary region → an =&element= slot,
- data-bound holes (=$.field=) → preserved bindings.
This is program generalization (anti-unification), not a mechanical cut/paste. It is
the hardest builder feature and the highest-leverage one.

* Scope / questions
1. Selection model on the canvas → the AST subtree(s) selected.
2. Param inference heuristics: what becomes =$param= vs literal vs =&slot=. Start
   CONSERVATIVE (everything literal; the designer marks params) → smarter later.
3. Emit a new =@template= (via EditAst) + replace the selection with an invocation
   =&name(args)=. Round-trips like any other .st write (EditAst handled).
4. Naming + collision handling; where the new template file lives.
5. UX: a "Create component" affordance; preview the inferred signature before commit.

* Insight
This is the inverse of typed composition (Vein 1): composition CONSUMES templates
(typed, valid-by-construction); extraction PRODUCES them. Together they form the growth
loop a real design tool needs. Framer makes you build components in Framer; here the
components ARE the project's code, grown from the canvas.

* Acceptance
- A designer selects a region, names it, and the admin emits a valid =@template= plus an
  invocation that renders identically (compile-time-hydrate parity).
- Inferred params are shown and adjustable before commit.
- The new template appears in the component palette immediately (registry-driven).
