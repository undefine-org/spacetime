* Why

Two hand-maintained mechanisms become queries over the `≤` table once it exists.

** 1. Diagnostics that suggest the fix

Today a type mismatch says what is wrong. With `≤` it can say what would work,
because the table already knows which types are accepted at that slot:

    expected `length`, got `color`
      `length_percentage` accepts both — did you mean to widen the parameter?

That second line is a QUERY (`{t : O ≤ t and E ≤ t}`), not a hand-written hint.
Hand-written hints are the failure mode this arc has deleted eight of: they
drift from the thing they describe.

** 2. Editor widgets at a slot

`%scalar_type` already carries `%widget`. Today an editor can only offer the
EXACT type's widget. With `≤` it can offer every widget valid at that slot — a
`length_percentage` parameter accepts a length picker AND a percentage slider,
and the table says so without either being listed anywhere.

* Verification seeds

- A suggestion must never suggest something that does NOT work. Gate: for every
  suggested type `t` at slot `E`, assert `subtype(O, t) && subtype(E, t)` holds.
  A suggestion that fails its own relation is worse than no suggestion.
- Snapshot the current diagnostics over the corpus before/after; text may
  improve, but no diagnostic should APPEAR or VANISH.
- The widget query must be total: every `%scalar_type` row either yields a
  widget set or is explicitly widget-less. No silent empty.

* Deprecation sweep

`src/diagnostics/suggestions.rs` currently holds `suggest_property()` and
`edit_distance()` (moved there in PLAN-136 W7). Edit-distance suggestion is
CORRECT for a MISSPELLED NAME and WRONG for a type mismatch — the two must not
be conflated when this lands. Keep the former, replace the latter, and say which
is which in the module doc.
