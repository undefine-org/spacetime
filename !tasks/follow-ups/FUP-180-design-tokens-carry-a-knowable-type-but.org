** Why the exemption was right, and why it is now wrong

Per spec a custom property accepts any token stream, so there is no CSS-derived
type to check against — the early return is correct AS CSS.

But these are not arbitrary token streams. They are a DESIGN SYSTEM, and this
compiler now has a type language for exactly these values (`%scalar_type`). A
theme's `--bd-coral-deep: #B43E4A` is a colour in every sense that matters to
the author; only the spec's permissiveness says otherwise.

That is the capability gap: PLAN-122 gave us types for CSS values, and the
largest body of values in the corpus that WANTS typing cannot be typed.

** The structural answer (not a special case)

A token declares its type once, and the declaration is the schema:

    @tokens Brand {
      --ink    color;
      --pad    length;
      --reveal duration;
    }

Then `--ink: #e8ee1` is refused by the SAME `capture_type_accepts` that refuses
`color: #e8ee1`; `var(--ink)` in a colour position is known-good without parsing
the fallback; and FUP-162 gets the type information it needs to fold safely.

Deliberately NOT inferring type from the first value: inference makes the first
value written into law, so correcting a token's type becomes a silent behaviour
change. A declared type is a promise; an inferred one is an accident.
