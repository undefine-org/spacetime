* The deeper problem

Body-item dispatch is a hand-written Rust token ladder: AT_SIGN → directive,
DOLLAR → binding, AMPERSAND → identity, COLON → property, combinators →
selector nesting. A new syntactic category (forms) needed a NEW RUST ARM —
the variants are data (registered forms) but the DISPATCH to them is not. This
is the same shape as FUP-153 (=%registers= declared, consumption hardcoded) and
the same shape as the closed =PresetType= enum: the metasystem can declare
surfaces, but the ASSIGNMENT of input regions to those surfaces is a Rust
match ladder.

=parse_body_item= is also where BUG-243 lived (TILDE falling through to the
preset-ref arm → nested =~ .b { }= compiled to a DESCENDANT selector, silently
wrong output). Arm ORDER in a hand ladder is where silent-wrong-output bugs
grow.

* Research question

Can body-item dispatch itself become registry-driven — i.e. the set of
statement-position prefixes (=@=, =$=, =&=, =:=, combinators, =--=) read from
metasystem data rather than a Rust if-chain — so that adding a syntactic
category is adding a registry entry, full stop?

This likely requires rethinking the matcher's ASSIGNMENT phase (which region of
input is even OFFERED to which grammar), not just the matching phase.
