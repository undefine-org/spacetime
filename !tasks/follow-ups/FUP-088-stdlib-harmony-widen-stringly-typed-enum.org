* Problem
Several stdlib macro forms declare an enum-valued param as a bare :string with a
doc comment listing the choices, instead of a Union capture. The introspection-
generated editor (PLAN-051) renders :string as a free TEXT FIELD; a Union renders
as a validated SEGMENTED/DROPDOWN for free. So the grammar under-describes itself.

Source-verified examples (stdlib/3d):
- @object: shape:string = "icosahedron" (doc: icosahedron|sphere|box|torus|
  torusknot|cone|cylinder|plane); material:string = "standard" (doc: standard|
  physical|glass|basic).
- @light: type:string = "directional" (doc: ambient|directional|point|spot).

* Fix
Widen these to Union captures, e.g.:
  shape: $shape:("icosahedron"|"sphere"|"box"|"torus"|"torusknot"|"cone"|
                 "cylinder"|"plane") = "icosahedron"
  material: $material:("standard"|"physical"|"glass"|"basic") = "standard"
  type: $type:("ambient"|"directional"|"point"|"spot") = "directional"
The form already supports Union (CaptureType::Union; signature.rs renders it).
This makes the value VALIDATED at parse time AND renders a dropdown in the editor
for free.

* Scope
- Audit stdlib for :string params whose /// doc enumerates a fixed choice set
  (grep for "string =" + doc lines with "|"). 3d is the densest; also check
  animation/motion/scene macros.
- Convert each to Union. Verify no call sites break (the values are identical
  strings; Union just constrains them).
- This is a PRECONDITION for the editor to shine on the 3d module (the mockup-58
  3D inspector assumes dropdowns for shape/material).

* Acceptance
- 3d shape/material/light-type are Union; @object/@light still compile + render.
- The dispatch reference (demos/spacetime-docs) shows the Union choices as typed
  tokens.
- An invalid enum value is now a parse error (was silently accepted as a string).
- Tests: existing 3d tests green; a dispatch-probe assertion that the param type
  reads as a union.
