GH-12 @stage element constraint — VERDICT: see bottom (RED → GREEN)

## The defect (GitHub #12)
`@stage` bound to ANY selector with zero compile-time diagnostic. `check` and
`build` both succeeded; the failure was runtime-only: three.js threw inside
`three-stage`'s try/catch because `canvas.getContext` does not exist on a div,
and sibling primitives logged separate `console.warn`s. Nothing rendered, and
nothing in the compiler's output could be searched for.

## The fix (user ruling: element `%scope`)
`@stage` now declares `%scope selector element(canvas)`; the compiler resolves
the bound selector's implied element and refuses when it cannot be a canvas.
`element(<tag>)` is a registry variant alongside `file | selector |
within(<construct>)` — kinds-as-data, not a Rust arm per case.

## The unknowable case — DECIDED: warn-not-error (W0963)
A selector with no element evidence (`.hero`), or a runtime-inserted node,
cannot have its element determined at compile time. Ruling: WARN, do not error.
An error would hard-block the legitimate pattern where a `<canvas>` is created
at runtime (JS) and the `.st` only knows its class. But it must NOT pass
silently — that silence is exactly how GH-23 (and this bug) happened. So
`element()` behaves in three tiers:
  - implied tag == required      → OK (canvas.st: `canvas.hero`)
  - implied tag != required      → ERROR E0963 (index.st: `div.hero`)
  - implied tag unknowable       → WARNING W0963 (unknowable.st: `.hero`)

## Runtime special case demoted
`three-stage.st`'s `new THREE.WebGLRenderer({ canvas, ... })` try/catch is kept
(WebGL genuinely can be unavailable / context-loss) but is no longer the ONLY
signal that a stage is on the wrong element — the compile-time E0963/W0963 fires
first. The sibling `console.warn("[Spacetime] three-stage: target element not
found.")` on a missing `%&el` remains a genuine guard (selector matches 0..N
elements at runtime), distinct from the wrong-ELEMENT case now caught at compile
time.
