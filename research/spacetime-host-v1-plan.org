* Purpose

Concrete, gated, wave-by-wave v1 build plan for Spacetime Host, superseding
the conceptual sketch in =research/spacetime-host-architecture.org= §D/§F
with implementation specifics grounded in DIRECT reads of both source repos
this session (6 parallel explore agents — 3 on =~/code/ora/push-website=,
3 on this repo). Every claim below is either verified-in-source (cited
file:line) or explicitly marked as an open design decision.

Two corrections from user input drove this revision (see companion note in
=research/spacetime-host-architecture.org= §D0 changelog):
1. push-online-server is NOT a wholesale fork target — most of it is dead
   weight once R2+Worker+KV serves traffic (§D0). Only a thin slice reuses.
2. Media (images AND video) routes through Cloudflare Images / Cloudflare
   Stream, not R2 — eliminates the "images only, no video" v1 constraint.

* 0. Ground-truth corrections vs the conceptual doc

These are FACTS discovered this session that change prior assumptions:

** push-online has NO login/signup system

=crates/push-online/src/cli/commands/push.rs:75-85= reads a single static
=PUSH_ONLINE_API_KEY= env var, Bearer-auth'd against ONE shared secret
checked by =require_auth= middleware (=crates/push-online-server/src/
routes/mod.rs=). No accounts table, no per-user token issuance, no
device-code/OAuth flow, no token persisted on disk by the CLI. This is an
agency-internal tool (one operator, many client sites), NOT a self-serve
multi-tenant SaaS. **Item A ("sign-up, log in") has zero prior art — fully
greenfield for v1.**

** push-online-server's Cloudflare integration is a stub

=crates/push-online-core/src/cloudflare.rs= (per this session's read, lines
1-260) contains only TYPES (=SslStatus= enum, =CreateCustomHostnameRequest=
struct) — no HTTP-calling function was found in that file, and
=crates/push-online-server/src/handlers/domains.rs= is explicitly annotated
by the research agent as "Cloudflare integration is stubbed (no real API
calls made)". push-online's actual production custom-domain TLS uses
CADDY'S OWN on-demand-TLS DCV flow (=verify_domain= endpoint, checked
against Caddy's ask), NOT a working Cloudflare-for-SaaS API client. **We
must write the actual Cloudflare-for-SaaS API calls ourselves** — the types
are reusable scaffolding, the integration is not done.

** No preview/production slot concept exists anywhere in push-online

Confirmed via direct schema read (=storage/metadata.rs:47-101=) and
=project.rs=/=project_resolver.rs=: each deploy fully deletes and
re-extracts =projects_dir/{project_id}/= in place
(=storage/files.rs::extract_archive=, "Clears existing files" then
re-extracts). No content hash, no pointer/symlink flip, no versioning
field in the schema. **§D0's content-addressed hash + KV pointer-flip
design has ZERO prior art to fork — it is entirely new logic**, informed
by but not copied from push-online.

* 1. Storage architecture (final, two lanes)

** Lane A — site bytes (HTML/CSS/JS) → Cloudflare R2

Unchanged from =research/spacetime-host-architecture.org= §D0: content-hash
keyed objects (=`{project_id}/{deploy_hash}/...`=), KV pointer table
(=preview=/=production= aliases), =spacetime-host-edge= Worker (Rust via
=workers-rs=) serves via Cache API → R2 fallback.

** Lane B — media (images, video) → Cloudflare Images / Cloudflare Stream

NEW this session, replaces the original "images only, raw upload, no
video" constraint entirely.

*** Images

- Verified pricing: $5/100K images stored/mo, $1/100K images delivered/mo,
  first 5,000 remote-origin transforms/mo free then $0.50/1,000. Up to 100
  named variants (e.g. =thumbnail=, =hero=), generated on first request,
  cached globally after.
- Flow: at =spacetime host push= build time, the orchestrator scans
  =dist/= for image references (png/jpg/jpeg/webp/gif — svg stays a raw R2
  object, Images doesn't transform vector formats), uploads each ONE TIME
  via Cloudflare Images' upload API, receives back an image ID + delivery
  URL template (=https://imagedelivery.net/{account_hash}/{image_id}/
  {variant}=), rewrites the corresponding =<img src>=/CSS =background-image=
  reference in the built HTML/CSS to the delivery URL before it's uploaded
  to R2. Re-pushing an unchanged image (same content hash) is a no-op
  (skip re-upload) — dedup keyed by a content hash we compute client-side,
  since Images doesn't offer content-addressing itself.
- This DELETES =push-online-core='s oxipng/mozjpeg/webp optimization
  dependency from our fork entirely — Cloudflare owns format
  conversion/resizing/quality now, we own zero image-processing code.

*** Video (v1, NOT deferred — the free-ingress economics removes the actual blocker)

- Verified pricing: ingress + encoding FREE always; storage $5/1,000 min
  stored/mo (a 60-min 4K source can transcode to ~240-300 stored minutes
  across ABR renditions — a real cost driver to surface to customers, not
  a blocker); delivery $1/1,000 min delivered/mo, bandwidth INCLUDED (zero
  separate egress).
- Flow: orchestrator requests a Direct Creator Upload URL from Stream's API
  (pre-signed, single-use, scoped to one video UID — our API token never
  leaves the server), CLI/build step PUTs the video bytes to that URL
  (TUS/resumable protocol required over 200MB, 30GB cap), orchestrator
  registers ONE webhook subscription (Cloudflare allows exactly one per
  account — verified) at =/api/webhooks/stream= to learn when transcoding
  finishes (HMAC-SHA256 =Webhook-Signature= header, verify before trusting
  the payload), then rewrites the built =<video>= reference to the Stream
  HLS manifest / player-embed URL.
- The routing Worker (Lane A) NEVER proxies media of either kind — full
  offload to Cloudflare's specialized CDNs. Cleaner separation of concerns
  than one origin serving everything, and removes media entirely from our
  own bandwidth/serving-logic surface area.
- Open question (folded into §8 below): is video a v1 launch feature or a
  fast-follow within v1.x? Recommend LAUNCH FEATURE — free ingress/encoding
  removes the actual cost/complexity blocker that justified deferring it
  originally; the only new work is the Stream API client + webhook
  handler, both thin.

* 2. Accounts & auth — REVISED: WorkOS AuthKit (identity) + thin local API tokens (CLI)

#+begin_quote
DECISION (this session, superseding the original §2 draft below the
changelog note): identity is delegated ENTIRELY to WorkOS AuthKit — we
own zero passwords, zero email-sending, zero magic-link token-expiry
logic. Considered three paths (hand-rolled Rust, Elixir+Ash+
AshAuthentication, managed provider) — full tradeoff writeup is in this
session's chat, condensed rationale here:
- Hand-rolled Rust (Argon2 + our own magic-link table): small but real
  ongoing security surface (token revocation, login rate-limiting,
  timing-safe comparison, email deliverability) we'd own forever.
- Elixir + Ash + AshAuthentication: =elixir/spacetime_lv= is a BARE
  Phoenix LiveView app today (verified via =mix.exs= — zero Ash
  dependency currently), so this path means introducing a SECOND
  deployed runtime (BEAM) a full product-cycle earlier than PLAN-073's
  own v2/v3 sequencing calls for (Elixir was slotted for v3
  live-collaboration only). Either a second network-hop service or a
  full rewrite of the already-scaffolded, =cargo metadata=-verified
  5-crate Rust workspace — more infra, not less.
- WorkOS AuthKit: verified free tier is 1M MAU (this product will not
  approach that ceiling for years), passwordless/magic-link is a
  first-class supported flow, and — discovered this session — WorkOS
  ships an OFFICIAL Rust SDK (=cargo add workos=, crate =workos=,
  =reqwest=-based, typed per-resource client: =client.user_management()=,
  =client.sso()=, etc., =Result<_, workos::Error>= throughout) AND a
  purpose-built CLI device-flow endpoint (=/authorize/device=) that IS
  the =gh auth login=-style browser/CLI handoff §2 was going to hand-roll
  — WorkOS gives us that mechanism natively instead. Only pay for
  enterprise SSO/SCIM connections later ($125→$50/ea at volume) — a
  natural extension path for v2's agency/institutional accounts (§F of
  the conceptual doc), not a rearchitecture.

This is the SAME philosophy already applied to storage/media/domains in
this plan: let a specialized service own a specialized problem, we stay
an orchestrator. Stays 100% Rust, stays in the single already-scaffolded
workspace, zero new runtime.
#+end_quote

** What WorkOS owns vs. what we still build

No identity provider removes the CLI-token layer — a CLI needs a
long-lived bearer credential, not a browser session cookie, regardless of
identity provider. So even with WorkOS:

| Owned by WorkOS | Owned by us (thin) |
|---|---|
| Human signup/login (magic-link, later SSO) | =accounts= table: maps =workos_user_id= → our internal =account_id= |
| Device-flow browser/CLI handoff (=/authorize/device=) | =api_tokens= table: our OWN scoped, revocable bearer token, minted AFTER a WorkOS-verified login |
| Email delivery (magic links) | Nothing — WorkOS sends the email |
| Session/token verification on the WorkOS side | Our own token verification on OUR api calls (SHA-256 lookup, same as before — CLI calls hit OUR server, not WorkOS, per-request) |
| (v2) Enterprise SSO/SCIM | (v2) Org/seat model built on top of =accounts= |

accounts(
  id                     TEXT PRIMARY KEY,      -- nanoid, e.g. "acct_V1StGXR8"
  workos_user_id         TEXT NOT NULL UNIQUE,  -- WorkOS's own user ID, source of truth for identity
  email                  TEXT NOT NULL UNIQUE,  -- cached from WorkOS at login time, for display/lookup only
  created_at             INTEGER NOT NULL,
  stripe_customer_id     TEXT,                  -- NEW (this session, §9): set on first Checkout
  plan                   TEXT DEFAULT 'free',    -- NEW: Stripe Price/Product id or a local plan slug
  subscription_status    TEXT                   -- NEW: mirrors Stripe subscription status
                                                 --   (active/past_due/canceled/...), updated by webhook
)

api_tokens(
  token_hash    TEXT PRIMARY KEY,      -- SHA-256 of the raw token; raw token shown ONCE at creation
  account_id    TEXT NOT NULL REFERENCES accounts(id) ON DELETE CASCADE,
  created_at    INTEGER NOT NULL,
  last_used_at  INTEGER
)
#+end_src

** Login flow (v1, revised)

1. =spacetime host login= → orchestrator calls WorkOS's =/authorize/device=
   endpoint (via the =workos= crate's device-authorization helper) to get a
   =user_code= + =verification_uri= + =device_code=. CLI prints the code and
   URL to the terminal (exactly =gh auth login='s UX) and opens the
   browser automatically if possible.
2. User completes login/signup entirely on WorkOS's hosted AuthKit page
   (magic-link email, or later SSO) — WorkOS handles the email send, the
   token, the expiry, all of it.
3. CLI polls WorkOS's token endpoint (per the device-flow spec, via the
   SDK) until the user completes step 2, receiving a WorkOS-issued token
   plus the =workos_user_id=.
4. Orchestrator's =auth::exchange= endpoint: given a valid WorkOS token,
   upserts an =accounts= row keyed by =workos_user_id= (create on first
   login), mints a NEW local =api_tokens= row scoped to that account,
   returns the raw token ONCE. CLI writes it to
   =$XDG_DATA_DIR/spacetime-host/credentials= (0600 permissions).
5. Every subsequent CLI call sends =Authorization: Bearer {our_token}= to
   OUR server (not WorkOS) — server looks up =SHA256(token)= in
   =api_tokens=, joins to =accounts=, then to =projects.account_id= for
   authorization. Identical to the original design from here on; only
   step 1-4 (how the token gets minted) changed.

This DELETES the original design's email-integration open question
entirely (§8 below) — WorkOS sends the email, we never touch SMTP/a
transactional-email API. Net LESS work than the original hand-rolled
design, not equivalent work moved around.

See §4's server route table — that IS the contract. CLI ↔ server auth:
=Authorization: Bearer {api_token}=, looked up via
=SHA256(token) -> api_tokens.token_hash -> account_id=. No API-key-in-env
pattern like push-online's =PUSH_ONLINE_API_KEY= — tokens are per-account,
minted via the login flow (§2), stored in
=$XDG_DATA_DIR/spacetime-host/credentials= by the CLI.

* 9. Billing — Stripe Checkout + Customer Portal (NEW this session)

User has an existing Stripe account, wants payments in v1 (not deferred).
Same philosophy as storage/media/domains/identity throughout this plan:
let Stripe's hosted pages own the UI, we orchestrate.

** Crate choice (verified this session)

=async-stripe= (the core Rust crate) is still PRE-1.0: =async-stripe-core=
is at alpha.9, "a few breaking changes still expected before RC" per its
own crates.io notice. =async-stripe-webhook= is materially more mature
(rc.5, released ~1 month before this session). Pragmatic split:
- =async-stripe-webhook= (rc.5) for signature verification + event-type
  parsing on incoming webhooks — worth the dependency, near-stable.
- Plain =reqwest= (already a workspace dependency) for the two OUTBOUND
  calls we need (create a Checkout Session, create a Portal Session) —
  both are simple, well-documented POST-with-form-body REST calls, not
  worth pulling in the still-alpha core crate for a 2-endpoint surface.
  If =async-stripe-core= reaches RC/stable before Wave 3 starts, revisit
  — no strong objection to switching, just not worth the alpha risk now.

** Endpoints

| Method | Path | Handler | Notes |
|---|---|---|---|
| POST | =/api/billing/checkout= | =billing::checkout= | creates a Stripe Checkout Session (reqwest POST to Stripe's API), redirects the browser there — Stripe owns the entire payment UI |
| POST | =/api/billing/portal= | =billing::portal= | creates a Customer Portal Session, redirects — Stripe owns the ENTIRE plan-change/cancel/payment-method UI, we build none of it |
| POST | =/api/webhooks/stripe= | =billing::stripe_webhook= | =async-stripe-webhook= verifies the signature, then handles =checkout.session.completed= (set =stripe_customer_id=, =plan=), =customer.subscription.updated=/=.deleted= (update =subscription_status=) |

Functions: =create_checkout_session(price_id, account_id) -> checkout_url=,
=create_portal_session(stripe_customer_id) -> portal_url=,
=verify_and_parse_webhook(body, signature_header) -> StripeEvent= (thin
wrapper around =async-stripe-webhook=).
