* The one-line shape of the break
A `&name($p){ … }` body STOPS being an opaque `$body:component_body` capture re-parsed by a
parallel construct grammar, and BECOMES a scope (like `.sel{}`): the ONE whole-file matcher
finds its nested constructs, span-containment assigns them, the reactive builder lowers its
HTML + mounts its nested matches. Everything that existed ONLY to serve the parallel parser
dies. The IR shrinks to what the builder + editable-schema actually need (HTML + holes +
scope-matches); the construct-classification fields die.

* Sequencing (clean break — ONE cutover, not staged-alongside)
Because the user wants a clean break + no zombies, do NOT run both paths in parallel. Instead:
  S1  Build the SCOPE path complete (template body → scope; param env; builder consumes
      scope-matches; factory payload from scope) on a branch of the work, WITHOUT deleting
      reify yet — but wired as the ACTIVE path (the capture becomes a scope; reify becomes
      unreferenced).
  S2  In the SAME change, DELETE everything in the kill-list. The compiler (removed CaptureType
      arms) + grep gate #1 enforce completeness — the build won't pass with a dangling reference,
      so a zombie literally cannot survive the cutover commit.
  S3  Regenerate/repurpose snapshots + the corpus against the scope path; run the full gate.
  (S1 is the bulk; S2 is mechanical once S1 is active; S3 proves it. No "alongside" phase, no
   feature flag, no dead branch left behind — that is the clean break.)
